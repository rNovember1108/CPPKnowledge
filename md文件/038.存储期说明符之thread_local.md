# 存储期说明符之 thread_local

`thread_local` 是 C++11 引入的存储期说明符，它让变量拥有线程存储期。它的核心作用是：每个线程都拥有该变量的独立实例，互不干扰；该实例的生命周期至多与所属线程相同——在线程启动时或首次使用前构造，在线程正常退出时销毁（异常退出路径不保证析构）。

## 核心特性

- 每线程独立：不同线程访问同一个 `thread_local` 变量时，操作的是各自线程内的那个副本，一个线程的修改不会影响另一个线程。
- 生命周期：命名空间作用域的变量在线程启动时或首次使用（odr-use）前构造（具体时机由实现定义），块作用域的变量在首次执行到声明处构造；两者都在线程正常退出时销毁（异常退出路径不保证析构）。
- 作用域与链接：在 C++ 中，`thread_local` 可与 `static` 或 `extern` 组合，以控制链接性。在块作用域内声明且未出现其他存储类说明符时，隐含 `static` 存储类说明符，但变量实际仍具有线程存储期。

## 应用场景

`thread_local` 的核心用途是在并发编程中，为每个线程提供一份独立的数据副本，从而在不加锁的情况下避免数据竞争。它是标准 C++ 提供的唯一原生线程局部存储机制。

1. 线程安全的全局或类级状态
    当多个线程需要访问某种“全局”状态，但各线程的逻辑又相互独立时，`thread_local` 可以避免锁的开销。例如，每个线程私有的错误码、配置上下文或统计计数器。线程局部数据本身通常不存在数据竞争（因为每个副本通常只有一个线程能访问它），但前提是不要把指针或引用传递给其他线程，否则仍可能产生竞争。

2. 避免重复初始化昂贵资源
    如果某个资源（如内存缓冲区、数据库连接句柄）在线程的多次函数调用中反复使用，且创建成本较高，可以将其声明为函数内的 `static thread_local`。这样，每个线程在首次执行到该声明时初始化（若初始化抛出异常，下次经过声明处会重试），线程内后续调用直接复用，线程正常退出时自动销毁。

3. 替代不可重入的函数接口
   一些 C 风格接口（如 `strtok`、`asctime`）使用静态缓冲区，在多线程下不安全。`thread_local` 可以用来为每个线程提供独立的缓冲区，使这类逻辑变得线程安全。

## 使用方法

### 全局/命名空间作用域使用

在全局或命名空间作用域声明的 `thread_local` 变量，每个线程访问时看到的是自己的副本。示例中两个线程各自对 `x` 自增 3 次，输出互不影响：

```cpp
#include <iostream>
#include <string>
#include <thread>
#include <mutex>

std::mutex cout_mutex;
thread_local int x = 0;

void thread_func(const std::string& name)
{
    for (int i = 0; i < 3; ++i)
    {
        ++x;
        std::lock_guard<std::mutex> lock(cout_mutex);
        std::cout << "thread[" << name << "]: x = " << x << std::endl;
    }
}

int main()
{
    std::thread t1(thread_func, "t1");
    std::thread t2(thread_func, "t2");
    t1.join();
    t2.join();
    return 0;
}
```

两个线程都会从 `x = 0` 开始各自自增，最终各自得到 1、2、3，彼此看不到对方的修改。

### 函数局部作用域使用

块作用域中的 `thread_local` 变量会隐含 `static` 存储类说明符（C++ 标准规定：块作用域的 `thread_local` 若未出现其他存储类说明符，则隐含 `static`），但它的存储期仍是线程存储期。它的作用域仍然限于该代码块；每个线程在首次执行到声明处时初始化（若初始化抛出异常，本次不算已初始化，下次经过声明处会重试），之后同一线程内重复调用函数会复用同一个副本。

> 注意：虽然在 C++ 中，块作用域中的 `thread_local` 变量会隐含 `static` 存储类说明符，但在实践中仍建议保留 `static` 关键字，为了可读性和跨语言兼容性（如在 C 语言中，块作用域的 `_Thread_local` 变量必须同时指定 `static` 或 `extern`，否则无法通过编译）。

```cpp
void thread_func()
{
    thread_local int counter = 0; // 每个线程独立初始化一次
    ++counter;
    std::cout << counter << std::endl;
}
```

同一线程多次调用 `thread_func()`，`counter` 会递增；不同线程各自从 0 开始。注意：不能在块外使用 `counter`，否则编译报错——“作用域没变，只是存储期变了”。

### 类静态成员使用

类的非静态数据成员不能声明为 `thread_local`，只有静态数据成员可以。

```cpp
class MyClass
{
public:
    static thread_local int tls_var; // 声明
    static thread_local std::string tls_str;
};

// 定义（类外，不加 static）
thread_local int MyClass::tls_var = 0;
thread_local std::string MyClass::tls_str = "hello";
```

每个线程访问 `MyClass::tls_var` 时，操作的是该线程自己的那份副本。`MyClass::tls_str` 这类需要动态初始化的对象，会在每个线程首次 odr-use 前分别构造（odr-use 通俗说就是第一次真正需要它的值或地址；具体时机由实现定义，可能提前到线程启动时），线程正常退出时按构造逆序析构。

### 与 static / extern 组合使用

`thread_local` 可以与 `static` 或 `extern` 组合使用，用来调整链接属性：

```cpp
static thread_local int internal_tls = 0;   // 内部链接
extern thread_local int external_tls;       // 外部链接，定义在别处
```

单独使用 `thread_local` 时，命名空间作用域不隐含 `static`：非 `const` 变量默认具有外部链接，`const` 变量仍按 `const` 规则默认具有内部链接；块作用域则隐含 `static` 存储类说明符（如上文所述），前提是声明中没有出现 `extern` 等其他存储类说明符。

## 初始化与析构阶段风险

上述几种使用方法，都需要关注析构风险；初始化风险则因作用域而异。核心风险集中在析构阶段：只要 `thread_local` 对象带有非平凡的析构函数，并且其析构逻辑可能触及其他 `thread_local` 对象，就存在难以诊断的 use-after-free 风险。初始化方面的风险则主要落在类/命名空间作用域和类静态成员使用上，块作用域相对安全。

1. 全局/命名空间作用域
    - 初始化风险：较高。Google C++ 风格指南明确要求，类或命名空间作用域的 `thread_local` 必须用编译期常量初始化（即不能有动态初始化），并用 `constinit`（或 `ABSL_CONST_INIT`）强制这一点。原因是这类变量的初始化顺序与静态变量类似，存在顺序不确定的问题，而且每个线程的初始化时机也难以精确控制。如果允许动态初始化（例如调用构造函数或函数返回值），可能在线程启动或首次使用时触发不可控的代码执行。

    - 析构风险：高。线程正常退出时，`thread_local` 对象按构造的逆序析构。如果 `A` 的析构函数访问了 `B`，而 `B` 已经先被析构（因为 `B` 后构造），就会访问已销毁的对象，造成 use-after-free。这种 bug 极难排查。此外，与全局/静态变量不同，`thread_local` 的析构在异常路径下可能不执行：进程级终止（`std::_Exit`、`std::quick_exit`、`std::terminate`）会跳过析构，但进程随即结束，资源由 OS 回收；若进程继续运行而单个线程被强制终止（如 Windows `TerminateThread`），该线程的 `thread_local` 资源才会真正泄漏。

2. 函数局部作用域
    - 初始化风险：低。函数内的 `thread_local` 在首次执行到声明处时初始化，且每个线程独立初始化自己的副本，不存在跨线程竞争，也不涉及跨翻译单元的初始化顺序问题。如果初始化抛出异常，变量不算已初始化，下次经过声明处会再次尝试。

    - 析构风险：仍然存在。Google 指南在指出函数内 `thread_local` 的初始化风险较低的同时，也强调它在 thread exit 时依然有 use-after-free 风险。也就是说，初始化安全了，析构的坑并没有消失。一个函数内 `thread_local` 的析构函数如果引用了另一个已被销毁的 `thread_local`，行为同样是未定义的。

3. 类静态成员
    - 初始化与析构风险：本质上与命名空间作用域相同。类静态 `thread_local` 成员在存储期和生命周期规则上与全局/命名空间作用域的 `thread_local` 一致，因此同样面临初始化顺序问题和逆序析构的 use-after-free 风险。

综合来看，降低风险的做法是：
1. 优先用平凡类型：`int`、指针等没有析构函数的类型完全绕开析构顺序问题。
2. 非平凡类型尽量放在函数局部：避开初始化顺序的不确定性，但析构风险仍需自行评估。
3. 确保析构函数不触碰其他 `thread_local`：这是最关键的约束。Google 指南指出，如果 `thread_local` 变量的析构函数所触发的代码引用了该线程上已销毁的其他 `thread_local`，就会造成极难诊断的 use-after-free；并建议优先使用平凡类型，或析构时不执行用户代码的类型，以最小化风险。
4. 类/命名空间作用域用编译期常量初始化：避免动态初始化带来的启动期不确定性。

## 注意事项

1. 初始化时机：全局/命名空间作用域的 `thread_local` 由实现定义——可能在线程启动时初始化，也可能延迟到该线程首次 odr-use 前；块作用域的 `thread_local` 在线程首次执行到声明处时动态初始化，若初始化抛出异常，本次不算已初始化，下次经过声明处会重试。非块作用域的 `thread_local` 若动态初始化抛出异常，则会调用 `std::terminate`。
2. 析构时机：线程正常结束时，该线程所有已构造的 `thread_local` 对象按构造逆序析构。跨翻译单元的 `thread_local` 动态初始化顺序是无序的（unsequenced），不要依赖跨 TU 的构造/析构顺序。
3. 地址随线程变化：`&x` 在不同线程中得到的是不同地址（各自副本的地址），不要跨线程保存 `thread_local` 变量的指针或引用。
4. 内存开销随线程数增长：每个 `thread_local` 变量在每个线程中都要占一份存储，线程很多时需注意内存消耗。
5. 不能用于普通类成员：非静态数据成员禁止 `thread_local`。
