# 进程管理与通信（Windows）

## 进程管理

C++ 标准库本身没有完整的进程管理 API，只提供了非常有限的进程相关功能，主要用于终止当前进程或进行环境控制。如果需要使用到进程相关的内容，只能依据操作系统平台来选择其对应的 API，Windows 和 Linux 都各有自己的方法且并不通用。如果你想要代码能够通用，避免写两套平台代码，可以考虑成熟的第三方库：如 `Boost.Process`、`Qt.QProcess` 等。本文主要聚焦 Windows 下创建和控制进程的完整 API 用法。

### 创建进程（CreateProcess）

`CreateProcess` 是 `Windows` 创建进程的核心 API（有 `CreateProcessA`/`CreateProcessW` 两个版本，`W` 版为 Unicode 宽字符版本，推荐使用）。以下简单介绍其参数，详情可以查看 Microsoft 的文档：

```cpp
BOOL CreateProcessW(
    LPCWSTR               lpApplicationName,   // 可执行文件全路径（可为 nullptr，由命令行解析）
    LPWSTR                lpCommandLine,       // 完整命令行（注意：此参数会被函数改写）
    LPSECURITY_ATTRIBUTES lpProcessAttributes, // 进程安全属性（决定句柄能否被子进程继承）
    LPSECURITY_ATTRIBUTES lpThreadAttributes,  // 主线程安全属性
    BOOL                  bInheritHandles,     // 子进程是否继承父进程的可继承句柄
    DWORD                 dwCreationFlags,     // 创建标志（优先级、控制台行为等）
    LPVOID                lpEnvironment,       // 环境变量块（nullptr 表示继承父进程）
    LPCWSTR               lpCurrentDirectory,  // 子进程工作目录（nullptr 表示与父进程相同）
    LPSTARTUPINFOW        lpStartupInfo,       // 子进程主窗口外观、标准句柄等启动信息
    LPPROCESS_INFORMATION lpProcessInformation // [出参] 返回进程/主线程句柄和 ID
);
```

> 提示：Windows NT 内核系列（从 Windows 2000 到现在的 10/11）内部完全使用 UTF-16 LE 编码（即宽字符，`wchar_t`）来处理字符串。使用函数的 A 版本会在内部先转换成 UTF-16，再调用对应的 W 版本，这样会造成额外的开销。并且 W 版本函数使用 UTF-16，与系统语言无关，能正确表示几乎所有语言的字符。A 版本转换时，如果 ANSI 代码页里没有某个字符，会替换成 ?（问号替换），导致出错。

我们使用 `CreateProcess` 来做一个最简单的创建示例：

```cpp
#include <windows.h>
#include <iostream>

int main()
{
    // MSVC下让 wcout 正常输出中文
    std::locale::global(std::locale(""));
    std::wcout.imbue(std::locale(""));

    STARTUPINFOW si = { sizeof(si) }; // STARTUPINFOW 第一个字段 cb 必须初始化为结构体大小
    PROCESS_INFORMATION pi = { 0 }; // 接收新进程的句柄与 ID

    // 注意：lpCommandLine 参数类型是可写的 LPWSTR，CreateProcess 内部会改写该缓冲区，
    // 因此不能直接传入字符串字面量，必须先复制到可写缓冲区
    wchar_t cmdLine[] = L"notepad.exe D:\\test.txt";

    BOOL ok = CreateProcessW(
        nullptr,        // 不指定 exe 路径，由命令行第一个字段解析
        cmdLine,        // 完整命令行
        nullptr,        // 进程安全属性：默认
        nullptr,        // 线程安全属性：默认
        FALSE,          // 子进程不继承父进程句柄
        0,              // 创建标志：默认
        nullptr,        // 继承父进程环境变量
        nullptr,        // 与父进程相同的工作目录
        &si, &pi);

    if (ok)
    {
        std::wcout << L"新进程 PID: " << pi.dwProcessId << std::endl;
        // 创建成功后系统会返回两个句柄（进程句柄 + 主线程句柄），用完必须关闭，否则句柄泄漏
        CloseHandle(pi.hThread);
        CloseHandle(pi.hProcess);
    }
    else
    {
        std::wcout << L"创建失败，错误码: " << GetLastError() << std::endl;
    }
    return 0;
}
```

#### 创建标志（dwCreationFlags）

`dwCreationFlags` 是位掩码，多个不互斥的标志可以用 `|` 组合，常用标志有：

- `CREATE_NEW_CONSOLE`：为新进程分配一个新控制台；
- `CREATE_NO_WINDOW`：不创建控制台窗口（适合 GUI 程序静默调用命令行工具）；
- `CREATE_SUSPENDED`：创建后主线程挂起，配合 `ResumeThread(pi.hThread)` 在合适时机再启动；
- `DEBUG_PROCESS/DEBUG_ONLY_THIS_PROCESS`：将子进程置于调试模式；
- `HIGH_PRIORITY_CLASS`：需要优先调度的进程。

#### 注意事项

1. 命令行缓冲区会被改写：这是最容易踩的坑，传入的 `lpCommandLine` 必须指向可写内存；
2. `lpApplicationName` 与 `lpCommandLine` 的解析规则不同：前者是精确路径，后者按规则解析第一个 `token`（**带空格的完整路径要用引号包裹**），实践中通常 `lpApplicationName` 传 `nullptr`，只用命令行；
3. 返回的 `pi.hProcess` / `pi.hThread` 必须配对 `CloseHandle`，建议先关闭主线程句柄，再关闭进程句柄，以确保资源释放顺序。
4. 有一些创建标志会互斥，如 `CREATE_NEW_CONSOLE`、`CREATE_NO_WINDOW`、`DETACHED_PROCESS` 不能同时设置，三者最多只能选一个。

### 等待进程结束

进程句柄是一个**可等待对象**：进程终止时句柄变为有信号状态，因此可以用等待函数同步。Windows 提供了单个 `WaitForSingleObject()` 和多个 `WaitForMultipleObjects()` 两个函数来等待进程结束。

#### 等待单个进程结束（WaitForSingleObject）

```cpp
// 等待单个子进程退出（第二个参数是超时毫秒数，INFINITE 表示无限等待）
DWORD result = WaitForSingleObject(pi.hProcess, 5000);
if (result == WAIT_TIMEOUT)
{
    // 5s 内进程没有退出
}
else if (result == WAIT_OBJECT_0)
{
    // 进程已退出
}
else if (result == WAIT_FAILED)
{
    // 出错，需 GetLastError 获取错误码
}
```

`WaitForSingleObject` 的第二个参数是超时毫秒数，`INFINITE` 表示无限等待。当你使用 `INFINITE` 时，进程会阻塞等待，直到进程退出或被强制终止。

> 注意：如果使用 `INFINITE` 且等待子进程不退出，当前线程就永远卡住。在 GUI 程序（Qt/MFC）的主线程用 `WaitForSingleObject(hProcess, INFINITE)` 会导致整个窗口假死，连重绘、响应鼠标都不可以，因为 Windows 消息循环被阻塞。

#### 等待多个进程结束（WaitForMultipleObjects）

`WaitForMultipleObjects` 函数的使用会根据第三个参数 `bWaitAll` 来判断是等全部进程还是等任意一个进程结束。

```cpp
// 等待全部进程结束（bWaitAll = TRUE）
DWORD result = WaitForMultipleObjects(
    (DWORD)handles.size(),
    handles.data(),
    TRUE,       // 等待所有句柄通知
    5000
);
if (result == WAIT_TIMEOUT)
{
    // 5s 内进程没有退出
}
else if (result == WAIT_OBJECT_0)
{
    // 所有进程都已退出
}
else if (result == WAIT_FAILED)
{
    // 出错，需 GetLastError 获取错误码
}

// 等待任一进程结束（bWaitAll = FALSE）
DWORD result = WaitForMultipleObjects(
    (DWORD)handles.size(),
    handles.data(),
    FALSE,          // 任意一个通知即返回
    5000
);
if (result == WAIT_TIMEOUT)
{
    // 5s 内没有任一进程退出
}
else if (result >= WAIT_OBJECT_0 && result < WAIT_OBJECT_0 + handles.size())
{
    // 有进程已退出
    DWORD index = result - WAIT_OBJECT_0;  // index 是进程在数组中的索引，从 0 开始
    // 可以根据 index 来判断是哪个进程退出了
}
else if (result == WAIT_FAILED)
{
    // 出错，需 GetLastError 获取错误码
}
```

1. `WaitForMultipleObjects` 第二个参数是进程句柄数组，每个元素是一个进程句柄。第一个参数是句柄数组的大小。
2. `WaitForMultipleObjects` 最后一个参数也是超时毫秒数，`INFINITE` 表示无限等待。当你使用 `INFINITE` 时，进程会阻塞等待，直到满足条件或报错。
3. `WaitForMultipleObjects` 第三个参数 `bWaitAll` 表示是否等全部进程结束。

    ① `bWaitAll` 为 `TRUE` 时，`WaitForMultipleObjects` 会阻塞等待，直到所有进程都退出或被强制终止，使用 `WAIT_OBJECT_0` 可以判断是否所有进程都退出了。

    ② `bWaitAll` 为 `FALSE` 时，`WaitForMultipleObjects` 会阻塞等待，直到任意一个进程退出或被强制终止。使用 `WAIT_OBJECT_0 + n` 可以判断是哪个进程退出了，n 是进程在数组中的索引，从 0 开始（`WAIT_OBJECT_0 + 0` 和 `WAIT_OBJECT_0` 完全等价，只是显式写出了索引 0，通常是为了统一表达式，让代码看起来一致）。当同时有多个进程在同一个等待周期内变为有信号时，返回的是其中索引最小的那个，不是全部。调用方需要在循环里不断调用（配合 `WAIT_OBJECT_0 < result < WAIT_OBJECT_0 + count` 判断完之后再处理下一个，或者继续等），否则会漏掉同时退出的其他进程。

### 获取进程退出码

```cpp
// 获取退出码（即 main/exit 的返回值）
DWORD exitCode = 0;
GetExitCodeProcess(pi.hProcess, &exitCode);
```
若进程尚未退出，`GetExitCodeProcess` 返回 `STILL_ACTIVE`（值为 259，是 Windows API 中专门为进程仍在运行而定义的常量）。由于业务退出码也可能恰好是 259，所以**不要用退出码判断进程是否存活**，应以 `WaitForSingleObject` 和 `WaitForMultipleObjects` 来判断。

### 打开已有进程与终止进程

```cpp
// 通过 PID 打开已有进程（PID 不等于句柄，需用 OpenProcess 转换成句柄才能操作）
HANDLE hProc = OpenProcess(PROCESS_QUERY_INFORMATION | PROCESS_TERMINATE, FALSE, dwPid);
if (!hProc)
{
    // 失败，常见原因：PID 不存在、权限不足（如目标是系统进程）
    DWORD err = GetLastError();
    return;
}
else
{
    // 强制终止进程：不会执行正常清理
    // 只能作为最后手段，正常退出让目标进程自己调用 ExitProcess/PostQuitMessage
    TerminateProcess(hProc, 1);
    // 关闭句柄
    CloseHandle(hProc);
}
```

`OpenProcess` 第一个参数 `dwDesiredAccess` 是请求的访问权限，是一个位掩码，通过按位或 | 组合多个权限标志。系统在打开对象时检查调用者是否有权获得这些权限，如果有，返回的句柄就带有这些权限；否则调用失败。常用权限位：`PROCESS_QUERY_INFORMATION`（查询退出码等）、`SYNCHRONIZE`（等待）、`PROCESS_TERMINATE`（终止）、`PROCESS_ALL_ACCESS`（全部权限）。

> 注意：一个句柄如果带有 `SYNCHRONIZE` 权限，你才能把它丢给 `WaitForSingleObject`、 `WaitForMultipleObjects` 这些等待函数去“盯着”。没有这个权限，等待函数会返回 `WAIT_FAILED`，调用 `GetLastError` 得到 `ERROR_ACCESS_DENIED`。

使用 `TerminateProcess` 函数强制终止进程，会造成以下问题：
- 不会发送 `DLL_PROCESS_DETACH` 通知， DLL 里的 `DllMain` 清理代码不执行；
- `atexit` 注册的函数不执行；
- 进程内存里的文件缓冲区不会 flush（虽然内核最终会关闭句柄，但 CRT 层的缓冲数据可能丢）；
- 目标进程如果开了子进程/线程，这些进程变成孤儿。

### 枚举系统进程（进程快照）

```cpp
#include <windows.h>
#include <iostream>
#include <tlhelp32.h>

int main()
{
    std::locale::global(std::locale(""));
    std::wcout.imbue(std::locale(""));

    // 拍摄进程快照
    HANDLE hSnap = CreateToolhelp32Snapshot(TH32CS_SNAPPROCESS, 0);
    PROCESSENTRY32W pe = { sizeof(pe) };
    if (Process32FirstW(hSnap, &pe))
    {
        do
        {
            std::wcout << L"PID: " << pe.th32ProcessID
                << L"  进程名: " << pe.szExeFile << std::endl;
        } while (Process32NextW(hSnap, &pe));
    }
    CloseHandle(hSnap);
    return 0;
}
```

注意： `PROCESSENTRY32W` 的 `dwSize` 字段必须先初始化为结构体大小，否则 `Process32FirstW` 会失败。

### ShellExecute 与 ShellExecuteEx

`ShellExecute` 是 Windows Shell API 提供的一个函数，用于打开文件、执行程序、浏览文件夹、打印文档、发送邮件等操作。它和 `CreateProcess` 不同：`CreateProcess` 直接创建进程，而 `ShellExecute` 通过 Shell 的关联机制来决定用什么程序打开目标。`ShellExecuteEx` 是 `ShellExecute` 的一个扩展，它支持更多参数，如设置工作目录、环境变量、是否等待子进程退出等。

```cpp
#include <windows.h>
#include <shellapi.h>

// 用系统默认浏览器打开网址
ShellExecuteW(nullptr, L"open", L"https://www.baidu.com", nullptr, nullptr, SW_SHOWNORMAL);

// 用关联程序打开文档（如 .txt 会打开记事本）
ShellExecuteW(nullptr, L"open", L"D:\\test.txt", nullptr, nullptr, SW_SHOWNORMAL);

// 以管理员权限运行（"runas" 动词会触发 UAC 提权对话框）
ShellExecuteW(nullptr, L"runas", L"cmd.exe", L"/c dir", nullptr, SW_SHOWNORMAL);
```

两者对比：

- `CreateProcess`：能拿到子进程句柄/PID，可等待、可重定向标准输入输出，但只支持 `exe`，不能提权；
- `ShellExecute`：支持文档关联、`URL`、`runas` 提权，但拿不到子进程信息（返回的 `HINSTANCE` 不是真正的内核句柄，它只是一个历史遗留的返回值约定）；需要句柄时改用 `ShellExecuteEx`（通过设置 `SHELLEXECUTEINFO` 的 `fMask` 为 `SEE_MASK_NOCLOSEPROCESS`，此时 `hProcess` 成员返回子进程句柄，可用于等待进程结束和获取退出码等）。

## 进程间通信（IPC）

Windows IPC（Inter-Process Communication，进程间通信）指的是在 Windows 操作系统上，不同进程之间交换数据或同步操作的机制。由于每个进程拥有独立的虚拟地址空间，无法直接访问对方的内存，因此需要操作系统提供的专门机制来跨越边界。

### 匿名管道

匿名管道是一个单向字节流，没有名字，无法通过名称被无关进程打开。两端是两个句柄，依赖句柄继承（通常通过**父子进程**关系）在进程间传递，典型用途是捕获子进程的标准输出。如下示例实现一个简单的匿名管道通信，将子进程的标准输出（`cmd` 下执行 `ipconfig`）捕获到父进程的控制台：

```cpp
#include <windows.h>
#include <iostream>

int main()
{
    // bInheritHandle = TRUE，用于继承
    SECURITY_ATTRIBUTES sa = { sizeof(sa), nullptr, TRUE };

    // 创建匿名管道，得到一读一写两个句柄
    HANDLE hRead = nullptr, hWrite = nullptr;
    if (!CreatePipe(&hRead, &hWrite, &sa, 0))
        return -1;

    // 管道两端默认都可继承，但父进程自己的读端不需要被子进程继承，显式取消
    SetHandleInformation(hRead, HANDLE_FLAG_INHERIT, 0);

    STARTUPINFOW si = { sizeof(si) };
    si.dwFlags = STARTF_USESTDHANDLES;  // 启用自定义标准句柄
    si.hStdOutput = hWrite;  // 子进程标准输出接到管道写端
    si.hStdError = hWrite;  // 子进程错误输出接到管道写端

    wchar_t cmd[] = L"cmd.exe /c ipconfig";
    PROCESS_INFORMATION pi = { 0 };

    // bInheritHandles 必须为 TRUE，否则子进程拿不到写端
    if (!CreateProcessW(nullptr, cmd, nullptr, nullptr, TRUE, CREATE_NO_WINDOW,
        nullptr, nullptr, &si, &pi))
    {
        CloseHandle(hRead);
        CloseHandle(hWrite);
        return -1;
    }

    // 不需要操作子进程线程句柄，先关闭
    CloseHandle(pi.hThread);

    // 关键：父进程读完前不需要写端，立即关闭。
    // 否则管道写端在父进程也保留一份，子进程退出后 ReadFile 也检测不到管道关闭
    CloseHandle(hWrite);

    char buffer[4096] = {};
    DWORD bytesRead = 0;

    // 循环读取，子进程退出后写端关闭，ReadFile 返回 FALSE（ERROR_BROKEN_PIPE）结束循环
    while (ReadFile(hRead, buffer, sizeof(buffer) - 1, &bytesRead, nullptr) && bytesRead > 0)
    {
        buffer[bytesRead] = '\0';
        std::cout << buffer;  // 注意：控制台程序输出通常是 GBK 编码，乱码时需做编码转换
    }

    WaitForSingleObject(pi.hProcess, INFINITE);

    CloseHandle(hRead);
    CloseHandle(pi.hProcess);
    return 0;
}
```

补充说明：
1. 之所以依赖父子进程关系，是因为匿名管道没有名字，只能通过句柄来使用，父子进程之间可以继承句柄，是最适宜的方式。当然你也可以使用 `DuplicateHandle` 来复制句柄，打破父子进程关系，但仍然需要通过其他的 IPC 手段将句柄值告诉目标进程，用在当前的场景下有些舍本逐末。
2. `CreateProcessW` 中 `CREATE_NO_WINDOW` 用于禁止子进程弹出独立的 cmd 黑窗口。如果不加这个标志，运行时会一闪而过一个控制台窗口。
3. 创建匿名管道（`CreatePipe`）时需要指定 `SECURITY_ATTRIBUTES` 结构体，设置 `bInheritHandle` 为 `TRUE`，确保管道句柄可以被子进程继承。创建子进程（`CreateProcessW`）时，需要指定 `bInheritHandles = TRUE`，确保子进程可以继承父进程的句柄。两者配合使用，确保子进程可以访问管道句柄，从而实现进程间通信。
4. 由于匿名管道是单向的，一边只读一边只写，本例中使用 `SetHandleInformation` 取消了父进程自己的读端的继承权限，确保子进程只能继承写端。
5. 子进程创建完成后，第一时间调用 `CloseHandle(pi.hThread)` 关闭子进程的线程句柄，是因为我们不再需要通过这个句柄去操作那个线程（比如 `WaitForSingleObject`、`SuspendThread`、`SetThreadPriority` 等）。关闭一个线程句柄，并不会终止该线程，也不会影响线程继续运行。这是一个良好的习惯，以免造成资源泄漏。
6. 读取数据之前，使用 `CloseHandle(hWrite)` 关闭父进程的写端句柄，确保管道子进程退出后，读端可以检测到管道关闭。管道的内核对象维护一个引用计数，只要还有任何一个写端句柄存在，管道就认为“可能还有数据要写”。父进程在创建管道后，同时持有读端和写端两个句柄。如果把写端句柄传给子进程后，父进程自己不关闭写端，那么写端句柄的引用计数至少为 2（父进程一份 + 子进程一份）。子进程退出后，它的写端句柄被系统关闭，计数减 1，但父进程那份还在，计数仍大于 0。父进程的 `ReadFile` 会一直阻塞等待，永远不会返回 `ERROR_BROKEN_PIPE`，程序卡死。

### 命名管道

命名管道突破了父子进程的限制，任何进程都可以通过固定名称打开它，支持全双工，甚至可以跨机器（`\\服务器名\pipe\名称`）。它是 Windows 下本机 C/S 架构的经典选择。

**服务端**

```cpp
#include <windows.h>
#include <iostream>

int main()
{
    // 创建命名管道实例（服务端）
    HANDLE hPipe = CreateNamedPipeW(
        L"\\\\.\\pipe\\MyTestPipe",                       // 固定前缀
        PIPE_ACCESS_DUPLEX,                               // 双向：可读可写
        PIPE_TYPE_BYTE | PIPE_READMODE_BYTE | PIPE_WAIT,  // 字节流模式 + 阻塞模式
        PIPE_UNLIMITED_INSTANCES,                         // 允许多实例服务多个客户端
        4096, 4096,                                       // 输出/输入缓冲区大小
        0, nullptr);

    if (hPipe == INVALID_HANDLE_VALUE)
        return -1;

    std::cout << "等待客户端连接..." << std::endl;

    // 阻塞直到有客户端通过 CreateFile 连接上来
    ConnectNamedPipe(hPipe, nullptr);

    char buffer[256] = {};
    DWORD bytesRead = 0;
    if (ReadFile(hPipe, buffer, sizeof(buffer) - 1, &bytesRead, nullptr))
    {
        buffer[bytesRead] = '\0';
        std::cout << "收到: " << buffer << std::endl;
    }

    // 回写一条消息（双工验证）
    const char* reply = "hello from server";
    DWORD bytesWritten = 0;
    WriteFile(hPipe, reply, (DWORD)strlen(reply), &bytesWritten, nullptr);

    DisconnectNamedPipe(hPipe);  // 与当前客户端断开，可再次 ConnectNamedPipe 服务下一个
    CloseHandle(hPipe);
    return 0;
}
```

**客户端**

```cpp
#include <windows.h>
#include <iostream>

int main()
{
    // 客户端用 CreateFile 以 OPEN_EXISTING 方式"打开"管道
    HANDLE hPipe = CreateFileW(
        L"\\\\.\\pipe\\MyTestPipe",
        GENERIC_READ | GENERIC_WRITE,
        0, nullptr, OPEN_EXISTING, 0, nullptr);

    if (hPipe == INVALID_HANDLE_VALUE)
    {
        // 所有管道实例都被占用时返回 ERROR_PIPE_BUSY，
        // 可用 WaitNamedPipe 等待出现空闲实例，之后需要重新 CreateFile 重试
        if (GetLastError() == ERROR_PIPE_BUSY)
            WaitNamedPipeW(L"\\\\.\\pipe\\MyTestPipe", 2000);
        return -1;
    }

    const char* msg = "hello from client";
    DWORD bytesWritten = 0;
    WriteFile(hPipe, msg, (DWORD)strlen(msg), &bytesWritten, nullptr);

    char buffer[256] = {};
    DWORD bytesRead = 0;
    if (ReadFile(hPipe, buffer, sizeof(buffer) - 1, &bytesRead, nullptr))
    {
        buffer[bytesRead] = '\0';
        std::cout << "收到: " << buffer << std::endl;
    }

    CloseHandle(hPipe);
    return 0;
}
```

补充说明：
1. 命名管道是“先有服务端实例，客户端才能打开”。服务端用 `CreateNamedPipeW` 创建，然后 `ConnectNamedPipe` 等待连接；客户端用 `CreateFile` 打开。没有服务端实例时，客户端打开会失败。
2. 命名管道的命名格式固定为 `\\.\pipe\管道名`（本机）、`\\服务器名\pipe\管道名`（跨机器）。
3. 管道模式除 `PIPE_TYPE_BYTE`（字节流）外还有 `PIPE_TYPE_MESSAGE`（消息模式），每个 `WriteFile` 就是一条消息边界，`ReadFile` 恰好读到一条完整消息，不会拆包/粘包；

    ```cpp
    // 服务端：类型和读模式都设为 MESSAGE
    CreateNamedPipeW(L"\\\\.\\pipe\\MsgPipe",
        PIPE_ACCESS_DUPLEX,
        PIPE_TYPE_MESSAGE | PIPE_READMODE_MESSAGE | PIPE_WAIT,
        PIPE_UNLIMITED_INSTANCES, 4096, 4096, 0, nullptr);

    // 客户端：CreateFile 后默认是字节读，必须切换为消息读
    DWORD mode = PIPE_READMODE_MESSAGE | PIPE_WAIT;
    SetNamedPipeHandleState(hPipe, &mode, nullptr, nullptr);
    ```

4. 高并发服务端应配合 `FILE_FLAG_OVERLAPPED`（重叠 `I/O`）实现异步收发，避免 `ConnectNamedPipe`/`ReadFile` 阻塞整个线程。

### 共享内存

共享内存是**速度最快**的 IPC 方式：两个进程把同一块物理内存映射到各自的地址空间，读写就是普通的指针访问，没有任何内核态数据拷贝。它本身**不提供同步**，需要配合命名互斥体/事件使用。

**写入端（数据生产者）**

```cpp
#include <windows.h>
#include <iostream>

int main()
{
    // 创建具名文件映射对象（基于页面文件，不关联磁盘文件），大小 1KB
    HANDLE hMap = CreateFileMappingW(
        INVALID_HANDLE_VALUE,
        nullptr,
        PAGE_READWRITE,
        0, 1024,
        L"Local\\MySharedMem");  // Global\ 前缀跨会话可见；Local\ 仅当前会话

    if (!hMap)
        return -1;

    // 把共享内存映射进本进程地址空间，返回的指针可直接读写
    char* pBuf = (char*)MapViewOfFile(hMap, FILE_MAP_ALL_ACCESS, 0, 0, 1024);
    if (!pBuf)
    {
        CloseHandle(hMap);
        return -1;
    }

    strcpy_s(pBuf, 1024, "hello shared memory");  // 写入后对其他进程立即可见
    std::cout << "写入完成，按回车退出..." << std::endl;
    std::cin.get();

    UnmapViewOfFile(pBuf);
    CloseHandle(hMap);
    return 0;
}
```

**读取端（数据消费者）**

```cpp
#include <windows.h>
#include <iostream>

int main()
{
    // 打开另一个进程创建的具名映射对象
    HANDLE hMap = OpenFileMappingW(FILE_MAP_ALL_ACCESS, FALSE, L"Local\\MySharedMem");
    if (!hMap)
        return -1;

    char* pBuf = (char*)MapViewOfFile(hMap, FILE_MAP_ALL_ACCESS, 0, 0, 1024);
    if (!pBuf)
    {
        CloseHandle(hMap);
        return -1;
    }

    std::cout << "读到: " << pBuf << std::endl;

    UnmapViewOfFile(pBuf);
    CloseHandle(hMap);
    return 0;
}
```

补充说明：
1. 共享内存名字可以为 `Global\共享内存名` 跨会话可见，`Local\共享内存名` 仅当前会话可见。
    > 这里的"会话"指 Windows 登录会话（Session 0 是系统服务会话，交互程序运行在 Session 1 及以后）。不同会话下 `Local\` 前缀对象互相不可见——典型坑是"Windows 服务 + 界面程序"组合，服务在 Session 0、界面在用户会话，都用 `Local\` 会互相打开失败；跨会话须统一改用 `Global\` 前缀。
2. 多进程、多线程读写同一块内存时必须自己加同步，例如使用命名互斥体（Mutex）或事件（Event）。

    ```cpp
    // 创建或打开具名互斥体（内核对象按名字全局唯一）
    HANDLE hMutex = CreateMutexW(...);
    HANDLE hMap = CreateFileMappingW(...);
    void* pView = MapViewOfFile(...);

    WaitForSingleObject(hMutex, INFINITE);
    // 读写 pView
    ReleaseMutex(hMutex);
    UnmapViewOfFile(pView);
    CloseHandle(hMap);
    CloseHandle(hMutex);
    ```

3. 本例中写入端进程调用 `CreateFileMappingW` 创建了对象，而读取端只是调用 `OpenFileMappingW` 打开了对象。所以必须先启动写入端再启动读取端。实际上如果第一个和第二个进程都调用同名 API（即 `CreateFileMappingW`），后启动的进程会得到 `ERROR_ALREADY_EXISTS`，但仍然成功拿到句柄，相当于打开了已有对象。因此，先启动写进程还是读进程，关键在于命名是否一致。
4. `CreateFileMappingW` 的第一个参数决定了映射对象的后端：传 `INVALID_HANDLE_VALUE` 为基于系统页面文件的纯内存映射（不落盘，最后一个句柄关闭后对象即销毁、重启丢失）；传 `CreateFile` 打开的真实文件句柄则为磁盘文件映射（可持久化、跨重启保留，但涉及磁盘 I/O，适合多进程之间或进程与文件之间共享大文件）。
5. 超大数据的处理使用分块 + 按需映射。`MapViewOfFile` 不必一次把整个映射对象全部映射进来，可通过 `dwFileOffset` 和 `dwNumberOfBytesToMap` 只映射当前要读写的一段（类似滑动窗口），用完 `UnmapViewOfFile` 再映射下一段。这对超大对象（如共享大文件、音视频缓冲）尤其重要：对象本身可以很大（`CreateFileMappingW` 的 `dwMaximumSizeHigh/Low` 决定），但每个进程的地址空间（尤其 32 位进程）有限，一次全量映射既浪费地址空间、也可能失败；分块 + 按需映射既省地址空间，又避免一次性占满物理内存。
6. 共享内存只能存放 POD 结构体（只含定长字段、数组等），不能存放复杂对象和指针。

    ① 复杂对象：如含内嵌指针的结构体、含 `std::string`、`std::vector`、`std::shared_ptr` 的结构体、含虚函数表指针的 C++ 对象、含 `HANDLE`、`HWND`、`COM` 的结构体等。这些只有在写入它的那个进程的地址空间里有效，换一个进程映射同一块内存，这个对象值就毫无意义，甚至会导致崩溃。可以考虑第三方方案（如：`Boost.Interprocess`）。

    ② 指针：进程一在共享内存里存的指针指向的是进程一地址空间的堆地址；进程二读到同一数值，指向的却是进程二地址空间中完全无关的位置，解引用即崩溃。

    ③ 即使是 POD 结构体，也要保证两个进程用相同的编译器、相同的结构体对齐设置、相同的 ABI。32 位进程和 64 位进程之间，指针大小和结构体布局都不同，不能共享同一套结构体定义。

### WM_COPYDATA 消息

`WM_COPYDATA` 是 Windows 专门为"向另一个进程的窗口发一块只读数据"设计的消息，系统负责把数据拷贝到目标进程地址空间，简单安全，但只能**单向、同步、小数据**（实践上单次建议不超过几十 KB，过大会让发送方 `SendMessage` 同步阻塞过久，拖慢目标窗口消息循环）。

**发送端**

```cpp
#include <windows.h>

int main()
{
    // 按窗口标题找到目标窗口（也可用类名查找）
    HWND hwnd = FindWindowW(nullptr, L"接收端窗口标题");
    if (!hwnd)
        return -1;

    wchar_t msg[] = L"hello from WM_COPYDATA";
    COPYDATASTRUCT cds = {};
    cds.dwData = 1;             // 自定义标识，接收方用它区分消息类型
    cds.cbData = sizeof(msg);   // 数据字节数
    cds.lpData = msg;           // 数据指针

    // SendMessage 同步阻塞：直到目标窗口处理完该消息才返回
    SendMessageW(hwnd, WM_COPYDATA, (WPARAM)nullptr, (LPARAM)&cds);
    return 0;
}
```

**接收端**（在窗口过程中处理）

```cpp
LRESULT CALLBACK WndProc(HWND hwnd, UINT msg, WPARAM wParam, LPARAM lParam)
{
    switch (msg)
    {
    case WM_COPYDATA:
    {
        // pcds 由系统跨进程投递，接收方只能读，不能修改其内容
        COPYDATASTRUCT* pcds = (COPYDATASTRUCT*)lParam;
        if (pcds && pcds->dwData == 1)
        {
            MessageBoxW(hwnd, (wchar_t*)pcds->lpData, L"收到消息", MB_OK);
        }
        return TRUE;  // 处理后必须返回 TRUE
    }
    // ... 其他消息 ...
    }
    return DefWindowProcW(hwnd, msg, wParam, lParam);
}
```

注意事项：
1. `PostMessage` 不能发送 `WM_COPYDATA`（使用 `PostMessage`，消息会先进入目标线程的消息队列，等目标线程稍后取出处理。发送方可能已经返回，`COPYDATASTRUCT` 和 `lpData` 指向的缓冲区可能已经释放或复用），必须使用同步的 `SendMessage`。
2. `WM_COPYDATA` 必须有一个目标窗口句柄，无窗口的后台进程、服务（Session 0）不适合用它。跨会话发送通常受会话隔离限制。
3. 窗口过程里要处理 `WM_COPYDATA`，并返回 `TRUE` 表示已处理。返回 `FALSE` 或未处理，发送方会得到失败。同时不要在接收方保存 `lpData` 指针，因为消息返回后那块内存就失效了，需要自己拷贝走。
4. `WM_COPYDATA` 对 `lpData` 不做任何编码/结构约定。发送端发的是 `wchar_t*` 还是 `char*`、是否带结尾 `\0`，接收端必须按同一约定解析，否则乱码或越界。`dwData` 字段就是用来区分数据格式/类型的（如 1=文本、2=自定义结构体），双方要提前约定。
5. 从 Windows 8 起，受 UIPI（用户界面特权隔离）限制，低完整性级别的进程默认会丢弃来自更高完整性级别进程的窗口消息（含`WM_COPYDATA`）。典型场景：管理员权限的进程向普通权限窗口发消息会静默失败。目标窗口需用 `ChangeWindowMessageFilterEx(hwnd, WM_COPYDATA, MSGFLT_ALLOW, nullptr)` 显式放行。

### 剪贴板

剪贴板是由 Windows 系统管理的全局共享、单所有者数据交换机制，用户复制粘贴是它最常见的触发方式，程序也可自动读写。它采用快照式传递，写入后数据由系统接管，不是持续通信通道。

**写入端**

```cpp
bool WriteTextToClipboard(const wchar_t* text)
{
    if (!OpenClipboard(nullptr))
    {
        return false;
    }

    // 清空剪贴板，释放旧数据的所有权
    if (!EmptyClipboard())
    {
        CloseClipboard();
        return false;
    }

    // 计算字节数，包含结尾的 L'\0'
    size_t bytes = (wcslen(text) + 1) * sizeof(wchar_t);

    // 必须用 GMEM_MOVEABLE 分配，系统接管后由系统释放
    HGLOBAL hMem = GlobalAlloc(GMEM_MOVEABLE, bytes);
    if (hMem == nullptr)
    {
        CloseClipboard();
        return false;
    }

    // 锁定内存，拷贝数据，解锁
    void* p = GlobalLock(hMem);
    if (p == nullptr)
    {
        GlobalFree(hMem);
        CloseClipboard();
        return false;
    }
    memcpy(p, text, bytes);
    GlobalUnlock(hMem);

    // 交给系统；成功后不能再 GlobalFree(hMem)
    if (SetClipboardData(CF_UNICODETEXT, hMem) == nullptr)
    {
        GlobalFree(hMem);   // 失败时所有权仍在自己，需要释放
        CloseClipboard();
        return false;
    }

    // 成功后 hMem 归系统所有，不要释放
    CloseClipboard();
    return true;
}
```

**读取端**

```cpp
std::wstring ReadTextFromClipboard()
{
    std::wstring result;

    if (!OpenClipboard(nullptr))
    {
        return result;
    }

    // 检查是否有 Unicode 文本格式
    if (!IsClipboardFormatAvailable(CF_UNICODETEXT))
    {
        CloseClipboard();
        return result;
    }

    HANDLE hData = GetClipboardData(CF_UNICODETEXT);
    if (hData == nullptr)
    {
        CloseClipboard();
        return result;
    }

    // 锁定并读取；不要释放 hData，它属于剪贴板
    const wchar_t* p = static_cast<const wchar_t*>(GlobalLock(hData));
    if (p != nullptr)
    {
        result = p;
        GlobalUnlock(hData);
    }

    CloseClipboard();
    return result;
}
```

注意事项：
1. 剪贴板操作是同步且全局的：`OpenClipboard` 会阻塞其他进程的剪贴板操作，直到你 `CloseClipboard`。所以不要在持有剪贴板时做耗时操作，否则会卡住整个系统的复制粘贴。
2. `GlobalAlloc` 分配全局内存，剪贴板必须用 `GMEM_MOVEABLE`；`GlobalFree` 释放它。关键在所有权：`SetClipboardData` 成功前归写入方，失败必须 `GlobalFree`，成功后归系统、绝不能再释放；读取方拿到的是剪贴板的句柄，只 `GlobalLock/GlobalUnlock`，永远不要 `GlobalFree`。
3. 剪贴板要求用 `GlobalAlloc(GMEM_MOVEABLE, size)` 分配内存。`GMEM_MOVEABLE` 意味着这块内存的物理位置不固定，系统为了整理内存碎片，可以在需要时移动它。如果你拿到了一个 `HGLOBAL` 句柄，但内存随时可能被系统挪走，这个时候你需要使用 `GlobalLock` 和 `GlobalUnlock` 来锁定和解锁。
4. `OpenClipboard` 的参数是"打开剪贴板的窗口句柄"，传 `nullptr` 表示以当前任务名义打开。剪贴板是单所有者，若其它窗口/进程已打开它，`OpenClipboard` 会失败返回 `FALSE`，这也是为什么不能长时间持有它。
5. 除立即提供数据外，剪贴板还支持延迟渲染：`SetClipboardData(format, nullptr)`（数据指针传 `nullptr`）表示"该格式我先声明、暂不提供数据"。当其它程序真正 `GetClipboardData(format)` 时，系统会向剪贴板所有者窗口发送 `WM_RENDERFORMAT`，此时才真正 `SetClipboardData` 提供数据；进程退出前若还有未渲染的格式，会收到 `WM_RENDERALLFORMATS`。适合大图/大文本等复制成本高的场景，避免运行时立刻复制大块内存。
6. 系统对文本格式做了内建转换：写入 `CF_UNICODETEXT` 后，系统会自动为 `CF_TEXT`（ANSI）提供延迟渲染，反之亦然。这就是同一份文本能被"按 Unicode 读"和"按 ANSI 读"的程序同时消费的原因。注意这只针对系统已知的文本格式对，自定义格式不会自动转换。

### 其他方式简述

- **Socket（`localhost` 或跨机器）**：双向、大流量、可跨机器，协议成熟（如 `protobuf` 定协议体）；缺点是要自己处理连接管理与数据边界；
- **邮槽（Mailslot）**：`CreateMailslot` 创建，单向、支持一对多广播，数据报式不可靠（单条建议不超过 424 字节才能保证可靠投递），适合简单通知；
- **自定义窗口消息**：`PostMessage(WM_APP + n)` 或 `RegisterWindowMessage` 广播消息，只能携带两个指针大小的参数（`WPARAM`/`LPARAM`），传指针必须保证目标可访问，大数据量退化为"通知 + 共享内存"；
- **命名内核对象（事件/信号量/互斥体）**：本身不传数据，用于跨进程同步与单实例检测（如 `CreateEventW(nullptr, FALSE, FALSE, L"Local\\AppRunning")` 的 `GetLastError() == ERROR_ALREADY_EXISTS` 判断程序是否已运行）；

### 通信方式一览

| 方式 | 方向 | 进程关系 | 数据量 | 速度 | 典型场景 |
| ---- | ---- | -------- | ------ | ---- | -------- |
| 匿名管道 | 半双工 | 通常父子进程 | 中 | 较快 | 重定向/捕获子进程输出 |
| 命名管道 | 全双工 | 任意进程 | 中 | 较快 | 本机或局域网 C/S 通信 |
| 共享内存 | 双向 | 任意进程 | 大 | **最快** | 大数据量高频交换（音视频帧） |
| WM_COPYDATA | 单向 | 任意进程（需窗口） | 小 | 慢（同步） | 向 GUI 程序发一次性消息 |
| 剪贴板 | 单向 | 任意进程 | 中 | - | 用户复制粘贴交互 |
| Socket | 全双工 | 任意进程 | 大 | 受网络影响 | 本机或跨机器通信 |
| 邮槽 | 单向广播 | 任意进程 | 小 | - | 简单通知/广播（不可靠） |
| 命名内核对象 | - | 任意进程 | 不传数据 | - | 互斥/事件同步、单实例检测 |
