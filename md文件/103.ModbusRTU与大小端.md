Modbus RTU（远程终端单元）是一种基于串行通信的协议，广泛用于工业自动化系统中，用于设备间的数据交换。Modbus RTU协议的消息结构相对固定，主要包括地址字段、功能码、数据长度、数据单元和校验和。下面详细解释每个字段的含义和长度：

1. 设备地址（Slave Address）
‌长度‌：1字节
‌位置‌：消息的起始位置
‌描述‌：这是设备的唯一标识符，用于指定消息的目的地。地址范围通常从0到247（0x00到0x7F）。广播地址是0（不常见，主要用于某些特定的功能码，例如广播查询）。
2. 功能码（Function Code）
‌长度‌：1字节
‌位置‌：紧接着设备地址之后
‌描述‌：指示请求的操作类型。例如，01表示读取保持寄存器，03表示读取输入寄存器，06表示写单个寄存器等。
3. 起始地址（Starting Address）
‌长度‌：1或2字节（取决于功能码）
‌位置‌：紧随功能码之后
‌描述‌：指定要读取或写入数据的起始地址。对于大多数读操作，这是寄存器的地址；对于写操作，这是要写入数据的起始位置。对于某些功能码，如03（读取输入寄存器），起始地址通常是固定的。
4. 数据长度（Number of Registers or Bytes）
‌长度‌：1或2字节（取决于功能码）
‌位置‌：紧随起始地址之后
‌描述‌：指示要读取或写入的数据数量。对于读取操作，这通常是请求的数据量；对于写入操作，这是提供的数据量。在某些情况下，如写单个寄存器操作，此字段可能被省略或设置为1。
5. 数据单元（Data）
‌长度‌：可变，取决于功能码和数据长度字段
‌位置‌：紧随数据长度字段之后
‌描述‌：包含实际的数据内容，如要读取的寄存器值或要写入的寄存器值。对于读取操作，这些数据在响应中返回；对于写入操作，这些是发送给从设备的数据。
6. 校验和（CRC Checksum）
‌长度‌：2字节
‌位置‌：消息的末尾
‌描述‌：用于确保消息在传输过程中未被损坏。校验和是对整个消息（包括地址、功能码、数据字段但不包括校验和自身）进行计算得出的16位CRC值。

示例消息结构
例如，一个读取保持寄存器0x0000开始的4个寄存器的请求消息结构如下：

地址	功能码	起始地址	数据长度	数据单元	校验和
0x01	0x03	0x00 0x00	0x00 0x04	（无）	CRC
注意事项
在实际的串行通信中，起始位、停止位和可能的奇偶校验位也会被包括在内，这些不是Modbus协议的一部分，但会影响到实际的物理层通信细节。
CRC校验和的计算通常在发送前完成，以确保数据的完整性。
通过以上介绍，你应该对Modbus RTU消息的各个部分及其长度有了全面的理解。


大端和小端的‌核心差异是多字节数据在内存中「高位/低位字节的存放顺序」不同‌，具体区别如下：

核心定义对比
表格
对比维度	大端模式（Big-Endian）	小端模式（Little-Endian）
核心规则	高位字节存储在‌低内存地址‌，低位字节存储在‌高内存地址‌	低位字节存储在‌低内存地址‌，高位字节存储在‌高内存地址‌
符合习惯	和人类读写数字的顺序一致，可读性好	符合CPU运算逻辑（加法从低位开始），运算效率更高
典型应用	TCP/IP网络传输、PowerPC处理器、部分嵌入式设备	x86架构PC（Windows/macOS/ Linux）、ARM默认架构
以32位整数0x12345678为例，存储在地址0x1000~0x1003时排列为：

‌大端序‌（地址从低到高）：0x12（高位） → 0x34 → 0x56 → 0x78（低位）
‌小端序‌（地址从低到高）：0x78（低位） → 0x56 → 0x34 → 0x12（高位）


在十六进制表示法（如 0x12345678）中，‌紧接在 0x 后面的是高位字节‌，‌最尾部的是低位字节‌。

详细解释：
‌书写习惯与数值权值‌
计算机中的十六进制数书写遵循人类阅读数字的习惯：‌从左到右，权值由高到低‌。

‌左边（靠近 0x）‌：是最高有效位（MSB, Most Significant Byte），即‌高位字节‌。
‌右边（末尾）‌：是最低有效位（LSB, Least Significant Byte），即‌低位字节‌。
‌举例说明‌
以 32 位整数 0x12345678 为例：

0x12：最高位字节（High Byte）
0x34：次高位字节
0x56：次低位字节
0x78：最低位字节（Low Byte）
‌与内存存储的区别（易混淆点）‌
虽然书写时“左边是高位”，但在‌内存存储‌时，顺序取决于‌字节序（Endianness）‌：

‌大端模式（Big-Endian）‌：内存低地址存高位（0x12），与书写顺序一致。
‌小端模式（Little-Endian）‌：内存低地址存低位（0x78），与书写顺序相反。
‌总结‌：无论内存怎么存，‌写在纸面上或代码里时，0x 后面的永远是高位，最尾的永远是低位。


标准的Modbus RTU数据帧结构为：[设备地址][功能码][数据区][CRC低字节][CRC高字节]，最后两个字节必须严格遵循低字节先发送、高字节后发送的小端序要求，这是协议的强制规范
寄存器存储的数据：协议规定使用大端序（高位字节在前），也就是16位数据先传高位、后传低位
这种混合设计是协议早期遗留的特点，开发中需要分别处理两个部分的字节序，不能统一用一种方式处理。


Intel x86架构优先考虑运算效率，选择了更适合CPU从低位开始运算的小端模式（windows linux）  网络一般使用大端模式
字节序本质由‌硬件处理器架构‌决定，而非操作系统位数。只有极特殊的非x86硬件平台上运行Windows才会改变字节序，这种情况在普通个人设备中几乎不会出现。





## 粘包与分包问题

### 本质

粘包与分包的根源在于：底层 IPC 提供的是**字节流（byte stream）**语义还是**消息（message）**语义。

- **字节流**：发送方多次写入的数据，接收方可能一次就读到全部（粘包），也可能一次只读了一部分（分包），边界完全丢失；
- **消息**：系统以一次写入调用为边界，接收方每次读到的就是一条完整消息。

下面按前几节介绍的方式逐一梳理是否存在这个问题。

### 逐方式分析

#### 不会发生粘包分包的

| 方式 | 原因 |
| ---- | ---- |
| 共享内存 | 就是一块普通内存，没有"发送/接收"的概念，写入即对其他进程立即可见，数据边界由你自己设计的数据结构保证（如固定长度头 + 变长体） |
| WM_COPYDATA | 系统把 `COPYDATASTRUCT` 整体投递到目标窗口的消息队列，一次 `SendMessage` 对应一次 `WM_COPYDATA`，系统保证边界 |
| 剪贴板 | 数据整体放在 `CF_*` 格式里，一次 `GetClipboardData` 拿到完整对象 |
| 命名内核对象 | 只做同步，不传数据 |

#### 取决于模式的

**命名管道**：默认是字节流模式（`PIPE_TYPE_BYTE`），此时会像 TCP 一样发生粘包分包。但如果创建时指定了**消息模式**：

```
// 同时设置 PIPE_TYPE_MESSAGE（服务端写入边界）和 PIPE_READMODE_MESSAGE（客户端按边界读出）
HANDLE hPipe = CreateNamedPipeW(
    L"\\\\.\\pipe\\MyTestPipe",
    PIPE_ACCESS_DUPLEX,
    PIPE_TYPE_MESSAGE | PIPE_READMODE_MESSAGE | PIPE_WAIT,
    ...);
```

消息模式下系统以每次 `WriteFile` 调用为边界，接收端每次 `ReadFile` 恰好读到一条完整消息，天然没有粘包分包。

**邮槽**：本身就是数据报（datagram）语义，一次写入对应一次读取，系统保证边界，但单条数据超过 424 字节可能被系统丢弃（无可靠投递保证）。

#### 一定会发生的（字节流语义）

| 方式 | 分析 |
| ---- | ---- |
| 匿名管道 | 字节流，只有"写入多少字节 → 读出多少字节"，多次写入的输出可能被合并在一次读取中读到 |
| Socket（TCP） | 经典重灾区：Nagle 算法会延迟发送小报文、合并多次发送；对端缓冲区满会拆包。这是最需要自己设计协议解包的场景 |

### 对比总表

| 方式 | 粘包分包风险 | 是否需要自己解包 |
| ---- | ------------ | ---------------- |
| 匿名管道 | 有 | ✅（通常用换行或固定长度分割） |
| 命名管道（字节流） | 有 | ✅ |
| 命名管道（消息模式） | 无 | ❌（系统保证边界） |
| TCP Socket | 有 | ✅（必须设计协议） |
| 邮槽 | 无（数据报） | ❌ |
| 共享内存 | 无（无收发） | ✅（自己设计数据结构） |
| WM_COPYDATA | 无 | ❌ |
| 剪贴板 | 无 | ❌ |

### 解决思路

对于字节流方式（匿名管道、TCP Socket、命名管道字节流模式），必须自行设计帧协议，把字节流切回消息，工程上常用两种做法：

**1. 长度前缀法（最常用）**

每条消息前面加固定长度（通常 4 字节）的字段表示后续数据的字节数，接收方先读长度再读数据体：

```
[4 字节 big-endian 长度][N 字节数据]
```

接收端循环读取：先尝试读 4 字节，不足则继续等；够了再算本次还需要读 `N` 字节，拼成完整消息后再交给业务层。

**2. 分隔符法**

约定一个不可能出现在业务数据中的特殊字节（如文本协议用 `\r\n`，二进制用 `\0`）作为消息边界。优点是简单，缺点是业务数据内不能包含分隔符，因此二进制协议通常不用。

注意：匿名管道捕获命令行输出时，实际上很少出问题，因为命令行工具本身就是换行分隔文本流，按 `\n` 切行处理即可。但如果自己在管道上传输二进制数据，必须套上上面的帧协议。

## 选型建议

1. **捕获子进程命令行输出** → 匿名管道 + `STARTF_USESTDHANDLES`，没有比这更合适的；
2. **本机两个任意进程双向收发命令/小数据** → 命名管道（消息模式）；
3. **大数据量、高频率**（音视频帧、图像流）→ 共享内存 + 命名事件/互斥体同步；
4. **与 GUI 程序做一次性消息交互** → `WM_COPYDATA`；
5. **需要跨机器** → Socket（或命名管道的远程形式，但不推荐新项目使用）；
6. **只是同步/互斥/单实例** → 命名内核对象，不必引入数据通道。

实际工程中常常组合使用：例如"共享内存传数据 + 命名事件做通知 + 命名互斥体做互斥"三件套，是 `Windows` 上高性能生产者-消费者模型的标准写法。

## Linux 进程创建与管理

### 模型差异：fork + exec vs CreateProcess

`Windows` 的 `CreateProcess` 是"一步到位"——创建进程的同时就加载了新程序。`Linux` 则把这个过程拆成了两步，源于 `Unix` 传统：

1. **`fork()`**：父进程复制出一个几乎一模一样的子进程（代码段、数据段、文件描述符表全部拷贝），两个进程从 `fork` 返回点继续并行执行；
2. **`exec` 系列**：子进程把自己的进程映像整体替换成新程序，替换成功后原代码不再执行。

这种拆步模型带来了灵活性：`fork` 之后 `exec` 之前，子进程可以重定向文件描述符（dup2）、修改环境变量、改变工作目录、调整 `uid/gid` 等——这些准备工作在 `Windows` 里要么通过 `CreateProcess` 的参数一次性传完，要么只能先启动再用 `CreateRemoteThread` 注入代码去改，非常不优雅。

### 核心函数

#### fork()

```
#include <unistd.h>
pid_t fork(void);
```

返回值是 `fork` 最关键的设计，通过它区分当前在父进程还是子进程：

| 返回值 | 含义 |
| ------ | ---- |
| `> 0` （子进程 PID） | 当前在父进程中，返回的是刚创建的子进程 PID |
| `0` | 当前在子进程中 |
| `< 0`（-1） | 失败，`errno` 记录原因（常见：系统进程数达到上限 `EAGAIN`、内存不足 `ENOMEM`） |

现代 `Linux` 的 `fork` 使用**写时复制（Copy-On-Write, COW）**：父子进程共享同一块物理内存页表，只有当某一方第一次尝试写入某个页时，内核才复制出一份新的物理页。因此 `fork` 本身并不复制数据，开销很小。

#### exec 系列

`exec` 有六种变体，分三组命名规则：

| 变体 | 参数形式 | 程序定位方式 | 是否可指定环境变量 |
| ---- | -------- | ------------ | ------------------ |
| `execl` | 可变参数列表 + `NULL` 结尾 | 必须给完整路径 | ❌（继承父进程） |
| `execlp` | 可变参数列表 + `NULL` 结尾 | 可只给文件名，自动在 `PATH` 里搜索 | ❌ |
| `execle` | 可变参数列表 + `NULL` + 环境变量数组 | 必须给完整路径 | ✅ |
| `execv` | `char* argv[]` 数组（以 `NULL` 结尾） | 必须给完整路径 | ❌ |
| `execvp` | `char* argv[]` | 可只给文件名 | ❌ |
| `execvpe` | `char* argv[]` | 可只给文件名 | ✅ |

命名规则：`l` = list（可变参数），`v` = vector（数组），`p` = PATH 搜索，`e` = environment。

```
// execlp 等价于在 shell 里敲 "ls -l /tmp"
execlp("ls", "ls", "-l", "/tmp", NULL);
//          ↑     ↑     ↑      ↑     ↑
//          文件名  argv[0]  argv[1]  argv[2]  必须 NULL 结尾

// execv：把命令行先组装成数组
char* args[] = {"ls", "-l", "/tmp", NULL};
execv("/bin/ls", args);     // 完整路径

// execve（底层系统调用，其他 exec 都封装它）可同时指定 argv 和环境变量
char* env[] = {"HOME=/root", "PATH=/bin", NULL};
execve("/bin/ls", args, env);
```

**关键点**：`exec` 成功时**不返回**——当前进程的代码段、数据段、堆、栈全部被新程序覆盖，替换后从 `main` 重新执行。只有 `exec` **失败**时才返回到原代码（返回 -1，`errno` 记录失败原因），通常此时子进程应该立即 `_exit(127)` 终止，避免继续执行父进程的逻辑。

#### wait / waitpid

`fork` 之后父进程应该回收子进程的退出状态，否则子进程会变成**僵尸进程**。

```
#include <sys/wait.h>

// 阻塞等待任意一个子进程结束
pid_t wait(int *status);

// 按 PID 等待，options 可以传 WNOHANG 实现非阻塞轮询
pid_t waitpid(pid_t pid, int *status, int options);
```

`waitpid` 的 `pid` 参数：

| 值 | 含义 |
| -- | ---- |
| `> 0` | 只等待指定 PID 的子进程 |
| `0` | 等待与父进程同进程组的所有子进程 |
| `-1` | 等待任意一个子进程（等价于 `wait`） |
| `< -1` | 等待指定进程组 ID（绝对值）的所有子进程 |

`options` 常用值：

- `WNOHANG`：立即返回，若没有子进程结束返回 0，不阻塞；
- `WUNTRACED`：连被暂停（SIGSTOP）的子进程也返回（默认只返回已终止的）。

`status` 不是简单的退出码，需要用宏解码：

```
if (WIFEXITED(status))          // 子进程正常退出（exit/_exit/main return）
    printf("退出码: %d\n", WEXITSTATUS(status));
else if (WIFSIGNALED(status))   // 子进程被信号杀死
    printf("被信号 %d 终止\n", WTERMSIG(status));
else if (WIFSTOPPED(status))    // 子进程被暂停（仅 WUNTRACED 选项生效）
    printf("被暂停信号 %d\n", WSTOPSIG(status));
```

#### exit / _exit

```
#include <stdlib.h>     // exit
#include <unistd.h>     // _exit

void exit(int status);
void _exit(int status);
```

区别很重要：

| 函数 | 执行清理 | 何时用 |
| ---- | -------- | ------ |
| `exit` | 执行 `atexit()` 注册的函数、刷新 `stdio` 缓冲区（`printf`/`fprintf`）、关闭标准 `I/O` | 普通进程正常结束 |
| `_exit` | 直接调用内核 `exit_group` 系统调用，**跳过所有用户态清理** | `fork` 之后的子进程里，在 `exec` 失败时调用——避免清理函数误操作 |

`fork` 之后子进程里只做了 `exec`，如果 `exec` 失败还继续往下跑，会执行父进程复制过来的 `atexit` 函数和 `stdio` 缓冲区清理，导致重复写入同一个流或执行不该执行的收尾逻辑。所以 `exec` 失败时必须用 `_exit(127)`（127 是 shell 找不到命令时的约定退出码）。

#### getpid / getppid

```
#include <unistd.h>

pid_t getpid(void);    // 当前进程 PID
pid_t getppid(void);   // 父进程 PID
```

基础但高频：`getpid()` 常用于日志打印、生成唯一临时文件名、给 `kill` 发送信号；`getppid()` 用于判断父进程是否已退出（若返回 1，说明已被 `init/systemd` 收养）。

#### signal / kill

Linux 用**信号（Signal）** 做进程间的轻量异步通信，类似 `Windows` 的消息机制。

```
#include <signal.h>
#include <sys/types.h>

// 发送信号：pid 可以是 PID 正数、0（当前进程组）、-1（所有有权限的进程）
int kill(pid_t pid, int sig);

// 注册信号处理器（信号到达时自动调用 handler）
typedef void (*sighandler_t)(int);
sighandler_t signal(int sig, sighandler_t handler);
```

常用信号：

| 信号 | 默认行为 | 触发场景 |
| ---- | -------- | -------- |
| `SIGKILL` | 终止（不可捕获/忽略） | 强杀进程，类似 `Windows TerminateProcess` |
| `SIGTERM` | 终止 | 默认的优雅终止信号，程序应该捕获后做清理 |
| `SIGINT` | 终止 | `Ctrl+C` |
| `SIGCHLD` | 忽略（默认） | **子进程退出/暂停时通知父进程**——解决僵尸进程的关键 |
| `SIGPIPE` | 终止 | 向已关闭的管道写数据（`errno = EPIPE`），网络编程高频陷阱 |
| `SIGALRM` | 终止 | `alarm()` 定时器到期 |

注意：`signal()` 是早期 `Unix` 接口，行为在不同 `libc` 实现里有差异（有的会在首次触发后重置为默认处理器）。生产代码推荐用 `sigaction()` 替代，语义更明确，也支持 `SA_RESTART` 等标志。

### 周边函数

#### system()

```
#include <stdlib.h>
int system(const char *command);
```

`system("ls -l")` 内部就是 `fork` + `exec("/bin/sh", "-c", command)` + `waitpid` 的封装，最简洁但有三个缺点：

1. **阻塞**：当前线程一直等到 shell 执行完；
2. **不可控**：只能通过退出码拿结果，无法拿到子进程的 `PID`，也无法重定向 `stdin/stdout`；
3. **SIGCHLD 干扰**：如果父进程自己也在等子进程，`system` 内部的 `waitpid` 可能"抢走"本该给父进程的子进程状态。

简单脚本化场景可用，正式代码推荐自己写 `fork+exec`。

#### popen() / pclose()

```
#include <stdio.h>
FILE *popen(const char *command, const char *type);
int pclose(FILE *stream);
```

`popen` 比 `system` 好的地方是它返回一个 `FILE*` 管道，能**读写子进程的标准输入输出**：

```
FILE* fp = popen("ls -l /tmp", "r");  // "r" 表示读子进程 stdout；"w" 表示写子进程 stdin
if (fp)
{
    char line[256];
    while (fgets(line, sizeof(line), fp))
        printf("%s", line);   // 注意：父进程的 stdout 是终端，直接 printf 就行
    pclose(fp);
}
```

内部实现是 `fork` + `pipe` + `dup2`（把子进程的 `stdout` 接到管道）+ `execl("/bin/sh", "-c", command)` + 父进程关闭不用的管道端。

#### posix_spawn()

```
#include <spawn.h>
int posix_spawn(pid_t *pid, const char *path,
                const posix_spawn_file_actions_t *file_actions,
                const posix_spawnattr_t *attrp,
                char *const argv[], char *const envp[]);
// 链接时可能需要：-lrt 或 -lpthread
```

`posix_spawn` 是 `POSIX` 标准提供的"一步到位"进程创建接口，语义上等价于 `Windows CreateProcess`。优势是**不会完整复制父进程的地址空间**（不像 `fork`），在内存紧张的嵌入式系统或 `fork` 后立即 `exec` 的场景里比 `fork+exec` 更高效。缺点是灵活性略低于 `fork+exec`（比如 `fork` 后可以做任意复杂的准备工作）。

### 关键概念

#### 僵尸进程与孤儿进程

**僵尸进程（Zombie）**：子进程执行 `exit` 后，内核释放了它的大部分资源（内存、文件描述符），但进程表条目中还保留了它的 `PID`、退出码等信息，等待父进程来 `wait` 回收。如果父进程迟迟不 `wait`，这个子进程就变成僵尸（`ps` 里状态显示 `Z`）。僵尸进程**不占内存但占 PID 号**，PID 号是有限资源，如果僵尸累积太多会导致系统无法创建新进程。

**孤儿进程**：父进程在子进程之前退出，子进程被 `init` 进程（`PID=1`，现代 `systemd` 系统里是 `systemd`）收养，`getppid()` 返回 1。孤儿进程不是问题，它的退出状态最终由 `init/systemd` 负责回收。

#### SIGCHLD 信号处理

处理僵尸进程有三种方案：

**方案一：显式 wait**

父进程创建子进程后立即 `waitpid`，简单但阻塞：

```
pid_t pid = fork();
if (pid == 0) { /* 子进程 exec */ }
else { waitpid(pid, &status, 0); }   // 父进程阻塞等这个子进程
```

**方案二：忽略 SIGCHLD（最省事）**

```
signal(SIGCHLD, SIG_IGN);   // 或 sigaction，设置 SA_NOCLDWAIT 标志
```

告诉内核："我不关心子进程的退出状态，你直接回收"。但有副作用——之后 `wait/waitpid` 都拿不到任何子进程的状态了。

**方案三：注册 SIGCHLD 处理器（工程上最常用）**

```
void on_child_exit(int sig)
{
    int status;
    // 必须用循环：多个子进程同时退出可能只触发一次信号
    // WNOHANG 确保不阻塞（如果没有子进程需要回收就立即返回）
    while (waitpid(-1, &status, WNOHANG) > 0)
    {
        // 可以在这里打日志：pid = waitpid 的返回值
    }
}

signal(SIGCHLD, on_child_exit);
```

注意处理器里**不能调用不安全的函数**——`signal` 处理器运行在异步上下文，任何可能重入的 `libc` 函数（`printf`/`malloc`/`fopen` 等）都可能崩溃。如果需要在处理器里打印日志，要么用 `write()` 系统调用（异步安全），要么把状态保存到一个全局标志里，主循环里再处理。

#### 文件描述符在父子进程间的共享

`fork` 之后，父子进程的文件描述符**指向内核中同一个文件表结构**——类似 `Windows` 里两个句柄指向同一个内核对象。这带来两个重要后果：

1. **读写游标共享**：父进程写了 100 字节，子进程再读会从第 101 字节开始读（除非各自 `lseek` 到不同位置）；
2. **关闭不影响对方**：父进程 `close(fd)` 只是在自己的文件描述符表里删除一项，内核的文件表结构还有子进程引用，真正释放要等两边都关。

这个机制正是管道（`pipe()`）、重定向（`dup2`）等 `Unix` IPC 技巧的基础。

### 完整示例

#### 示例 1：fork + exec + wait 经典流程

子进程执行 `ls -l`，父进程等待并打印退出状态：

```
#include <unistd.h>
#include <sys/wait.h>
#include <stdio.h>
#include <stdlib.h>

int main()
{
    pid_t pid = fork();
    if (pid < 0)
    {
        perror("fork 失败");
        return -1;
    }
    else if (pid == 0)   // 子进程
    {
        // execlp 在 PATH 里查找 "ls"；argv[0] 必须是程序名本身
        execlp("ls", "ls", "-l", "/tmp", NULL);
        // exec 失败才会走到这里，用 _exit 避免清理代码误操作
        perror("exec 失败");
        _exit(127);
    }
    else                 // 父进程
    {
        int status;
        pid_t ended = waitpid(pid, &status, 0);   // 阻塞等这个子进程
        if (ended < 0)
        {
            perror("waitpid 失败");
        }
        else if (WIFEXITED(status))
        {
            printf("子进程 %d 正常退出，退出码: %d\n", ended, WEXITSTATUS(status));
        }
        else if (WIFSIGNALED(status))
        {
            printf("子进程 %d 被信号 %d 终止\n", ended, WTERMSIG(status));
        }
    }
    return 0;
}
```

#### 示例 2：popen 捕获子进程输出

等价于在 `Windows` 里用匿名管道重定向子进程 `stdout`：

```
#include <stdio.h>

int main()
{
    FILE* fp = popen("cat /proc/version", "r");   // 读取内核版本信息
    if (!fp) { perror("popen"); return -1; }

    char buf[512];
    while (fgets(buf, sizeof(buf), fp))
        printf("%s", buf);   // 把子进程的输出打印到自己的 stdout

    pclose(fp);
    return 0;
}
```

#### 示例 3：自定义 SIGCHLD 处理器回收僵尸进程

适合父进程创建很多子进程、不想每创建一个就阻塞 `wait` 的场景：

```
#include <signal.h>
#include <sys/wait.h>
#include <unistd.h>
#include <stdio.h>

volatile sig_atomic_t g_child_exit_count = 0;   // 信号处理器与主循环共享用 sig_atomic_t

void on_child_exit(int sig)
{
    int status;
    // 循环 + WNOHANG：确保把所有已退出的子进程一次性清完
    while (waitpid(-1, &status, WNOHANG) > 0)
        g_child_exit_count++;
}

int main()
{
    signal(SIGCHLD, on_child_exit);

    // fork 5 个短生命周期子进程
    for (int i = 0; i < 5; i++)
    {
        if (fork() == 0)
        {
            printf("子进程 %d 运行中 (PID=%d)\n", i, getpid());
            usleep(100 * 1000);   // 子进程休眠 100ms 后退出
            _exit(i);
        }
    }

    // 父进程做别的事，靠信号异步通知
    printf("父进程继续工作，已创建 5 个子进程\n");
    sleep(2);   // 等 2 秒让子进程都退出

    printf("共回收 %d 个已退出的子进程\n", g_child_exit_count);
    return 0;
}
```

#### 示例 4：用 pipe + dup2 重定向子进程 stdout

手动实现 `popen` 的核心逻辑，理解 Unix 下文件描述符传递的本质：

```
#include <unistd.h>
#include <sys/wait.h>
#include <stdio.h>

int main()
{
    int pipefd[2];
    pipe(pipefd);   // pipefd[0] = 读端，pipefd[1] = 写端

    pid_t pid = fork();
    if (pid == 0)              // 子进程
    {
        close(pipefd[0]);          // 子进程不需要读端，关掉
        dup2(pipefd[1], 1);        // 把 pipefd[1] 复制到 fd=1（stdout）
                                   // 之后任何 write(1, ...) 都会写到管道里
        close(pipefd[1]);          // dup2 之后原 pipefd[1] 已经没用了，关掉

        execlp("echo", "echo", "hello from redirected stdout", NULL);
        _exit(127);
    }
    else                        // 父进程
    {
        close(pipefd[1]);          // 父进程不需要写端，关掉

        char buf[256] = {};
        ssize_t n = read(pipefd[0], buf, sizeof(buf) - 1);   // 阻塞读到子进程输出
        printf("收到: %s", buf);

        close(pipefd[0]);
        waitpid(pid, NULL, 0);
    }
    return 0;
}
```

关键点：`dup2(fd, target_fd)` 的语义是"让 `target_fd` 指向 `fd` 所指向的内核对象"，自动关闭 `target_fd` 原来指向的文件。这行 `dup2(pipefd[1], 1)` 之后，子进程的 `stdout` 就不是原来的终端了，而是管道写端。

### Windows vs Linux 进程模型对比

| 维度 | Windows | Linux |
| ---- | ------- | ----- |
| 创建 API | `CreateProcess`（一步到位） | `fork` + `exec`（两步拆开） |
| 进程间传递可执行文件 | 不支持；必须预先把 exe 放到共享位置或用共享内存传文件内容 | `fork` 后父子进程天然共享所有已打开文件描述符（包括 `mmap` 映射的二进制） |
| 进程句柄 vs PID | 句柄是内核对象，权限控制细；PID 只是标识符，`OpenProcess` 需要额外权限 | PID 是唯一标识；`kill()`/`waitpid()` 直接用 PID，无额外权限层 |
| 子进程等待 | `WaitForSingleObject(hProcess, INFINITE)` | `waitpid()`（同步）或信号 `SIGCHLD`（异步） |
| 进程重定向/管道 | `STARTF_USESTDHANDLES` 指定句柄，匿名管道 | `pipe()` + `dup2`，文件描述符继承 |
| 终止进程 | `TerminateProcess(h, code)`（强杀）；正常退出靠目标进程自己 | `kill(pid, SIGTERM)`（优雅）/ `kill(pid, SIGKILL)`（强杀） |
| 僵尸进程 | 无此概念（句柄 `CloseHandle` 即释放） | 必须 `wait/waitpid` 或处理 `SIGCHLD`，否则累积 |
| 文件描述符 | 句柄（`HANDLE`），每个进程独立编号，不共享数字 | 整数（0/1/2 是 stdin/stdout/stderr），`fork` 后父子共享同一个内核文件表 |

## Linux 进程间通信（简述）

与 `Windows` 的命名管道/共享内存/`WM_COPYDATA` 等对应，`Linux` 提供两套 IPC 机制：传统 `System V IPC`（`shmget`/`msgget`/`semget`）和更现代的 `POSIX IPC`（`shm_open`/`mq_open`/`sem_open`）。二者功能重叠，新项目推荐 `POSIX` 版本（接口更统一、基于文件描述符、可以用 `ls`/`rm` 管理）。下面只列最常用的几种。

| POSIX IPC | 对应 Windows | 粘包分包 | 说明 |
| --------- | ------------ | -------- | ---- |
| 匿名管道 `pipe()` | 匿名管道 | 有（字节流） | 父子进程专用，内部 `fd[0]` 读、`fd[1]` 写 |
| 命名管道 `mkfifo` + `open` | 命名管道 | 有（字节流） | 任何进程可通过固定路径 `open("/tmp/myfifo", ...)` 访问；没有消息模式，边界必须自己做 |
| 共享内存 `shm_open` + `mmap` | `CreateFileMapping` + `MapViewOfFile` | 无 | 速度最快；配合 POSIX 信号量 `sem_open` 或互斥体同步 |
| 消息队列 `mq_open` | 无直接对应 | **无**（消息边界保留） | 每条消息独立投递，支持按优先级排序，天然无粘包分包 |
| 信号量 `sem_open` | 命名互斥体 `CreateMutex` | 不传数据 | 跨进程同步计数 |
| 信号 `kill` | `PostMessage` + 注册窗口消息 | 不传数据 | 异步通知，只能传整数信号号 |
| Socket（`localhost`） | Socket | 有（TCP） | 跨机器、跨进程通用；本机可用 `AF_UNIX` 域 Socket（比 TCP 更快） |
| `eventfd` | 事件对象 `CreateEvent` | 不传数据 | Linux 特有：一个 fd 上读写一个 8 字节整数，常用于单进程内线程唤醒 |

选型上，Linux IPC 的粘包分包结论与 Windows 一致：字节流（pipe/FIFO/TCP）需要自己做帧协议；消息队列（POSIX `mq`）天然有边界；共享内存需要自己设计数据结构。
