# CMake（跨平台的构建工具）

## 概述

`CMake` 是一个跨平台的安装（编译）工具，可以用简单的语句来描述所有平台的安装(编译过程)。他能够输出各种各样的 `makefile` 或者 `project` 文件，能测试编译器所支持的 C++ 特性,类似 UNIX 下的 `automake`。只是 `CMake` 的组态档取名为 `CMakeLists.txt`。`Cmake` 并不直接建构出最终的软件，而是产生标准的建构档（如 `Unix` 的 `Makefile` 或 `Windows Visual C++` 的 `projects/workspaces`），然后再依一般的建构方式使用。这使得熟悉某个集成开发环境（IDE）的开发者可以用标准的方式建构他的软件，这种可以使用各平台的原生建构系统的能力是 `CMake` 和 `SCons` 等其他类似系统的区别之处。

在 C/C++ 语言中，`gcc/g++` 是最底层的编译器，它真正负责把源代码编译、链接成可执行文件；`make` 是底层的执行工具，它并不理解代码，只是按照规则调用 `gcc/g++`；`Makefile` 则是这些规则的具体形式，明确写出了哪些文件依赖哪些文件、在什么情况下调用 `gcc/g++` 执行哪些命令；而 `CMake` 站在更高一层，用来描述工程的整体结构，并根据这些结构描述自动生成 `Makefile` 等构建文件。

**开发者用 `CMake` 描述工程结构，`CMake` 根据环境生成构建规则，具体的构建工具负责执行，而编译器只专注于把代码变成程序。每一层只做一件事，大家各司其职。**

![](..\images\b29f2933055205c34b0894fa841631f2.png)

在 Linux 下，常见流程是：

```
cmake -S . -B build
cmake --build build
```

其中：

```
cmake -S . -B build
```

是配置阶段，意思是：

`-S .`：源码目录是当前目录；

`-B build`：**把生成的构建文件放到 `build` 文件夹里。**


```
cmake --build build
```

用于构建，意思是：**进入 `build` 对应的构建目录，调用实际构建工具生成可执行文件或库文件。**

## CMake语法

### 基础规则

1. 大小写不敏感‌：`CMake` 的命令名不区分大小写（例如 `set` 和 `SET` 等效），但为了代码规范，社区通常推荐‌命令使用小写‌。

    **注意：变量名、字符串内容和参数值通常是‌区分大小写‌的。**

2. 命令格式‌：

    ```
    command_name(arg1 arg2 arg3 ...)
    ```

    参数之间使用空格、换行或分号分隔。

3. 注释‌：
    - 单行注释‌：使用 #，从 # 开始直到行尾。

        ```
        # 这是一个单行注释
        message("Hello") # 行尾注释
        ```

    - 多行注释（Bracket Comment）‌：`CMake 3.0+` 支持，使用 `#[[ ... ]]`。

        ```
        #[[
        这是一个
        多行注释
        ]]
        ```

### 变量与列表

在 `CMake` 中，一切皆字符串。列表只是由分号 `;` 分隔的特殊字符串。

1. 定义变量

    使用 set() 命令定义变量。

    ```
    # 定义普通变量
    set(MY_VAR "Hello World")

    # 定义列表（隐式使用分号分隔）
    set(MY_LIST a b c) 
    # MY_LIST 的实际值为 "a;b;c"

    # 定义显式字符串（包含空格）
    set(MY_STR "a b c")
    ```

2. 引用变量

    使用 `${VAR_NAME}` 进行替换。

    ```
    message(${MY_VAR}) # 输出: Hello World
    ```

3. 环境变量

    必须使用 `$ENV{<变量名>}` 语法，不能直接使用 `${<变量名>}`

    ```
    # 获取系统环境变量 HOME 的值
    message(STATUS "Home directory: $ENV{HOME}")

    # 获取 PATH
    message(STATUS "Path: $ENV{PATH}")

    # 判断环境变量是否定义
    if(DEFINED ENV{MY_CUSTOM_VAR})
        message("MY_CUSTOM_VAR is set")
    endif()

    # 设置环境变量（仅在当前 CMake 进程中生效）
    set(ENV{MY_VAR} "Hello World")

    # 清除环境变量
    unset(ENV{MY_VAR})

    # 或者设置为空字符串
    set(ENV{MY_VAR} "")
    ```

    在 `CMakeLists.txt` 中使用 `set(ENV{...})` 修改的值，‌不会‌传递给随后由 `CMake` 启动的构建工具（如 `make`, `ninja`）或测试程序。这是因为这些子进程通常继承的是 `CMake` 启动时的环境快照，或者由构建系统单独管理环境。

4. 列表操作

    CMake 提供了 `list()` 命令来操作列表。

    ```
    set(SOURCES main.cpp utils.cpp)

    # 追加元素
    list(APPEND SOURCES config.cpp)

    # 删除元素
    list(REMOVE_ITEM SOURCES config.cpp)

    # 获取长度
    list(LENGTH SOURENCES LEN)

    # 遍历列表
    foreach(src IN LISTS SOURCES)
        message("Source file: ${src}")
    endforeach()
    ```

5. 重要陷阱：引号与展开

    - 未加引号‌：`${LIST}` 会被展开为多个参数。

        ```
        set(FLAGS -Wall -Wextra)
        add_compile_options(${FLAGS}) # 正确：传递两个参数 -Wall 和 -Wextra
        ```

    - 加双引号‌：`${LIST}` 被视为单个字符串参数。

        ```
        add_compile_options("${FLAGS}") # 错误：传递一个参数 "-Wall;-Wextra"，可能导致编译失败
        ```

    - 最佳实践

        如果变量可能包含空格或作为单个整体传递，请加引号；如果是列表且希望展开为多个参数，通常不加引号（除非在 `if()` 判断中，建议始终加引号以避免空值错误）。

### 消息打印

用于调试或输出信息

```
message(STATUS "Building project...")      # 蓝色/白色信息，默认级别
message(WARNING "This is a warning")       # 黄色警告
message(FATAL_ERROR "Build failed!")       # 红色错误，立即终止 CMake
```

### 转义字符和字符串

1. 转义字符

    ```
    \"  # 双引号
    \\  # 反斜杠
    \;  # 分号
    \n  # 换行符
    \t  # 制表符
    \r  #回车符
    ```

2. 字符串

    `CMake` 提供了两种主要方式来定义包含多行或特殊字符的字符串

    - 双引号字符串 (Quoted Strings): 双引号字符串支持多行书写，但‌会进行变量展开和转义序列处理

        ```
        # 多行字符串，内部包含换行和变量
        set(MULTI_LINE_STR "
            This is line 1.
            This is line 2.
            Variable value: ${CMAKE_VERSION}
            Escape sequence: \\n
        ")
        message(${MULTI_LINE_STR})
        ```

        - 优点‌：支持变量替换。
        - ‌缺点‌：如果字符串中包含大量双引号、反斜杠或美元符号，需要频繁转义，容易出错。

    -  括号参数 (Bracket Arguments)：推荐用于复杂字符串

        这是 `CMake 3.0+` 引入的特性，类似于 `Lua` 语言的长字符串。格式为 `[=[ ... ]=]`。
        - 语法‌：
            以 `[` 开头，后跟任意数量的 `=`，再跟 `[` 开始，以 `]` 开头，后跟相同数量的 `=`，再跟 `]` 结束。
        - 特性‌：
            ‌不进行转义‌：内部的 `\n`, `\"`, `\\` 等都被视为普通字符。
            ‌不进行变量展开‌：`${VAR}` 不会被替换，而是保留原样。
            ‌原生支持多行‌：可以直接换行。
            ‌包含特殊字符‌：可以安全地包含双引号 `"`、分号 `;` 等。

            ```
            # 基本用法
            message([=[
                This is a multi-line string.
                It contains "double quotes" without escaping.
                It contains ${CMAKE_VERSION} literally (no variable expansion).
                It contains backslashes \ like this \.
            ]=])

            # 嵌套括号处理
            # 如果字符串内部包含 ]=]，可以使用更多等号来界定边界
            message([==[
                Inner bracket: ]=]
                This is still part of the string.
            ]==])
            ```
        - 使用场景
            - 编写复杂的正则表达式。
            - 嵌入 `JSON`、`XML` 或 `SQL` 片段。
            - 生成包含大量特殊字符的脚本文件。
            - 需要保留 `${}` 字面量的模板文本。


### 控制流

1. 条件判断（`if()`）

    支持字符串比较、数值比较、布尔运算和路径判断

    ```
    set(OS_NAME "Linux")

    if(OS_NAME STREQUAL "Linux")
        message("Running on Linux")
    elseif(OS_NAME STREQUAL "Windows")
        message("Running on Windows")
    else()
        message("Unknown OS")
    endif()

    # 判断变量是否定义
    if(DEFINED MY_VAR)
        message("MY_VAR is defined")
    endif()

    # 判断文件是否存在
    if(EXISTS "/path/to/file")
        message("File exists")
    endif()
    ```

    **注意：在 `if()` 中引用变量时，‌不需要‌使用 `${}`，直接写变量名即可（例如 `if(MY_VAR)`），除非你需要先展开变量再判断其内容。**

2. 循环 `foreach()` / `while()`

    ```
    # 范围循环
    foreach(i RANGE 1 5)
        message("Index: ${i}")
    endforeach()

    # 列表循环
    set(ITEMS apple banana orange)
    foreach(item IN LISTS ITEMS)
        message("Fruit: ${item}")
    endforeach()

    #while
    while(condition)
        # ...
    endwhile()
    ```

### 函数和宏以及作用域

```
# 函数（独立作用域）
function(my_func arg1 arg2)
    set(result ${arg1}${arg2} PARENT_SCOPE) # 若要在函数内修改外部变量，需使用 PARENT_SCOPE
endfunction()

# 宏（作用域与调用处相同，参数直接展开）
macro(my_macro arg)
    # 可直接修改外部变量
endmacro()
```

`CMake` 的作用域规则较为特殊，分为目录作用域和函数作用域。

- ‌目录作用域‌：在当前 `CMakeLists.txt` 中设置的变量，对当前目录及其子目录（通过 `add_subdirectory` 加入）可见。
- ‌函数作用域‌：`function()` 内部创建的变量是局部的，外部不可见。

**若要在函数内修改外部变量，需使用 `PARENT_SCOPE`**

‌宏（`macro`）‌：没有独立作用域，其行为类似文本替换，直接操作调用者的变量空间（不推荐使用，优先使用 `function`）。


### 运算符

1. 算术运算符‌

    `CMake` ‌不支持‌在普通变量赋值或 `if `语句中直接使用 `+`, `-`, `*`, `/`，`%`，`()`和“位运算”等进行计算。必须使用 `math(EXPR ...)` 命令来执行数学表达式。
    
    ```
    set(A 10)
    set(B 3)

    # 基本运算
    math(EXPR RESULT_ADD "${A} + ${B}")      # 结果: 13
    math(EXPR RESULT_SUB "${A} - ${B}")      # 结果: 7
    math(EXPR RESULT_MUL "${A} * ${B}")      # 结果: 30
    math(EXPR RESULT_DIV "${A} / ${B}")      # 结果: 3 (注意是整除)
    math(EXPR RESULT_MOD "${A} % ${B}")      # 结果: 1

    # 复杂表达式
    math(EXPR RESULT_COMPLEX "(${A} + ${B}) * 2") # 结果: 26

    message(STATUS "Add: ${RESULT_ADD}, Div: ${RESULT_DIV}")
    ```

2. 比较运算符

    比较运算符主要用于 `if()` 语句中。`CMake` 严格区分‌数值比较‌、‌字符串比较‌和‌版本比较‌。

    ```
    set(NUM1 10)
    set(NUM2 20)
    set(STR1 "Hello")
    set(STR2 "hello")
    set(VER1 "1.10.0")
    set(VER2 "1.9.0")

    # 数值比较
    if(NUM1 LESS NUM2)
        message("NUM1 is smaller")
    endif()

    # 字符串比较 (STREQUAL 不区分大小写，所以为真)
    if(STR1 STREQUAL STR2)
        message("Strings are equal (case-insensitive)")
    endif()

    # 版本比较 (1.10.0 > 1.9.0，这是语义化版本比较的优势)
    if(VER1 VERSION_GREATER VER2)
        message("Ver1 is newer")
    endif()
    ```

3. 逻辑运算符

    逻辑运算符用于组合多个条件，主要在 `if()` 语句中使用。

    在 `if()` 中，以下值被视为 ‌`FALSE`‌：

    - `0`, `OFF`, `NO`, `FALSE`, `N`, `IGNORE`, `NOTFOUND`
    - 空字符串 `""`
    - 以 `-NOTFOUND` 后缀结尾的字符串（常用于 `find_library` 失败的情况）
    - 其他所有值（包括非零数字、非空字符串、`ON`, `YES`, `TRUE` 等）均视为 `‌TRUE`‌。

    ```
    option(ENABLE_FEATURE_A "Enable Feature A" ON)
    option(ENABLE_FEATURE_B "Enable Feature B" OFF)

    # 逻辑与
    if(ENABLE_FEATURE_A AND NOT ENABLE_FEATURE_B)
        message("Feature A is on, B is off")
    endif()

    # 逻辑或
    if(ENABLE_FEATURE_A OR ENABLE_FEATURE_B)
        message("At least one feature is enabled")
    endif()
    ```

4. 生成器表达式中的运算符

    在构建系统生成阶段（而非配置阶段），可以使用生成器表达式（Generator Expressions）。它们的语法不同，通常用于目标属性设置。
    - 条件表达式‌: `$<condition:true_string>` 或 `$<IF:condition,true_string,false_string>`
    - ‌逻辑运算符‌:
        - `$<AND:cond1,cond2,...>`
        - `$<OR:cond1,cond2,...>`
        - `$<NOT:condition>`
    - 布尔转换‌: `$<BOOL:string>` (将任意字符串转换为 `0` 或 `1`)
    ```
    # 如果是 Debug 模式且是 Windows 平台，则添加定义
    target_compile_definitions(my_target PRIVATE
        $<$<AND:$<CONFIG:Debug>,$<BOOL:${WIN32}>>:_DEBUG_WIN>
    )
    ```

### option与file

1. option

    在 `CMake` 中，`option()` 命令用于定义一个‌布尔型（Boolean）‌的配置选项。它允许用户在配置阶段（Configuration Stage）通过命令行、CMake GUI来启用或禁用项目的特定功能（如构建测试、启用日志、选择库类型等）。

    ```
    # 定义选项，默认不构建测试
    # ON (或 TRUE, YES, 1)：默认启用。
    # OFF (或 FALSE, NO, 0)：默认禁用。
    # 注意‌：如果省略此参数，默认值为 OFF。
    option(BUILD_TESTS "Build unit tests" OFF)

    if(BUILD_TESTS)
        enable_testing()
        add_subdirectory(tests)
    endif()
    ```

2. file

    `file()` 是 `CMake` 中最强大的命令之一，用于在配置阶段（Configure Time）执行各种文件系统操作。它涵盖了读取、写入、复制、删除、搜索文件以及路径转换等功能。

    ```
    # 收集 include 目录下所有 .h 和 .hpp 文件
    file(GLOB HEADER_FILES 
        "${CMAKE_CURRENT_SOURCE_DIR}/include/*.h"
        "${CMAKE_CURRENT_SOURCE_DIR}/include/*.hpp"
    )

    # 递归搜索 src 目录下所有的 .cpp 文件
    file(GLOB_RECURSE SOURCE_FILES 
        "${CMAKE_CURRENT_SOURCE_DIR}/src/*.cpp"
    )
    ```

## CMake基本使用

### 单文件CMake的使用

组织文件结构如下：

![](..\images\0031694beea6aec53330665ff5e441c8.png)

其中 `main.cpp` 内容如下：

```
#include <iostream>
using namespace std;

int main()
{
    cout << "Hello World" << endl;
    return 0;
}
```

`CMakeLists.txt` 内容如下：

```
cmake_minimum_required(VERSION 3.16) 
project(Hello LANGUAGES CXX)
add_executable(hello main.cpp)
```

其中：

```
cmake_minimum_required(VERSION 3.16)
```

表示这个项目要求 `CMake` 版本至少为 3.16。

```
project(Hello LANGUAGES CXX)
```

定义项目名称为 `Hello`，使用的语言是 C++。

如果是 C 项目，可以写：

```
project(Hello LANGUAGES C)
```

如果同时使用 C 和 C++：

```
project(Hello LANGUAGES C CXX)
```

```
add_executable(hello main.cpp)
```

表示生成一个可执行文件，名字叫 `hello`，由 `main.cpp` 编译而来。

在 Linux 中执行以下命令，生成 `hello`，并运行：

```
cmake -S . -B build
cmake --build build
./build/hello
```

### 多文件CMake的使用

真实项目不会只有一个 `main.cpp`。我们重新组织 `test` 文件夹，添加一个 `math.h` 和 `math.cpp`，实现一个最简单的求和函数。

![](..\images\9ec7e16971f0e33ab67e8a4fc69adbc6.png)

`math.h` 内容如下：

```
#pragma once

int sum(int a, int b);
```

`math.cpp` 内容如下：

```
#include "math.h"

int sum(int a, int b)
{
    return a + b;
}
```

`main.cpp` 内容如下：

```
#include <iostream>
#include "math.h"

using namespace std;

int main()
{
    int total = sum(1 , 2);
    cout << "the sum is:" << total << endl;
    return 0;
}
```

`CMakeLists.txt` 内容如下：

```
cmake_minimum_required(VERSION 3.16) 
project(Test LANGUAGES CXX)
add_executable(test main.cpp math.cpp)
```

再次执行命令，构建编译运行如下：

![](..\images\c7cb20129d171bf59937c6f897cea3f7.png)

`test` 这个可执行文件由 `main.cpp` 和 `math.cpp` 共同编译链接得到。头文件 `math.h` 不一定写进 `add_executable`，因为它不会单独编译。当然也可以写：

```
add_executable(test
    main.cpp
    math.cpp
    math.h
)
```

这不会改变最终链接逻辑，只是让头文件也出现在工程管理中。

另外，组织代码目录结构时，头文件通常会放到 `include` 目录，源文件放到 `src` 目录。

![](..\images\9c369051edd43a32c2b68d8eece0037b.png)

此时 `CMakeLists.txt` 内容更新如下：

```
cmake_minimum_required(VERSION 3.16)
project(Test LANGUAGES CXX)
add_executable(test src/main.cpp src/math.cpp)
target_include_directories(test PRIVATE include)
```

`target_include_directories` 表示：编译 `test` 这个目标时，额外去 `include` 目录里寻找头文件。

### 库文件CMake的使用

真实项目中，通常不会把所有 `.cpp` 都塞进一个 `add_executable` 里。更常见的是一部分代码形成库，`main.cpp` 只负责调用库。我们再重新组织 `test` 文件夹，添加一个 `math_utils` 文件夹，将 `math.h` 和 `math.cpp` 放入其中。

![](..\images\5ef3038705258568a13feca07b36cc18.png)

此时`CMakeLists.txt`内容更新如下：

```
cmake_minimum_required(VERSION 3.16)
project(Test LANGUAGES CXX)

add_library(math_utils math_utils/math.cpp)
target_include_directories(math_utils PUBLIC math_utils)

add_executable(test src/main.cpp)
target_link_libraries(test PRIVATE math_utils)
```

这里构建生成了有两个 `target`：

```
add_library(math_utils math_utils/math.cpp)
```

编译 `math_utils/math.cpp` 创建一个库 `target`，名字是 `math_utils`。在build目录下会生成一个 `libmath_utils.a` 文件。

```
add_executable(test src/main.cpp)
```

编译 `src/main.cpp` 创建一个可执行文件 `target`，名字是 `test`。在build目录下会生成一个 `test` 文件。

再之后：

```
target_link_libraries(test PRIVATE math_utils)
```

表示 `test` 依赖 `math_utils`，所以链接 `test` 时要把 `math_utils` 库链接进去。

由于生成 `math_utils` 时使用的头文件目录属性是 `PUBLIC`：

```
target_include_directories(math_utils PUBLIC math_utils)
```

所以当 `test` 链接 `math_utils` 库时，`test` 也自动获得了 `math_utils` 的头文件搜索路径。

### 静态库和动态库

在生成库文件时，可以选择使用静态库的方式还是动态库的方式来生成。

1. **静态库**就是在**链接阶段**被合并进最终可执行程序的库。写法是：

    ```
    add_library(math_utils STATIC math_utils/math.cpp)
    ```

    `build` 目录会生成一个名为 `libmath_utils.a` 的静态库文件，程序 `test` 运行时，不需要再去找 `math_utils` 这个库文件，因为库里的代码已经被合进 `test` 了。如果我们将生成的 `libmath_utils.a` 重命名为别的名字，不影响test的运行：

    ![](..\images\a737a0c446498420e9c631475a42a220.png)

2. **动态库**不是在链接阶段完全合进程序，而是在程序**运行时被加载**。写法是：

    ```
    add_library(math_utils SHARED math_utils/math.cpp)
    ```

    `build` 目录下会生成一个名为 `libmath_utils.so` 的动态库文件，最终程序 `test` 运行时，系统需要能找到这个动态库文件。如果找不到，就可能出现 `"error while loading shared libraries: libmath_utils.so: cannot open shared object file: No such file or directory"` 之类的错误。如果我们将生成的 `libmath_utils.so` 重命名为别的名字，错误如下：

    ![](..\images\56b1c2b95784cfbe2183f5085dfcc72b.png)

如果不写 `STATIC` 或 `SHARED`，`CMake` 会根据变量 `BUILD_SHARED_LIBS` 决定生成静态库还是动态库，当你在 `CMakeLists.txt` 中调用 `add_library()` 且‌**没有**‌指定 `STATIC`、`SHARED` 或 `MODULE` 关键字时，CMake 会检查 `BUILD_SHARED_LIBS` 的值：

- ‌如果 `BUILD_SHARED_LIBS` 为 `ON` (或 `TRUE`)，`add_library(mylib src.cpp)` 等价于 `add_library(mylib SHARED src.cpp)`，生成动态库（`Linux` 下为 `.so`，`Windows` 下为 `.dll` + `.lib` 导入库）。
- ‌如果 `BUILD_SHARED_LIBS` 为 `OFF` (或 `FALSE`，默认值)，`add_library(mylib src.cpp)` 等价于 `add_library(mylib STATIC src.cpp)`，生成静态库（`Linux` 下为 `.a`，`Windows` 下为 `.lib` 静态归档库）。

‌**注意**‌：如果你在 `add_library()` 中‌**显式指定**‌了类型（如 `add_library(mylib STATIC ...)`），那么 `BUILD_SHARED_LIBS` 对该目标‌**无效**‌，显式指定的优先级最高。

## CMake进阶使用

### 给Target添加属性

在 `CMake` 中，`target` 可以理解为一个构建目标。所有东西都围绕 `target`。可执行程序（如 `test`）需要什么头文件、需要什么 C/C++ 标准、需要什么宏、需要链接什么库，都写成：

```
target_xxx(test ...)
```

上一章节提到的 `test` 和 `math_utils` 都是 `target`：

```
add_executable(test src/main.cpp)
add_library(math_utils math_utils/math.cpp)
```

#### 添加头文件目录

```
target_include_directories(math_utils PUBLIC math_utils)
```

#### 添加链接库文件

```
target_link_libraries(test PRIVATE math_utils)
```

#### 添加宏定义

```
target_compile_definitions(test PRIVATE DLL_EXPORTS)
```

甚至可以添加带值的宏，可以在代码中输出其值：

```
target_compile_definitions(app PRIVATE VERSION="1.0.0")

#include <iostream>
int main()
{
    std::cout << "Version: " << VERSION << std::endl;
    return 0;
}
```

#### 添加编译器选项

```
target_compile_options(test PRIVATE -Wall -Wextra -Wpedantic)
```

其意思是

```
-Wall      开启常见警告
-Wextra    开启更多额外警告
-Wpedantic 更严格地按照标准检查
```

`CMake` 最终生成的编译命令中，会自动带上这些参数。编译选项不是 `CMake` 自己定义的，而是具体编译器定义的。这些选项是 `GCC/Clang` 风格，在 `MSVC` 下不一定适用。

更严谨的写法是：

```
if(MSVC)
    target_compile_options(app PRIVATE /W4)
else()
    target_compile_options(app PRIVATE -Wall -Wextra -Wpedantic)   
endif()
```

通过条件判断的方式，如果当前使用的是 `MSVC` 编译器，就使用 `/W4`；否则使用 `GCC/Clang` 风格的 `-Wall -Wextra -Wpedantic`。

#### 添加编译器特性

```
target_compile_features(test PRIVATE cxx_std_17)
```

**这是 `CMake` 的一般写法，先创建 `target`，再给 `target`添加属性。**

### 属性传播（PRIVATE、PUBLIC 和 INTERFACE）

在 `CMake` 中，`PRIVATE`、`PUBLIC` 和 `INTERFACE` 是用于控制目标（`Target`）属性传播和作用域的关键字。它们主要应用于 `target_link_libraries`、`target_include_directories`、`target_compile_definitions` 等命令中，决定了依赖关系、头文件路径、编译宏等属性如何从被依赖的目标传递到依赖它的目标。

理解这三个关键字的核心在于明确两个维度：

1. ‌**当前目标（Current Target）**：即你正在配置的那个库或可执行文件。

2. ‌**下游目标（Downstream/Consumer Targets）**：即链接了当前目标的其他库或可执行文件。

| 关键字             | 对当前目标生效？ | 对下游目标生效？ | 语义简述                                                              |
| --------------- | -------- | -------- | ----------------------------------------------------------------- |
| ‌**PRIVATE**‌   | ✅ 是      | ❌ 否      | ‌**内部实现细节**‌。仅当前目标编译时需要，不传递给使用者。提供最强的封装性。                         |
| ‌**PUBLIC**‌    | ✅ 是      | ✅ 是      | ‌**公共接口**‌。当前目标编译时需要，且使用者也需要知道这些信息（如头文件路径）。依赖关系会向下传递。             |
| ‌**INTERFACE**‌ | ❌ 否      | ✅ 是      | ‌**纯接口信息**‌。当前目标编译时不需要，但使用者需要。常用于头文件库（Header-only libraries）或接口库。 |

#### PRIVATE：私有依赖

**含义**‌：

- 该属性仅用于构建当前目标本身。任何链接到当前目标的其他目标都无法继承这些属性。

‌**适用场景**‌：

- 库的内部实现所依赖的头文件路径（例如 `.cpp` 文件中包含，但 `.h` 中未暴露的路径）。
- 仅在当前目标编译时需要的宏定义。
- 当前目标内部使用的静态库或工具库，不希望暴露给上层调用者。

**示例**：

```
target_include_directories(MyLib PRIVATE src/private_inc)
```

`MyLib` 编译时需要 `src/private_inc` 下的头文件， 但使用 `MyLib `的程序不需要知道这个路径。

```
target_link_libraries(MyLib PRIVATE HiddenLib)
```

`MyLib` 内部使用了 `HiddenLib`，但使用者不需要链接 `HiddenLib`。

#### PUBLIC：公共依赖

**含义**‌：

- 该属性既用于构建当前目标，也会传递给所有链接到当前目标的下级目标。

‌**适用场景**‌：

- 库的公共头文件路径（即 `.h` 文件中包含的路径，使用者必须能访问）。
- 使用者也必须链接的依赖库（例如，如果 `MyLib.h` 中包含了 `Boost` 的类型，那么使用 `MyLib` 的程序也必须链接 `Boost`）。
- 使用者编译时也需要知道的宏定义。

**示例**：

```
target_include_directories(MyLib PUBLIC ${CMAKE_SOURCE_DIR}/include)
```

`MyLib` 编译时需要 `include` 目录，同时，任何链接 `MyLib` 的目标也需要包含这个目录以找到 `MyLib` 的头文件。

```
target_link_libraries(MyLib PUBLIC SomeLib)
```

`MyLib` 依赖 `SomeLib`，且 `MyLib` 的头文件中暴露了 `SomeLib` 的接口，因此使用者也必须链接 `SomeLib`。

#### INTERFACE：接口依赖

**含义**‌：

- 该属性不用于构建当前目标，仅传递给链接到当前目标的下级目标。

‌**适用场景**‌：

- **头文件库（Header-only Library）**：没有源文件 `.cpp`，只有头文件。当前目标不需要编译，但使用者需要包含头文件路径。
- **接口库（Interface Library）**：用于聚合一组依赖或编译选项，本身不产生二进制文件。
- 当前目标不需要，但使用者需要的宏定义或链接库。

**示例**：

```
add_library(Catch2 INTERFACE)
target_include_directories(Catch2 INTERFACE ${CMAKE_CURRENT_SOURCE_DIR}/include)
```

创建一个纯头文件库 `Catch2`，`Catch2` 本身不需要编译，所以不用 `PRIVATE` 或 `PUBLIC`，但使用者需要知道头文件在哪里。

```
target_link_libraries(MyLib INTERFACE UtilLib)
```

`MyLib` 不需要链接 `UtilLib`，但使用者需要。

**为了更清晰地理解，我们可以看这几个常用命令在不同关键字下的行为**：

**`target_include_directories` (头文件路径)**

- ‌**PRIVATE**‌: 仅当前目标编译时添加 `-I` 路径。
- ‌**PUBLIC**‌: 当前目标编译时添加 `-I`，且下游目标编译时也自动添加该 `-I`。
- ‌**INTERFACE**‌: 当前目标编译时不添加 `-I`，但下游目标编译时添加。

**`target_link_libraries` (库链接)**

- ‌**PRIVATE**‌: 仅当前目标链接该库。下游目标不会自动链接该库。
- ‌**PUBLIC**‌: 当前目标链接该库，且下游目标也会自动链接该库（传递依赖）。
- ‌**INTERFACE**‌: 当前目标不链接该库，但下游目标会自动链接该库。

**`target_compile_definitions` (编译宏)**

- ‌**PRIVATE**‌: 仅当前目标编译时定义宏（如 `-DDEBUG`）。
- ‌**PUBLIC**‌: 当前目标和下游目标编译时都定义该宏。
- ‌**INTERFACE**‌: 仅下游目标编译时定义该宏。

#### 最佳实践与建议

**最小权限原则**‌：

- 默认优先使用 `PRIVATE`。除非你确定下游目标需要继承该属性，否则不要使用 `PUBLIC`。
- 过度使用 `PUBLIC` 会导致依赖树膨胀，增加编译时间，并可能引发命名冲突或链接错误。

‌**头文件暴露规则**‌：

- 如果你的库的头文件（`.h`）中包含了其他库的头文件（例如 `#include <boost/asio.hpp>`），那么你对 Boost 的依赖必须是 `PUBLIC`。
- 如果其他库的头文件仅在源文件（`.cpp`）中包含，那么依赖应该是 `PRIVATE`。

‌**头文件库使用 INTERFACE**‌：

- 对于没有源码的纯头文件库，必须使用 `INTERFACE` 关键字来设置包含目录和编译选项，因为不存在“当前目标编译”这一过程。

‌**调试技巧**‌：

- 如果遇到“找不到头文件”或“未定义引用”的问题，检查依赖链中的关键字是否正确。
- 可以使用 `cmake --build . --verbose` 查看实际的编译命令行，确认 `-I` 路径和链接库是否符合预期。

通过合理使用 `PRIVATE`、`PUBLIC` 和 `INTERFACE`，你可以构建出模块清晰、依赖关系明确且易于维护的 `CMake` 项目。

### 接入三方库(find_package)

`find_package` 是 `CMake` 中用于查找和加载外部依赖库（Package）的核心命令。它的主要作用是定位已安装的第三方库，并导入其构建所需的信息（如头文件路径、库文件路径、编译选项等），从而简化项目配置。

```
find_package(<PackageName> [version] [REQUIRED] [COMPONENTS <components>...])
```

- ‌`<PackageName>`‌：必填项，指定要查找的包名称。
- `‌[version]‌`：可选，指定所需的最低版本或精确版本。
- `‌REQUIRED‌`：可选。如果未找到该包，`CMake` 将停止配置并报错。如果不加此参数且未找到包，变量 `<PackageName>_FOUND` 将被设为 `FALSE`。
- `‌COMPONENTS‌`：可选。指定需要加载的特定组件（例如 `Boost` 库中的 `system` 和 `filesystem`）。

**两种搜索模式**

`CMake` 通过两种主要模式来查找包，默认情况下会先尝试“配置模式”，失败后再尝试“模块模式”。

1. 配置模式 (Config Mode) - ‌推荐

    这是现代 `CMake` 库（如 `Qt`, `OpenCV`, `fmt`, `Eigen` 等）首选的方式。

    - 机制‌：`CMake` 搜索由库本身提供的配置文件，通常命名为 `<PackageName>Config.cmake` 或 `<lowercase-name>-config.cmake`。
    - ‌优势‌：
      - 由库的开发者维护，信息更准确。
      - 通常提供 ‌Imported Targets‌（导入目标），如 `fmt::fmt` 或 `OpenCV::core`。使用这些目标链接时，`CMake` 会自动处理头文件包含目录、链接库以及传递性依赖，无需手动设置 `include_directories`。
    - ‌强制使用‌：可以通过添加 `CONFIG` 或 `NO_MODULE` 参数强制仅使用此模式。

    ```
    cmake_minimum_required(VERSION 3.10)
    project(MyProject)

    # 查找 fmt 库，如果找不到则报错
    find_package(fmt CONFIG REQUIRED)

    add_executable(app main.cpp)

    # 直接链接导入的目标，自动处理头文件和依赖
    target_link_libraries(app PRIVATE fmt::fmt)
    ```

2. 模块模式 (Module Mode)

    主要用于较旧的库或没有提供 `Config` 文件的库（如部分系统库）。

    - 机制‌：`CMake` 搜索名为 `Find<PackageName>.cmake` 的脚本文件。
    - 搜索路径‌：
      - `CMAKE_MODULE_PATH` 变量指定的路径（用户可自定义）。
      - `CMake` 安装目录下的内置模块路径。
    - 特点‌：
      - `Find*.cmake` 文件通常由 `CMake` 官方、操作系统或用户编写，而非库本身提供。
      - 找到后通常会定义一系列变量，如 `<PackageName>_INCLUDE_DIRS` 和 `<PackageName>_LIBRARIES`。
      - 需要手动使用 `target_include_directories` 和 `target_link_libraries` 链接这些变量。
    - 强制使用‌：可以通过添加 `MODULE` 参数强制仅使用此模式。

    ```
    cmake_minimum_required(VERSION 3.5)
    project(TestCURL)

    # 查找 CURL 库
    find_package(CURL REQUIRED)

    add_executable(app main.cpp)

    # 手动指定头文件路径
    target_include_directories(app PRIVATE ${CURL_INCLUDE_DIRS})

    # 手动链接库文件
    target_link_libraries(app PRIVATE ${CURL_LIBRARIES})
    ```

**总结**

- ‌优先使用 `Config` 模式‌：现代库通常提供 `*Config.cmake` 和 `Imported Targets`，使用 `target_link_libraries` 链接 `Target` 是最健壮的方式。
- ‌善用 `REQUIRED`‌：对于核心依赖，务必加上 `REQUIRED`，以便在环境缺失时尽早发现错误。
- ‌检查 `_FOUND` 变量‌：对于可选依赖，检查 `<PackageName>_FOUND` 变量来决定是否启用相关功能。

## CMake高级使用

### 测试框架‌（CTest）

`CMake` 提供了一套完整的测试框架，主要由 `‌CTest`‌ 驱动。在 `CMake` 项目中添加和运行测试通常涉及三个核心步骤：启用测试功能、定义测试用例、执行测试。

#### 基本配置流程

要在 `CMake` 项目中集成测试，需要在 `CMakeLists.txt` 文件中完成以下配置：

1. 启用测试支持

    在根目录或子目录的 `CMakeLists.txt` 中调用 `enable_testing()`。这通常放在 `project()` 命令之后。

    ```
    cmake_minimum_required(VERSION 3.10)
    project(MyProject)

    # 启用 CTest 支持
    enable_testing()
    ```

2. 创建测试可执行文件

    测试通常是一个独立的可执行程序。你需要使用 `add_executable()` 创建它，并链接必要的库。

    ```
    # 假设有一个待测试的库 my_lib
    add_library(my_lib src/my_lib.cpp)

    # 创建测试可执行文件
    add_executable(unit_tests tests/test_main.cpp)
    target_link_libraries(unit_tests PRIVATE my_lib)
    ```

3. 注册测试用例

    使用 `add_test()` 命令将可执行文件注册为测试用例。

    ```
    # 基本语法
    add_test(
        NAME <TestName>          # 测试名称（唯一标识）
        COMMAND <command>        # 要执行的命令（通常是测试可执行文件）
        [WORKING_DIRECTORY <dir>] # 可选：指定工作目录
        [CONFIGURATIONS <cfg>...] # 可选：仅在特定配置下运行（如 Debug, Release）
    )

    # 示例：注册一个简单的测试
    add_test(NAME MyUnitTest COMMAND unit_tests)
    ```

    **最佳实践‌**：推荐使用生成器表达式 `$<TARGET_FILE:target_name>` 来引用可执行文件路径，这样可以避免硬编码路径，特别是在多配置生成器（如 `Visual Studio` 或 `Xcode`）中非常有用。

    ```
    add_test(NAME MyUnitTest COMMAND $<TARGET_FILE:unit_tests>)
    ```

#### 高级测试配置

1. 设置测试属性

    可以使用 `set_tests_properties()` 对测试进行更精细的控制，例如设置超时时间、环境变量或预期失败。

    ```
    # 设置超时时间为 30 秒
    set_tests_properties(MyUnitTest PROPERTIES TIMEOUT 30)

    # 设置环境变量
    set_tests_properties(MyUnitTest PROPERTIES ENVIRONMENT "FOO=bar;BAZ=qux")

    # 标记为预期失败（如果测试通过反而报错，用于开发中的已知bug）
    set_tests_properties(FlakyTest PROPERTIES WILL_FAIL TRUE)
    ```

2. 按标签分组

    可以使用 `LABELS` 属性给测试打标签，以便后续选择性运行。

    ```
    add_test(NAME SlowTest COMMAND slow_runner)
    set_tests_properties(SlowTest PROPERTIES LABELS "slow;integration")

    add_test(NAME FastTest COMMAND fast_runner)
    set_tests_properties(FastTest PROPERTIES LABELS "fast;unit")
    ```

#### 运行测试

配置并构建项目后，可以在构建目录中使用 `ctest` 命令行工具来运行测试。

| 命令 | 说明 |
| --- | --- |
| `ctest` | 运行所有注册的测试。 |
| `ctest -V` | `verbose` 模式，显示每个测试的详细输出。 |
| `ctest -VV` | 更详细的 `verbose` 模式。 |
| `ctest --output-on-failure` | ‌推荐‌。仅在测试失败时输出日志，保持成功测试的输出简洁。 |
| `ctest -R <regex>` | 仅运行名称匹配正则表达式的测试。例如：`ctest -R "Unit"`。 |
| `ctest -E <regex>` | 排除名称匹配正则表达式的测试。 |
| `ctest -L <label>` | 仅运行具有指定标签的测试。例如：`ctest -L "fast"`。 |
| `ctest -j <N>` | 并行运行测试，使用 N 个线程/作业。例如：`ctest -j 4`。 |
| `ctest -C <Config>` | 指定构建配置（如 `Debug` 或 `Release`）。适用于多配置生成器。 |

**常用组合命令**：

```
# 构建项目
cmake --build .

# 运行测试，失败时显示输出，并使用4个并行任务
ctest --output-on-failure -j 4
```

#### 完整示例

项目结构如下：

```
MyProject/
├── CMakeLists.txt
├── src/
│   ├── math.cpp
│   └── math.h
└── tests/
    └── test_math.cpp
```

`CMakeLists.txt` 内容如下：

```
cmake_minimum_required(VERSION 3.16)
project(MathLib)

# 1. 启用测试
enable_testing()

# 2. 定义库
add_library(math_lib src/math.cpp)
target_include_directories(math_lib PUBLIC ${CMAKE_CURRENT_SOURCE_DIR}/src)

# 3. 定义测试可执行文件
add_executable(test_math tests/test_math.cpp)
target_link_libraries(test_math PRIVATE math_lib)

# 4. 注册测试
add_test(
    NAME MathAdditionTest 
    COMMAND $<TARGET_FILE:test_math>
    WORKING_DIRECTORY ${CMAKE_CURRENT_BINARY_DIR}
)

# 5. 设置属性（可选）
set_tests_properties(MathAdditionTest PROPERTIES TIMEOUT 10)
```

`tests/test_math.cpp` 内容如下：

```
#include "math.h"
#include <iostream>

int main() {
    if (add(2, 3) != 5)
    {
        std::cerr << "Test Failed: add(2, 3) should be 5" << std::endl;
        return 1; // 非零退出码表示测试失败
    }
    std::cout << "Test Passed" << std::endl;
    return 0; // 零退出码表示测试通过
}
```

#### 常见问题与技巧

- 测试失败排查‌：如果测试失败，首先使用 `ctest --output-on-failure` 查看标准输出和错误流。如果还不够，使用 `ctest -V` 查看 `CTest` 的内部执行细节。
- ‌工作目录问题‌：如果测试依赖相对路径的数据文件，务必使用 `WORKING_DIRECTORY` 指定正确的目录，或者在代码中使用绝对路径。
- CI/CD 集成‌：在持续集成环境中，建议始终使用 `--output-on-failure` 和 `-j` 参数，以节省时间并快速定位错误。
- ‌Dashboard 支持‌：`CTest` 还可以将测试结果提交到 `CDash` 仪表盘，用于长期跟踪项目质量，但这需要额外的配置（如 `include(CTest)` 和配置提交脚本）。

### 部署安装‌（CMake install）

`cmake install` 是 `CMake` 中用于定义项目构建后如何将文件（如可执行文件、库、头文件、配置文件等）部署到指定目录的核心命令。它生成的规则会在执行 `make install`、`ninja install` 或 `cmake --install <dir>` 时被触发。

#### 核心概念与变量

- `CMAKE_INSTALL_PREFIX`‌：安装根目录。
    - `Linux/macOS` 默认通常为 `/usr/local`。
    - `Windows` 默认通常为 `C:/Program Files/${PROJECT_NAME}`。
    - 可以通过命令行覆盖：`cmake --install . --prefix /path/to/install`。
- `‌DESTINATION`‌：指定相对于 `CMAKE_INSTALL_PREFIX` 的子路径。推荐使用相对路径，以便支持重定位安装。

#### 主要用法场景

`install()` 命令有多种签名，最常用的是安装目标（`Targets`）、文件（`Files`）和目录（`Directories`）。

1. 安装构建目标 (`TARGETS`)

    这是最常用的方式，用于安装通过 `add_executable()` 或 `add_library()` 创建的目标。`CMake` 会根据目标类型自动区分静态库、动态库和可执行文件。

    ```
    # 基本语法
    install(TARGETS <target_name>...
            [EXPORT <export-name>]
            [RUNTIME DESTINATION <dir>]   # 可执行文件 (.exe, .dll on Windows)
            [LIBRARY DESTINATION <dir>]   # 共享库 (.so, .dylib, .dll on Linux/Mac)
            [ARCHIVE DESTINATION <dir>]   # 静态库 (.a, .lib)
            [PUBLIC_HEADER DESTINATION <dir>] # 公共头文件
            [INCLUDES DESTINATION <dir>]  # 指定包含目录，用于生成导出文件
    )

    # 示例
    add_library(my_lib SHARED src/lib.cpp)
    add_executable(my_app src/main.cpp)
    target_link_libraries(my_app PRIVATE my_lib)

    # 安装规则
    install(TARGETS my_lib my_app
        EXPORT MyProjectTargets       # 导出目标信息，供其他项目 find_package 使用
        LIBRARY DESTINATION lib       # 安装动态库到 <prefix>/lib
        ARCHIVE DESTINATION lib       # 安装静态库到 <prefix>/lib
        RUNTIME DESTINATION bin       # 安装可执行文件到 <prefix>/bin
        PUBLIC_HEADER DESTINATION include/my_lib # 安装头文件
    )
    ```

    **注意‌**：在现代 `CMake (3.0+)` 中，推荐同时使用 `install(EXPORT ...)` 来生成配置文件，以便其他项目可以通过 `find_package() `找到你的库。

2. 安装普通文件 (`FILES`)

    用于安装非构建生成的文件，如配置文件、文档、脚本等。

    ```
    # 基本语法
    install(FILES <file>... DESTINATION <dir>
        [PERMISSIONS <permissions...>]
        [CONFIGURATIONS <config...>]
    )

    # 示例
    # 安装配置文件到 etc 目录
    install(FILES cmake-examples.conf DESTINATION etc)

    # 安装多个头文件
    install(FILES include/foo.h include/bar.h DESTINATION include)
    ```

3. 安装目录 (`DIRECTORY`)

    用于递归安装整个目录及其内容。可以配合 `PATTERN` 或 `REGEX` 进行过滤。

    ```
    # 基本语法
    install(DIRECTORY <dir>... DESTINATION <dir>
        [FILE_PERMISSIONS <permissions...>]
        [DIRECTORY_PERMISSIONS <permissions...>]
        [USE_SOURCE_PERMISSIONS]
        [PATTERN <pattern> [EXCLUDE] [PERMISSIONS <permissions...>]]
    )

    # 示例
    # 安装 include 目录下的所有内容到 <prefix>/include
    # 注意：如果源路径以 / 结尾，则安装目录内的内容；否则安装目录本身
    install(DIRECTORY ${PROJECT_SOURCE_DIR}/include/ DESTINATION include)

    # 仅安装 .h 文件，排除 .tmp 文件
    install(DIRECTORY ${PROJECT_SOURCE_DIR}/data/ DESTINATION share/data
            PATTERN "*.tmp" EXCLUDE
            PATTERN "*.h" PERMISSIONS OWNER_READ GROUP_READ WORLD_READ)
    ```

4. 安装脚本 (`SCRIPT/CODE`)

    在安装过程中执行自定义 `CMake` 脚本或代码片段。

    ```
    # 执行一个外部 CMake 脚本文件
    install(SCRIPT "${CMAKE_CURRENT_SOURCE_DIR}/post_install.cmake")

    # 执行一段 CMake 代码
    install(CODE "message(STATUS \"Installation completed successfully!\")")
    ```

#### 常用参数详解

| 参数 | 说明 |
| --- | --- |
| `DESTINATION` | ‌必填‌。安装路径（相对于 `CMAKE_INSTALL_PREFIX`）。 |
| `PERMISSIONS` | 设置文件权限，如 `OWNER_READ`, `OWNER_WRITE`, `EXECUTE` 等。 |
| `CONFIGURATIONS` | 指定仅在特定构建配置下安装，如 `Debug`, `Release`。 |
| `COMPONENT` | 将安装文件分组为组件。用户可以使用 `cmake --install . --component <name>` 只安装特定组件。 |
| `OPTIONAL` | 如果文件不存在，不报错并继续安装。 |
| `EXCLUDE_FROM_ALL` | 该文件不会在默认的全局安装中安装，除非显式指定组件。 |

#### 现代最佳实践

**导出与查找**

为了让其他项目能够方便地使用你安装的库，应结合 `install(EXPORT)` 和 `export()`。

```
# 1. 定义库
add_library(MyLib src/mylib.cpp)
target_include_directories(MyLib PUBLIC 
    $<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/include>
    $<INSTALL_INTERFACE:include>
)

# 2. 安装目标和头文件
install(TARGETS MyLib
    EXPORT MyLibConfig          # 导出名为 MyLibConfig 的目标集
    LIBRARY DESTINATION lib
    ARCHIVE DESTINATION lib
    RUNTIME DESTINATION bin
    INCLUDES DESTINATION include
)

# 3. 安装头文件
install(DIRECTORY include/ DESTINATION include)

# 4. 生成并安装配置文件 (MyLibConfig.cmake)
install(EXPORT MyLibConfig
    FILE MyLibConfig.cmake
    NAMESPACE MyLib::
    DESTINATION lib/cmake/MyLib
)
```

这样，其他项目就可以通过以下方式找到并使用你的库：

```
find_package(MyLib CONFIG REQUIRED)
target_link_libraries(app PRIVATE MyLib::MyLib)
```

#### 执行安装

配置并构建项目后，使用以下命令执行安装：

```
# 方法 1: 使用 cmake --install (推荐，跨平台统一)
cmake --install <build_dir> --prefix <install_prefix>

# 方法 2: 使用构建工具原生命令
make install
# 或
ninja install
```

**常用选项**：‌

- `--prefix <path>`: 覆盖默认的 `CMAKE_INSTALL_PREFIX`。
- `--config <cfg>`: 指定构建配置（如 `Debug` 或 `Release`），适用于多配置生成器（如 `Visual Studio`）。
- `--component <comp>`: 仅安装特定组件。

### 配置预设‌（CMake Presets）

`CMake Presets`（预设）是 `CMake 3.19` 引入的一项功能，旨在解决配置选项共享和标准化的问题。它允许开发者通过 `JSON` 文件定义常见的配置、构建和测试选项，从而简化命令行操作、统一 CI/CD 流程，并改善 IDE（如 `Visual Studio`、`VS Code`、`CLion`、`Qt Creator`）的集成体验。

#### 核心文件

`CMake Presets` 主要依赖两个位于项目根目录的 `JSON` 文件：

1. `CMakePresets.json`‌：
    - 用途‌：保存项目级别的通用构建设置。
    - ‌版本控制‌：‌应当‌提交到版本控制系统（如 `Git`），以便团队成员和 CI 服务器共享相同的配置。

2. `‌CMakeUserPresets.json`‌：
    - 用途‌：保存开发者个人的本地设置（如特定的编译器路径、个人调试偏好）。
    - ‌版本控制‌：‌不应当‌提交到版本控制系统，通常应加入 `.gitignore`。
    - ‌优先级‌：用户预设可以继承或覆盖项目预设中的值。

**‌注意‌**：这两个文件格式完全相同。如果使用了 `--preset` 参数，至少需要存在其中一个文件。

#### 基本结构

`Presets` 文件是一个 `JSON` 文档，主要包含以下部分：

- `version`：预设架构的版本号（当前最高支持到版本 `10`，对应 `CMake 3.31+`）。
- `cmakeMinimumRequired`：指定所需的最低 `CMake` 版本。
- `include`：可选，用于包含其他预设文件。
- `configurePresets`：定义配置阶段的选项（相当于 `cmake -S . -B <build_dir> ...` 的参数）。
- `buildPresets`：定义构建阶段的选项（相当于 `cmake --build <build_dir> ...` 的参数）。
- `testPresets`：定义测试阶段的选项（相当于 `ctest ...` 的参数）。
- `packagePresets`：定义打包阶段的选项（`CMake 3.24+`）。
- `workflowPresets`：将配置、构建、测试等步骤组合成一个工作流（`CMake 3.25+`）。

**常用字段详解 (以 `configurePresets` 为例)**

```
{
  "version": 6,
  "cmakeMinimumRequired": {
    "major": 3,
    "minor": 23,
    "patch": 0
  },
  "configurePresets": [
    {
      "name": "ninja-debug",  # 预设的唯一标识符，用于命令行引用
      "displayName": "Ninja Debug",  # 在 IDE 中显示的友好名称
      "description": "Build with Ninja generator in Debug mode",
      "generator": "Ninja",  # 指定生成器（如 "Ninja", "Unix Makefiles", "Visual Studio 17 2022"）
      "binaryDir": "${sourceDir}/build/ninja-debug",  # 构建目录路径。支持变量如 ${sourceDir} (源码根目录), ${presetName}, ${hostSystemName} 等。
      "cacheVariables": {  # 设置 CMake 缓存变量（即 -DVAR=VALUE）
        "CMAKE_BUILD_TYPE": "Debug",
        "MY_CUSTOM_OPTION": "ON"
      },
      "environment": {  # 设置环境变量。支持 $env{VAR} (引用当前预设或系统变量) 和 $penv{VAR} (仅引用系统环境变量)。
        "PATH": "$env{HOME}/my-tools/bin:$penv{PATH}",
        "CC": "/usr/bin/clang"
      },
      "toolchainFile": "toolchains/linux-clang.cmake",
      "inherits": "base-config"  # 继承另一个预设的配置，实现复用和覆盖
    }
  ]
}
```

#### 使用方法

1. 命令行使用

    - 配置项目‌

        ```
        cmake --preset=ninja-debug
        # 或者简写
        cmake --preset ninja-debug
        ```

    - 构建项目

        ```
        cmake --build --preset=ninja-debug
        ```

    - 运行测试

        ```
        ctest --preset=ninja-debug
        ```

2. IDE集成

    现代 C++ IDE 均原生支持 `CMake Presets`：

    - `‌Visual Studio` / `VS Code (CMake Tools)‌`：打开项目后，IDE 会自动检测 `CMakePresets.json`，并在状态栏或命令面板中提供下拉菜单选择预设。选择后，配置、构建和调试将自动应用预设中的设置。
    - `‌CLion‌`：自动导入预设作为 `CMake Profiles`。可以在设置中管理预设的加载行为。
    - `‌Qt Creator`‌：支持读取预设，并在构建设置中显示。

#### 最佳实践

1. ‌标准化 CI/CD‌：在 `‌CMakePresets.json`‌ 中定义用于 CI 的预设（如 `‌ci-linux-gcc`‌, `‌ci-windows-msvc`‌），确保本地开发与云端构建环境一致。
2. ‌利用继承‌：创建一个 `‌base`‌ 预设包含通用设置（如警告标志、标准版本），其他预设通过 `‌inherits`‌ 继承并修改特定部分（如构建类型、生成器）。
3. ‌区分用户与项目设置‌：将团队共享的工具链、编译器标志放入 `‌CMakePresets.json`‌；将个人本地的路径、临时实验性选项放入 `‌CMakeUserPresets.json`‌。
4. ‌使用变量‌：充分利用 `‌${sourceDir}`‌, `‌${presetName}`‌, `‌$env{...}`‌ 等变量，使预设具有可移植性，避免硬编码绝对路径。


**示例：完整的工作流预设**

```
{
  "version": 6,
  "configurePresets": [
    {
      "name": "default",
      "generator": "Ninja",
      "binaryDir": "${sourceDir}/build/${presetName}",
      "cacheVariables": {
        "CMAKE_CXX_STANDARD": "17"
      }
    },
    {
      "name": "debug",
      "inherits": "default",
      "cacheVariables": {
        "CMAKE_BUILD_TYPE": "Debug"
      }
    },
    {
      "name": "release",
      "inherits": "default",
      "cacheVariables": {
        "CMAKE_BUILD_TYPE": "Release"
      }
    }
  ],
  "buildPresets": [
    {
      "name": "debug",
      "configurePreset": "debug"
    },
    {
      "name": "release",
      "configurePreset": "release"
    }
  ],
  "testPresets": [
    {
      "name": "debug",
      "configurePreset": "debug",
      "output": {
        "outputOnFailure": true
      }
    }
  ],
  "workflowPresets": [
    {
      "name": "debug-all",
      "steps": [
        {
          "type": "configure",
          "name": "debug"
        },
        {
          "type": "build",
          "name": "debug"
        },
        {
          "type": "test",
          "name": "debug"
        }
      ]
    }
  ]
}
```

通过运行 `cmake --workflow --preset=debug-all`，即可一键完成配置、构建和测试。


### 交叉编译工具链（CMake Toolchains）

`CMake Toolchains`（工具链）‌ 是 `CMake` 用于编译、链接库、创建归档文件以及执行其他构建任务的一组实用程序集合。工具链的具体内容取决于项目中启用的编程语言（如 `C`、`C++`）。

在常规的主机构建中，`CMake` 会通过系统自省自动确定默认的工具链。但在‌交叉编译‌或需要特定编译器环境的场景下，开发者通常需要通过‌工具链文件（Toolchain File）‌来显式指定编译器路径、目标架构和其他相关设置。通过合理使用工具链文件，开发者可以轻松地在不同平台和编译器之间切换，实现高效的多平台开发和部署。

#### 核心概念

1. 语言启用‌：

    工具链与语言紧密相关。通过 `project()` 命令启用语言（默认为 `C` 和 `CXX`）。当启用某种语言时，`CMake` 会查找对应的编译器，并确定供应商、版本、目标架构等信息。

2. ‌关键变量‌：
    - `CMAKE_<LANG>_COMPILER`：指定特定语言的编译器（如 `CMAKE_C_COMPILER`, `CMAKE_CXX_COMPILER`）。
    - `CMAKE_SYSTEM_NAME`：指定目标系统名称（如 `Linux`, `Windows`, `Android`）。在交叉编译时，必须设置此变量以告诉 `CMake` 正在进行跨平台构建。
    - `CMAKE_<LANG>_COMPILER_EXTERNAL_TOOLCHAIN`：如果编译器驱动支持，可指定外部工具链的路径，用于查找归档器、链接器等辅助工具。

#### 使用工具链文件

工具链文件是一个标准的 `CMake` 脚本文件（通常以 `.cmake` 结尾），其中包含针对特定目标平台的配置指令。

1. 创建工具链文件

    创建一个名为 `toolchain.cmake` 的文件，内容示例如下（以交叉编译为例）：

    ```
    # 指定目标系统
    set(CMAKE_SYSTEM_NAME Linux)
    # 指定目标处理器架构
    set(CMAKE_SYSTEM_PROCESSOR arm)

    # 指定交叉编译器，不要用当前电脑默认的 /usr/bin/gcc 和 /usr/bin/g++，而是用 ARM 交叉编译器，因为应用于 arm 平台
    set(CMAKE_C_COMPILER /usr/bin/arm-linux-gnueabihf-gcc)
    set(CMAKE_CXX_COMPILER /usr/bin/arm-linux-gnueabihf-g++)

    # 指定目标环境的根路径
    set(CMAKE_FIND_ROOT_PATH /usr/arm-linux-gnueabihf)

    # 关键设置：
    # 查找程序（如编译器、工具）时，只在主机系统中找，不要到目标根路径下找
    set(CMAKE_FIND_ROOT_PATH_MODE_PROGRAM NEVER)

    # 查找库文件、头文件、CMake包配置文件时，只在目标根路径下找，不要污染主机环境
    set(CMAKE_FIND_ROOT_PATH_MODE_LIBRARY ONLY)
    set(CMAKE_FIND_ROOT_PATH_MODE_INCLUDE ONLY)
    set(CMAKE_FIND_ROOT_PATH_MODE_PACKAGE ONLY)
    ```

    **值**：

    ![](..\images\eeaaf75ad8160ada0980739ae4c36606.png)

    **变量**：

    - `CMAKE_FIND_ROOT_PATH`‌：定义了一个或多个目录，作为交叉编译时目标环境的“根”。
    - `CMAKE_SYSROOT‌`：也可以用来指定单个目标系统根目录，效果类似 `CMAKE_FIND_ROOT_PATH`。
    - `CMAKE_FIND_ROOT_PATH_MODE_LIBRARY‌`：控制 `find_library()` 的行为，通常设为 `ONLY`。
    - `CMAKE_FIND_ROOT_PATH_MODE_INCLUDE‌`：控制 `find_path()` 和 `find_file()` 的行为，通常设为 `ONLY`。
    - `CMAKE_FIND_ROOT_PATH_MODE_PACKAGE`：控制 `find_package()` 的行为，通常设为 `ONLY`。

**注意**：在绝大多数交叉编译场景中，应将 `‌CMAKE_FIND_ROOT_PATH_MODE_PROGRAM`‌ 设置为 ‌`‌NEVER`‌‌，以避免 `‌CMake`‌ 错误地链接或执行针对目标架构编译的二进制文件。

2. 在配置时指定工具链文件

    在使用 `CMake` 配置项目时，通过 `-DCMAKE_TOOLCHAIN_FILE` 参数指向该文件：

    ```
    cmake -DCMAKE_TOOLCHAIN_FILE=/path/to/toolchain.cmake -B build_dir -S source_dir
    ```

    或者，如果使用 `‌CMake Presets‌`，可以在 `CMakePresets.json` 中定义：

    ```
    {
        "version": 3,
        "configurePresets": [
            {
            "name": "cross-compile",
            "toolchainFile": "toolchain.cmake",
            "binaryDir": "${sourceDir}/build/cross"
            }
        ]
    }
    ```

#### 应用场景

1. 交叉编译（Cross Compiling）

    - `‌Linux` 嵌入式‌：为 `ARM`、`MIPS` 等架构编译。
    - ‌`Android‌`：使用 `Android NDK` 进行编译。`CMake` 提供了专门的模块来处理 `NDK` 工具链。
    - ‌`iOS/macOS`‌：针对不同 `Apple` 平台架构编译。
    - ‌`Windows CE/Universal/Store‌`：针对特定 `Windows` 子平台编译。
    - ‌`QNX‌`：为 `QNX` 实时操作系统编译。

2. 指定特定编译器

    即使在同一平台上，也可能需要切换编译器（例如从 `GCC` 切换到 `Clang`）。可以通过工具链文件或直接设置环境变量/缓存变量来实现：

    ```
    cmake -DCMAKE_C_COMPILER=clang -DCMAKE_CXX_COMPILER=clang++ ..
    ```

#### 注意事项
1. 弃用的模块‌：早期 `CMake` 版本中使用的 `CMakeForceCompiler` 模块已在 `CMake 3.6` 中弃用。现代 `CMake` 能够自动检测编译器标识，无需强制指定编译器 ID，只需设置编译器路径即可。
2. ‌IDE 支持‌：像 `CLion` 这样的 IDE 允许用户配置多个工具链（包括 `CMake` 可执行文件、构建工具、编译器、调试器等），并在不同的 `CMake` 配置文件之间切换。
3. ‌变量作用域‌：工具链文件中设置的变量通常在 `project()` 命令调用之前生效，因此它们会影响编译器检测和初始配置过程。


## CMake工程化使用

### 标准构建类型（Debug和Release）

#### 构建类型说明

同一份 C++ 代码，可以有很多种编译方式。最常见的就是：`Debug`、`Release`，我们写了一个程序，程序运行后崩溃了。这时候最关心的是：程序崩在哪里？变量是多少？调用栈是什么？为了方便调试，编译器需要：保留变量信息、行号，让调试器容易追踪代码。构建方式就是 `Debug`，但是 `Debug` 程序通常更大、更慢，因为它保留了大量调试信息。真正发布程序时，用户不关心源码行号，编译器会开启优化、删除无用代码、减少调试信息，构建方式就是 `Release`。

`CMake` 支持以下四种标准构建类型，它们对应不同的编译器优化标志：

| 构建类型             | 说明              | 典型编译器标志 (GCC/Clang) | 应用场景        |
| ---------------- | --------------- | ------------------- | ----------- |
| `‌Debug`‌          | 调试模式，无优化，包含调试符号 | `-g -O0`             | 开发、调试阶段     |
| ‌`Release‌`        | 发布模式，最高优化，无调试符号 | `-O3 -DNDEBUG`        | 生产环境部署，追求性能 |
| ‌`RelWithDebInfo`‌ | 发布模式带调试信息，适度优化  | `-O2 -g -DNDEBUG`     | 性能测试、线上问题排查 |
| `‌MinSizeRel`‌     | 最小体积发布模式        | `-Os -DNDEBUG`        | 对二进制大小敏感的场景 |

在 `CMake` 构建系统中，`CMAKE_BUILD_TYPE` 和 `--config` 分别用于‌**配置阶段**‌和‌**构建阶段**‌，且它们的适用场景取决于所使用的‌**生成器**（`Generator`）类型。

核心区别在于：‌**单配置生成器**‌（如 `Unix Makefiles`, `Ninja`）与‌**多配置生成器**‌（如 `Visual Studio`, `Xcode`）对构建类型的处理方式不同。

| 特性      | CMAKE_BUILD_TYPE                    | --config <Type>                            |
| --------- | ----------------------------------- | ------------------------------------------ |
| ‌作用阶段‌  | ‌配置阶段‌ (`cmake ..`)                   | ‌构建阶段‌ (`cmake --build .`)                   |
| ‌适用生成器‌ | ‌单配置生成器‌(`Unix Makefiles`, `Ninja`)     | ‌多配置生成器‌(`Visual Studio`, `Xcode`)             |
| ‌功能描述‌  | 在生成构建文件时固定构建类型。一旦设定，整个构建目录只能构建该类型。  | 在多配置构建环境中，指定本次构建具体要编译哪种配置（`Debug/Release`等）。 |
| ‌典型命令‌  | `cmake -DCMAKE_BUILD_TYPE=Release ..` | `cmake --build . --config Release`          |

#### 单配置生成器

单配置生成器(`Linux/macOS` 常用, 如 `Make`, `Ninja`)

1. 正确做法：

    在运行 `cmake` 配置命令时，通过 `-D` 参数指定 `CMAKE_BUILD_TYPE`。

     ```
     # 1. 配置阶段：指定为 Release
     cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
     # 2. 构建阶段：直接构建，无需 --config
     cmake --build build
     # 或者直接使用 make/ninja
     # make -j4
     # ninja 
     ```

2. 错误做法‌：

    - 如果在配置时未指定 `CMAKE_BUILD_TYPE`（默认为空或 `Debug`），然后在构建时尝试使用 `--config Release`，通常会报错或无效，因为单配置生成器不支持在构建时切换配置。
    - 示例错误：`cmake --build build --config Release` 在 `Makefile` 项目中可能被忽略或导致 `"Unknown build type"` 错误。

**注意：在 `Linux` 或 `macOS` 上使用默认的 `Unix Makefiles` 或 `Ninja` 时，`CMake` 在配置阶段就必须知道你要构建什么类型。**

#### 多配置生成器

多配置生成器(`Windows` 常用, 如 `Visual Studio`, `Xcode`)，在 `Windows` 上使用 `Visual Studio` 生成器，或在 `macOS` 上使用 `Xcode` 生成器时，`CMake` 会生成一个包含多种配置（`Debug`, `Release`, `RelWithDebInfo` 等）的项目文件。

1. 配置阶段：

    通常不需要指定 `CMAKE_BUILD_TYPE`（指定了也可能被忽略，取决于具体版本和生成器）。

    ```
    cmake -S . -B build -G "Visual Studio 16 2019
    ```

2. 构建阶段：

    使用 `--config` 参数选择要构建的具体配置。

    ```
    # 构建 Release 版本
    cmake --build build --config Release
    # 构建 Debug 版本
    cmake --build build --config Debug
    ```

‌**注意‌：对于多配置生成器，`CMAKE_BUILD_TYPE` 变量在配置阶段通常不起主要作用，构建类型的选择权移交给了构建工具（如 `MSBuild` 或 `xcodebuild`）。**

#### 最佳实践建议

1. 跨平台脚本编写：

    如果你需要编写兼容 `Linux` 和 `Windows` 的构建脚本，建议检测当前生成器类型或使用条件逻辑。

      - ‌**Linux/Mac (Make/Ninja)**‌:

        ```
        cmake -B build -DCMAKE_BUILD_TYPE=Release
        cmake --build build
        ```

      - ‌**Windows (VS)**‌:

        ```
        cmake -B build -G "Visual Studio 16 2019"
        cmake --build build --config Release
        ```

2. ‌避免硬编码：

    不要在 `CMakeLists.txt` 中强制设置 `set(CMAKE_BUILD_TYPE Release)`，这会降低灵活性，允许用户通过命令行覆盖才是最佳实践。如果必须设置默认值，建议使用如下模式：

    ```
   if(NOT CMAKE_BUILD_TYPE AND NOT CMAKE_CONFIGURATION_TYPES)
        set(CMAKE_BUILD_TYPE Release CACHE STRING "Choose the type of build." FORCE)
        set_property(CACHE CMAKE_BUILD_TYPE PROPERTY STRINGS "Debug" "Release" "RelWithDebInfo" "MinSizeRel")
    endif()
    ```

3. ‌统一构建命令：

    `cmake --build .` 是一个跨平台的通用构建命令，它会自动调用底层的构建工具（`make`, `ninja`, `msbuild` 等）。推荐始终使用 `cmake --build` 而不是直接调用 `make` 或 `msbuild`，以提高脚本的可移植性。

#### 总结

- 用 ‌**Make/Ninja**‌ 时：请在‌**配置时**‌使用 `-DCMAKE_BUILD_TYPE=Release`。
- 用 ‌**Visual Studio/Xcode**‌ 时：请在‌**构建时**‌使用 `--config Release`。


### 工程化实战

当项目变大后，所有内容放在一个 `CMakeLists.txt` 里会很乱。这时可以使用多目录分层管理，每个子目录可以有自己的 `CMakeLists.txt` 并且构建生成自己的 `target`。 `CMake` 多层 `CMakeLists.txt` 的核心机制是“作用域隔离”与“变量/目标继承”‌。通过在主目录和子目录分别放置 `CMakeLists.txt`，并利用 `add_subdirectory()` 命令建立层级关系，可以实现模块化构建、依赖管理和代码组织。

#### 核心命令（add_subdirectory）

这是连接多层结构的桥梁。它在当前作用域中进入指定的子目录，执行其中的 `CMakeLists.txt`，并将该子目录中定义的目标（`Targets`）暴露给父目录。

```
# 在父目录的 CMakeLists.txt 中
add_subdirectory(<source_dir> [binary_dir] [EXCLUDE_FROM_ALL])
```

1. `<source_dir>‌`：子目录相对于当前文件的路径。
2. ‌`[binary_dir]‌`：可选。指定子目录构建产物存放的位置。如果不指定，默认在构建目录下的同名子文件夹中。
3. ‌`EXCLUDE_FROM_ALL‌`：可选。如果加上此参数，子目录中的目标不会在默认的全局构建（如 `make all`）中被构建，除非显式指定构建该目标。常用于可选模块或测试代码。


#### 典型项目结构示例

假设一个包含库、可执行程序和测试的项目结构：

```
MyProject/
├── CMakeLists.txt          # 根目录配置
├── src/
│   ├── CMakeLists.txt      # 库源码配置
│   ├── math.cpp
│   └── math.h
├── app/
│   ├── CMakeLists.txt      # 应用程序配置
│   └── main.cpp
└── tests/
    ├── CMakeLists.txt      # 测试配置
    └── test_math.cpp
```

可以看到，项目结构中，每个文件夹下面都有一个 `CMakeLists.txt`。

1. 根目录 `CMakeLists.txt`：

    负责全局设置、启用功能并添加子目录

    ```
    cmake_minimum_required(VERSION 3.16)
    project(MyProject LANGUAGES CXX)

    # 全局设置
    set(CMAKE_CXX_STANDARD 17)
    set(CMAKE_CXX_STANDARD_REQUIRED ON)

    # 启用测试支持
    enable_testing()

    # 添加子目录
    # 顺序很重要：先定义库，后定义依赖库的应用
    add_subdirectory(src)
    add_subdirectory(app)
    add_subdirectory(tests)
    ```

2. 库目录 `src/CMakeLists.txt`：

    定义静态或动态库，并设置其公共接口

    ```
    # 创建库目标
    add_library(math_lib STATIC math.cpp)

    # 设置公共头文件路径
    # BUILD_INTERFACE: 构建时使用的路径
    # INSTALL_INTERFACE: 安装后其他项目使用时的路径
    target_include_directories(math_lib PUBLIC
        $<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}>
        $<INSTALL_INTERFACE:include>
    )
    ```

3. 应用目录 `app/CMakeLists.txt`：

    定义可执行文件并链接库

    ```
    add_executable(my_app main.cpp)

    # 链接之前定义的库目标
    # 因为 math_lib 在父作用域或通过 add_subdirectory 可见，这里可以直接引用
    target_link_libraries(my_app PRIVATE math_lib)
    ```

4. 测试目录 `tests/CMakeLists.txt`

    定义测试可执行文件并注册测试

    ```
    add_executable(test_math test_math.cpp)
    target_link_libraries(test_math PRIVATE math_lib)

    # 注册测试
    add_test(NAME MathTest COMMAND test_math)
    ```

#### 作用域与变量传递

理解变量和作用域是处理多层结构的关键：

| 特性 | 说明 |
| --- | --- |
| ‌变量作用域‌ | `CMake` 变量具有‌函数/目录作用域‌。子目录可以读取父目录定义的变量，但子目录中修改变量‌不会‌影响父目录（除非使用 `PARENT_SCOPE`）。 |
| ‌目标全局性‌ | 通过 `add_library` 或 `add_executable` 创建的目标（`Target`）是‌全局可见‌的。一旦在子目录中定义，父目录或其他兄弟子目录都可以直接通过名称引用它（前提是 `add_subdirectory` 已执行）。 |
| ‌`PARENT_SCOPE`‌ | 如果子目录需要向父目录传递信息（如版本号、发现的路径），需使用 `set(VAR VALUE PARENT_SCOPE)`。 |
| `‌CACHE` 变量‌ | 缓存变量（`set(VAR VALUE CACHE STRING ""`)）是全局共享的，任何层级都可以读写。常用于用户配置选项。 |

#### 最佳实践

1. 优先使用 `Target` 而非变量‌：

    - ❌ ‌旧式做法‌：在子目录中设置 `MY_LIB_INCLUDES` 和 `MY_LIB_LIBRARIES` 变量，父目录手动 `include_directories` 和 `link_libraries`。
    - ✅ ‌现代做法‌：使用 `target_link_libraries` 链接目标。`CMake` 会自动处理传递性依赖（Include 路径、编译定义等）。

2. ‌合理使用 `PUBLIC`/`PRIVATE`/`INTERFACE`‌：

    在 `target_include_directories` 和 `target_link_libraries` 中明确指定关键字：

    - `PRIVATE`‌：仅当前目标使用，不传递给依赖它的目标。
    - `‌PUBLIC`‌：当前目标使用，且传递给依赖它的目标。
    - ‌`INTERFACE‌`：当前目标不使用（如头文件库），但传递给依赖它的目标。

3. ‌避免硬编码路径‌：

    使用 `${CMAKE_CURRENT_SOURCE_DIR}` 和 `${CMAKE_CURRENT_BINARY_DIR}` 而不是相对路径或绝对路径，确保项目可重定位。

4. ‌控制构建顺序‌：

    `add_subdirectory` 的顺序决定了目标的定义顺序。如果 `app` 依赖 `lib`，则必须先 `add_subdirectory(lib)` 再 `add_subdirectory(app)`，或者确保在 `app` 的 `CMakeLists.txt` 执行时 `lib` 目标已存在。

5. 可选子目录‌：

    对于可选模块，可以使用 `option()` 结合 `if()` 来控制是否添加子目录：

    ```
    option(BUILD_TESTS "Build unit tests" ON)
    if(BUILD_TESTS)
        add_subdirectory(tests)
    endif()
    ```

#### 常见问题排查

1. 错误：Target not found‌

    - 原因：尝试链接的目标尚未定义。
    - 解决：检查 `add_subdirectory` 的顺序，确保被依赖的子目录先被添加。

2. 错误：Include file not found‌

    - 原因：头文件路径未正确传播。
    - 解决：检查库目标是否使用了 `target_include_directories(... PUBLIC ...)`，并且应用是否正确链接了该库目标。

3. ‌变量未生效‌：

    - 原因：在子目录中 `set` 的变量试图影响父目录。
    - 解决：如果需要向上层传递，使用 `set(VAR VALUE PARENT_SCOPE)`；如果是全局配置，考虑使用 `CACHE` 变量或在根目录定义。



**通过合理划分目录结构和利用现代 `CMake` 的目标系统，多层 `CMakeLists.txt` 能够极大地提升大型项目的可维护性和构建效率。**
