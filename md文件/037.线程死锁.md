# 线程死锁

## 锁的粒度

在讨论死锁之前，先了解锁的粒度（Lock Granularity）。锁的粒度是并发控制中衡量锁作用范围的核心概念，指锁保护的数据单元大小，其选择直接影响系统的并发度、性能开销以及死锁风险。

### 定义与分类

- 粗粒度锁：锁定范围大，并发度低但管理开销小。例如用一把全局锁保护整个容器，任何线程持锁期间，其他所有竞争者都被阻塞。
- 细粒度锁：锁定范围小，并发度高但管理复杂。例如容器的每个分桶（或每个元素）各持有一把锁，线程只锁住自己要操作的那一小部分数据。
- 中间粒度锁：介于两者之间，例如按分片（shard）划分若干把锁，在并发度与管理成本之间折中。

### 性能影响

- 并发度：粒度越小，并发访问能力越强（细粒度锁允许多线程同时操作不同数据）。
- 开销：细粒度锁需要创建和管理更多的锁对象，内存与维护开销更大，粗粒度锁则反之。
- 竞争概率：粗粒度锁易引发线程竞争，细粒度锁通过分散锁降低竞争。

### 与死锁的关系

- 粒度越细，系统中锁的数量越多，多把锁被交叉持有的机会越大，死锁风险也随之上升；粗粒度锁数量少、竞争集中，反而不易死锁。
- 因此实践中需要在并发度与死锁风险之间权衡，并配合统一的加锁顺序、一次性加锁等手段来规避死锁。

## 死锁

在并发编程中，死锁（Deadlock）是指两个或两个以上的执行单元（进程、线程）在执行过程中，因为竞争资源而陷入了互相等待的状态，导致没有一个执行单元能够继续执行。死锁通常发生在多执行单元环境中，当多个执行单元同时锁定资源而又试图获取其他执行单元已锁定的资源时，就可能发生死锁。

### 死锁的产生条件

产生死锁的四个必要条件：
- 互斥条件：指执行单元对所分配到的资源进行排它性使用，即在一段时间内某资源只由一个执行单元占用。如果此时还有其它执行单元请求资源，则请求者只能等待，直至占有资源的执行单元用毕释放。
- 请求和保持条件：指执行单元已经保持至少一个资源，但又提出了新的资源请求，而该资源已被其它执行单元占有，此时请求执行单元阻塞，但又对自己已获得的资源保持不放。
- 非剥夺条件：指执行单元已获得的资源，在未使用完之前，不能被剥夺，只能在使用完时由自己释放。
- 循环等待条件：指在发生死锁时，必然存在一个执行单元——资源的环形链，即执行单元集合 {P0，P1，P2，···，Pn} 中的 P0 正在等待一个 P1 占用的资源；P1 正在等待 P2 占用的资源，……，Pn 正在等待已被 P0 占用的资源。

### 死锁的产生场景

#### 线程对同一个锁反复加锁

如果同一线程对同一个锁加锁两次，那么这会导致死锁，这种情况在使用自释放锁时经常出现，比如 C++11 的 `std::lock_guard<std::mutex>`，如果在 `std::lock_guard` 还没释放时再次对同一个锁使用 `std::lock_guard<std::mutex>`，程序就会永久阻塞在该处。严格来说，同一线程对同一个 `std::mutex` 重复加锁属于未定义行为，死锁卡死只是其最常见的表现，并不会抛出异常或使程序崩溃。

代码示例如下：

```cpp
std::mutex mutex;
void ThreadFunc()
{
    std::lock_guard<std::mutex> lock1(mutex); // 第 1 次加锁：当前线程已持有 mutex
    std::this_thread::sleep_for(std::chrono::milliseconds(1));
    std::lock_guard<std::mutex> lock2(mutex); // 第 2 次加锁同一把锁：阻塞等待自己释放 —— 死锁点
    std::cout << "Thread success" << std::endl; // 永远执行不到：线程已永久阻塞在上面
}
```

**解决方法**：

使用递归锁 `std::recursive_mutex`，通过锁计数器实现可重入性。其工作原理如下：
- 锁计数器机制：同一线程每次调用 `lock()` 时，内部计数器递增；调用 `unlock()` 时计数器递减。仅当计数器归零时，锁才真正释放供其他线程获取。
- 与线程ID的关联：虽然实现上会记录持有锁的线程ID（用于验证重入权限），但避免死锁的关键在于允许同一线程多次加锁，而非单纯依赖ID检测。若线程 `A` 持有锁时再次请求，递归锁会通过计数器放行，而普通 `std::mutex` 会因重复加锁直接死锁。
- 性能权衡：递归锁因维护计数器及线程ID信息，性能略低于普通互斥锁，适用于递归调用或复杂回调等必须嵌套加锁的场景。
- 使用建议：递归锁容易掩盖加锁范围的设计问题，能通过重构（缩小或拆分临界区）解决时，应优先重构而不是引入递归锁。

```cpp
std::recursive_mutex mutex;
void ThreadFunc()
{
    std::lock_guard<std::recursive_mutex> lock1(mutex); // 第 1 次加锁：计数器 0 -> 1
    std::this_thread::sleep_for(std::chrono::milliseconds(1));
    std::lock_guard<std::recursive_mutex> lock2(mutex); // 同线程重入：计数器 1 -> 2，直接放行
    std::cout << "Thread success" << std::endl;
    // 作用域结束时逆序析构，计数器归零才真正释放锁
}
```

#### 多个线程对多个锁相互加锁等待

如果同时存在多个线程和多个锁，而每个线程都有机会操作所有的锁，那么这就可能导致死锁，比如线程 `A` 加锁 `mutex1`，等待加锁 `mutex2`，而线程 `B` 加锁 `mutex2`，等待加锁 `mutex1`。

代码示例如下：

```cpp
#include <iostream>
#include <thread>
#include <mutex>

std::mutex mutex1, mutex2;

void ThreadA()
{
    std::lock_guard<std::mutex> lock1(mutex1); // 先锁 mutex1
    std::this_thread::sleep_for(std::chrono::milliseconds(1)); // 持有 mutex1 时暂停，给 ThreadB 锁定 mutex2 的机会
    std::lock_guard<std::mutex> lock2(mutex2); // 再申请 mutex2：若已被 ThreadB 持有，则互相等待
    std::cout << "Thread A" << std::endl;
}

void ThreadB()
{
    std::lock_guard<std::mutex> lock2(mutex2); // 先锁 mutex2
    std::this_thread::sleep_for(std::chrono::milliseconds(1)); // 持有 mutex2 时暂停，给 ThreadA 锁定 mutex1 的机会
    std::lock_guard<std::mutex> lock1(mutex1); // 再申请 mutex1：若已被 ThreadA 持有，则互相等待
    std::cout << "Thread B" << std::endl;
}

int main()
{
    std::thread t1(ThreadA);
    std::thread t2(ThreadB);
    t1.join();
    t2.join();
    return 0;
}
```

在这个代码中，`ThreadA` 首先尝试锁定 `mutex1` 然后是 `mutex2`，而 `ThreadB` 则是首先锁定 `mutex2` 然后是 `mutex1`。如果两个线程几乎同时运行，它们可能会各自锁定一个互斥量，然后永远等待另一个互斥量的释放，这就导致了死锁。

**解决方法一**：

始终都按照一致的顺序对多个锁进行加锁，比如有两个锁 `mutex1` 和 `mutex2`，所有线程都必须采用同一种顺序（例如都按先 `mutex1` 后 `mutex2` 或者都按先 `mutex2` 后 `mutex1`），不能各自选择不同顺序。

```cpp
std::mutex mutex1, mutex2;
void ThreadA()
{
    std::lock_guard<std::mutex> lock1(mutex1); // 按先 mutex1 后 mutex2 的同一顺序加锁
    std::lock_guard<std::mutex> lock2(mutex2);
    std::cout << "Thread A" << std::endl;
}

void ThreadB()
{
    std::lock_guard<std::mutex> lock1(mutex1); // 加锁顺序与 ThreadA 完全一致，不会形成交叉持有锁
    std::lock_guard<std::mutex> lock2(mutex2);
    std::cout << "Thread B" << std::endl;
}
```

统一顺序后，无论线程以怎样的时序交错运行都不会死锁，后到者只会阻塞在第一把锁 `mutex1` 上，等先到者执行完毕释放后再继续。

在大型项目中，锁的数量多且来源分散，仅靠人工约定顺序容易疏漏。常用的工程化落地手段是锁层级（Lock Hierarchy）：给每把锁定义层级编号，约定所有线程只能按编号递增（或递减）的次序加锁，一旦发现违反层级的代码即视为设计缺陷。

**解决方法二**：

通过非阻塞的 `try_lock()` 尝试获取锁，若失败则释放已持有的锁并重试。由于线程不会在持有一把锁的状态下阻塞等待另一把锁，因此打破了“请求和保持”条件。这种方式相比直接 `lock()` 能有效预防死锁，但需注意活锁风险（线程持续重试）以及权衡频繁重试带来的性能开销。

```cpp
std::mutex mutex1, mutex2;
void ThreadA()
{
    while(true)
    {
        if(mutex1.try_lock())
        {
            std::this_thread::sleep_for(std::chrono::milliseconds(1));
            if(mutex2.try_lock())
            {
                std::cout << "Thread A" << std::endl;
                mutex2.unlock(); // 先释放后获取的锁（逆序）
                mutex1.unlock();
                break;
            }
            else
            {
                mutex1.unlock(); // 拿不到 mutex2，先释放已持有的 mutex1，打破“请求和保持”条件
                std::this_thread::sleep_for(std::chrono::milliseconds(1));
            }
        }
        else
        {
            std::this_thread::sleep_for(std::chrono::milliseconds(1)); // 避免获取第一把锁失败时忙等空转
        }
    }
}

void ThreadB()
{
    while(true)
    {
        if(mutex2.try_lock())
        {
            std::this_thread::sleep_for(std::chrono::milliseconds(1));
            if(mutex1.try_lock())
            {
                std::cout << "Thread B" << std::endl;
                mutex1.unlock(); // 先释放后获取的锁（逆序）
                mutex2.unlock();
                break;
            }
            else
            {
                mutex2.unlock(); // 拿不到 mutex1，先释放已持有的 mutex2，打破“请求和保持”条件
                std::this_thread::sleep_for(std::chrono::milliseconds(1));
            }
        }
        else
        {
            std::this_thread::sleep_for(std::chrono::milliseconds(1)); // 避免获取第一把锁失败时忙等空转
        }
    }
}
```

**解决方法三**：

倘若实在无法确保顺序，那么可以使用 C++17 提供的 `std::scoped_lock` 进行同步加锁。其内部基于 `std::lock()` 的免死锁算法（尝试加锁，失败则回退重试），能以避免死锁的方式一次性获取所有传入的锁。

```cpp
std::mutex mutex1, mutex2;
void ThreadA()
{
    std::scoped_lock<std::mutex, std::mutex> lock1(mutex1, mutex2); // 构造时以免死锁算法一次性锁定 mutex1、mutex2
    std::this_thread::sleep_for(std::chrono::milliseconds(1)); // 模拟临界区内的耗时操作/延长持锁时间
    std::cout << "Thread A" << std::endl;
}

void ThreadB()
{
    std::scoped_lock<std::mutex, std::mutex> lock1(mutex1, mutex2); // 同样一次性锁定两把锁，不会与 ThreadA 交叉持有
    std::this_thread::sleep_for(std::chrono::milliseconds(1)); // 模拟临界区内的耗时操作/延长持锁时间
    std::cout << "Thread B" << std::endl;
}
```

若受限于 C++11/14（没有 `std::scoped_lock`），可以用 `std::lock()` 配合 `std::adopt_lock` 实现同样的效果：`std::lock()` 同样以免死锁算法一次性锁定多把锁；随后用 `std::lock_guard` 接管已持有的锁，`std::adopt_lock` 表示构造时不再加锁、仅负责析构时释放。

```cpp
std::mutex mutex1, mutex2;
void ThreadA()
{
    std::lock(mutex1, mutex2); // 采用避免死锁的算法一次性锁定 mutex1、mutex2
    std::lock_guard<std::mutex> lock1(mutex1, std::adopt_lock); // 接管 mutex1：构造不加锁，析构时释放
    std::lock_guard<std::mutex> lock2(mutex2, std::adopt_lock); // 接管 mutex2：构造不加锁，析构时释放
    std::cout << "Thread A" << std::endl;
}
```

`ThreadB` 的写法相同，此处不再重复。

**解决方法四**：

使用作用域或者函数封装等利用 RAII 的方式，让锁管理对象（如 `std::lock_guard` 或 `std::unique_lock`）的作用域限制在代码块或函数内，使得线程用完一把锁就立即释放，不会在持有一把锁的同时再去申请另一把锁，从而避免死锁。

```cpp
std::mutex mutex1, mutex2;
void ThreadA()
{
    {
        std::lock_guard<std::mutex> lock1(mutex1);
    } // 作用域结束，立即释放 mutex1

    std::this_thread::sleep_for(std::chrono::milliseconds(1)); // 模拟两次临界区之间的耗时业务处理

    {
        std::lock_guard<std::mutex> lock2(mutex2);
    } // 作用域结束，立即释放 mutex2

    std::cout << "Thread A" << std::endl;
}

void ThreadB()
{
    {
        std::lock_guard<std::mutex> lock2(mutex2);
    } // 作用域结束，立即释放 mutex2

    std::this_thread::sleep_for(std::chrono::milliseconds(1)); // 模拟两次临界区之间的耗时业务处理

    {
        std::lock_guard<std::mutex> lock1(mutex1);
    } // 作用域结束，立即释放 mutex1

    std::cout << "Thread B" << std::endl;
}
```

此方案实质是把一个双锁临界区拆成两个独立单锁临界区，这只有在两次操作之间没有原子性要求时才成立。如果业务必须同时持有两把锁（例如原子地转移两个账户的余额），方案四会破坏正确性，此时应改用方法一/二/三这类能够同时持有两把锁的方案。

#### 持有锁等待其他线程

线程 `A` 持有锁 `mutex` 的同时调用 `join()` 等待线程 `B` 结束，而线程 `B` 恰好也需要锁 `mutex` 才能完成工作——`B` 永远拿不到 `mutex`，`A` 永远等不到 `B`，形成死锁。这类“锁 + 等待”组合的死锁比纯多锁死锁更隐蔽。

```cpp
std::mutex mutex;
void ThreadB(int& result)
{
    std::lock_guard<std::mutex> lock(mutex); // ThreadB 也需要 mutex 才能干活
    result = 42;
}

void ThreadA()
{
    int result = 0;
    std::lock_guard<std::mutex> lock(mutex); // ThreadA 先持有 mutex
    std::thread t(ThreadB, std::ref(result));
    t.join(); // 等待 ThreadB —— 但 ThreadB 拿不到 mutex，永远无法结束：死锁
}
```

**解决方法**：

核心原则是不要在持有锁的状态下去等待其他线程：把锁的作用域收窄，释放锁之后再发起 `join()` 等待。

```cpp
void ThreadA()
{
    int result = 0;
    {
        std::lock_guard<std::mutex> lock(mutex); // 锁只用于保护共享数据
        // ... 需要持锁的操作 ...
    } // 作用域结束，先释放 mutex

    std::thread t(ThreadB, std::ref(result));
    t.join(); // 无锁状态下等待，ThreadB 可以正常获取 mutex 并结束
    std::cout << "Thread success" << std::endl;
}
```

如果等待确实无法移出锁外，就要从设计上消除依赖：确保“等待者持有的锁”与“被等待者需要的锁”没有交集，例如用不同的锁分别保护各自的数据，或改用消息队列传递结果，让被等待的线程不依赖等待者手里的锁。

#### 持有锁调用外部代码

在持锁状态下回调外部代码（用户回调、虚函数、其他模块的接口），而被调用方的加锁行为不受自己控制：回调内若再次加同一把锁，就是重复加锁死锁；若与其他线程形成交叉等待，则是多锁死锁。这类问题常在联调或依赖升级后突然出现。

```cpp
std::mutex mutex;
void ThreadFunc(const std::function<void()>& callback)
{
    std::lock_guard<std::mutex> lock(mutex);
    callback(); // 危险：回调内部若再次加锁 mutex，则重复加锁死锁；
                // 若与其他线程交叉加锁，则形成多锁死锁
    std::cout << "Thread success" << std::endl;
}
```

实践上应尽量在释放锁之后再发起回调；确实必须在锁内调用时，要在接口约定中明确“回调内不得加哪些锁”。

#### 线程间 join 交叉等待

`join()` 的本质也是“等待对方释放资源”——等的是目标线程的结束。如果线程 `A` 调用 `tB.join()` 等待线程 `B`，而线程 `B` 又在等待线程 `A` 结束，两者就互相等待，形成没有锁身影的死锁，更加隐蔽。同理，在线程内部对代表自身的 `std::thread` 对象调用 `join()` 属于逻辑错误，标准要求实现检测并抛出 `std::system_error` 异常。

#### 条件变量永久等待

条件变量的误用不属于锁之间的相互等待，但表现同样是线程永久卡死，排查死锁时要一并考虑。常见原因有三种：
- 等待方不检查条件直接 `wait()`，错过了此前已经发生的 notify，从此无人再通知；
- 通知方修改共享状态时未持锁，修改对等待方不可见；
- 修改状态后忘记调用 `notify_one()` / `notify_all()`。

规范做法：等待方使用带谓词的 `wait(lock, pred)`，自动处理虚假唤醒和错过唤醒；通知方持锁修改共享状态，释放锁后再通知。

## 死锁的排查与兜底

死锁一旦发生，表现为相关线程永久阻塞、CPU 占用极低。常用排查与兜底手段：
- 调试器查看线程栈：卡死后用调试器附加到进程（如 Visual Studio 的“调试 → 附加到进程”，或 Linux 下 `gdb -p`），查看各线程的调用栈。如果多个线程都停在加锁调用上，且互相持有的锁形成环（Windows 下 WinDbg 可用 `!locks` 查看锁的持有/等待关系），即可确认死锁并定位到具体加锁位置。
- ThreadSanitizer 检测：g++/clang++ 编译时加 `-fsanitize=thread -g`，TSan 会在运行时监控锁的获取顺序，对“两个线程以相反顺序获取同样两把锁”的死锁隐患报告 lock-order-inversion。注意 MSVC 不支持 TSan，需在 Linux/macOS 下使用。
- 超时兜底：把 `std::mutex` 换成 `std::timed_mutex`，用 `try_lock_for()` 设置等待上限，超时后放弃本次操作走降级/重试逻辑，避免永久卡死。代价是要为临界区设计超时后的处理策略，通常只在无法保证加锁顺序的核心路径上使用。

    ```cpp
    std::timed_mutex mutex1;

    void ThreadA()
    {
        if (mutex1.try_lock_for(std::chrono::milliseconds(100))) // 最多等待 100ms
        {
            std::lock_guard<std::timed_mutex> lock(mutex1, std::adopt_lock); // 接管已持有的锁，析构时释放
            std::cout << "Thread success" << std::endl;
        }
        else
        {
            std::cout << "Thread timeout" << std::endl; // 超时降级，避免永久阻塞
        }
    }
    ```

注意上面的示例只演示了单把锁的情形。多锁场景下，对每把锁的获取都应设置超时，且任何一把获取失败都要先释放已持有的锁，再进入降级/重试逻辑，避免陷入“持有一把锁去等另一把锁”的状态。
