# 多线程同步

C++ 多线程同步的核心，是解决多个线程并发访问共享数据时产生的竞态条件（Race Condition）。如果没有同步，两个线程同时写同一个变量，结果取决于调度顺序，程序行为就变得不可预测。

## 问题的根因与解决方案

多线程共享同一进程的地址空间，这带来便利，也带来两个麻烦：
1. 数据竞争：多个线程同时读写同一内存位置，且至少有一个是写操作，且没有同步。C++ 标准明确规定这是未定义行为，不只是“结果可能不对”，而是编译器可以假设它不存在，从而做出各种优化。
2. 执行顺序不确定：线程调度由操作系统决定，你无法预知谁先谁后。同步机制的本质，就是给这种不确定性人为施加顺序约束。

所有同步工具，归根结底在保证两件事：
1. 互斥（Mutual Exclusion）：同一时刻只有一个线程能进入临界区，防止数据竞争。
2. 可见性（Visibility）：一个线程对共享变量的修改，其他线程能及时看到，而不是读到 CPU 缓存或寄存器里的旧值。

C++ 同步工具可分为两大层次：
1. 互斥与条件变量（高层，基于锁）。适合保护较大的临界区。
2. 原子操作与内存序（底层，无锁）。当临界区很小，比如只是一个计数器，用锁的开销可能不划算，这时可以用 `std::atomic` 实现原子操作。

## 互斥

这是最常用的方式，适合保护较大的临界区。

### 互斥量

互斥锁用于保护共享资源，确保同一时间只有一个线程可以访问该资源。

| 互斥量                   | 版本    | 作用                                      |
| --------------------- | ----- | --------------------------------------- |
| `std::mutex`                 | C++11 | 最基本的互斥量                                 |
| `std::timed_mutex`           | C++11 | 有超时机制的互斥量                               |
| `std::recursive_mutex`       | C++11 | 可重入的互斥量                                 |
| `std::recursive_timed_mutex` | C++11 | 结合 `std::timed_mutex` 和 `std::recursive_mutex` 特点的互斥量 |
| `std::shared_timed_mutex`    | C++14 | 具有超时机制的可共享互斥量                           |
| `std::shared_mutex`          | C++17 | 共享的互斥量                                  |

这个系列的对象均提供了加锁（`lock()`）、尝试加锁（`try_lock()`）和解锁（`unlock()`）的方法。`lock()` 和 `unlock()` 必须成对使用：如果只加锁忘记解锁，锁会被一直占用，其他线程将永远阻塞。

#### std::mutex(C++11)

独占式访问资源互斥量，同一时间只可以被一个线程锁定。同一个线程对已持有的 `std::mutex` 再次调用 `lock()` 属于未定义行为（实际中通常表现为死锁）。通过成员函数 `lock()` 进行上锁，`unlock()` 进行解锁。

```cpp
std::mutex mtx;
mtx.lock();
// todo: 访问共享资源
mtx.unlock();
```

#### std::recursive_mutex(C++11)

这是递归互斥量，允许同一线程多次获得这个互斥量而不会死锁，只要解锁的次数和锁定的次数相同，互斥量就会被释放。通过成员函数 `lock()` 进行上锁，`unlock()` 进行解锁。

主要场景：
1. 一个类的公有方法加了锁，内部又调用了另一个也加锁的公有方法。
2. 递归算法，每一层都需要保护共享数据。

```cpp
std::recursive_mutex mtx;
void recursive_func(int depth)
{
    mtx.lock();
    if (depth > 0)
    {
        recursive_func(depth - 1);   // 同一线程再次 lock，不会死锁
    }
    mtx.unlock();
}

int main()
{
    recursive_func(3);
    return 0;
}
```

如果是普通的 `std::mutex`，上面这段递归调用在第二次 `lock()` 时就是未定义行为（实际中通常表现为线程永久阻塞，即死锁）。而 `std::recursive_mutex` 内部会记录当前持有锁的线程 ID 和递归计数，同一个线程再次 `lock()` 时只增加计数，不阻塞。不过有以下几点需要注意：
1. `lock()` / `unlock()` 必须配对使用，同一个线程 `lock()` 了几次，就要 `unlock()` 几次，锁才真正释放。
2. 只对同一线程递归有效，如果线程 A 持有锁，线程 B 调用 `lock()` 仍然会被阻塞，这一点和普通 `std::mutex` 一样。
3. 不能跨线程 `unlock()`，一个线程加的锁必须由同一个线程解锁，否则是未定义行为。
4. 性能开销比 `std::mutex` 大，因为每次 `lock()`/`unlock()` 都需要检查线程 ID 和递归计数。如果只是出于偷懒而滥用 `std::recursive_mutex`，往往意味着设计有问题，更好的做法是拆分函数、缩小锁的粒度，让每个加锁的函数不再调用其他加锁的函数。

#### std::timed_mutex(C++11)

带超时功能的独占互斥量，可以理解为 `std::mutex` 的超时增强版，为此它提供了 `try_lock_for()` 和 `try_lock_until()` 两个方法。
1. `try_lock_for(duration)`：尝试锁定互斥量，最多等待指定的时间 `duration`。
2. `try_lock_until(time_point)`：尝试锁定互斥量，直到指定的时间点 `time_point`。

```cpp
std::timed_mutex mtx;
void timed_func1()
{
    if (mtx.try_lock_for(std::chrono::seconds(1)))  // 尝试锁定互斥量 最多等待1秒
    {
        std::cout << "Locked" << std::endl;
        // todo: 访问共享资源
        mtx.unlock();
    }
    else
    {
        std::cout << "Failed to lock" << std::endl;
    }
}

void timed_func2()
{
    auto timeout = std::chrono::steady_clock::now() + std::chrono::seconds(2); // 2秒后的时间点
    if (mtx.try_lock_until(timeout)) // 尝试锁定互斥量 直到2秒后的时间点
    {
        std::cout << "Locked" << std::endl;
        // todo: 访问共享资源
        mtx.unlock();
    }
    else
    {
        std::cout << "Failed to lock" << std::endl;
    }
}
```

当你希望线程在获取锁时不要无限期等待，而是能在超时后放弃、转而执行其他逻辑（如记录日志、降级处理或重试）时，`std::timed_mutex` 是合适的选择。

#### std::recursive_timed_mutex(C++11)

同时具备递归所有权和带超时尝试获取两种特性的互斥量，是 `std::recursive_mutex` 和 `std::timed_mutex` 的结合体。它既允许同一线程多次加锁（递归），又支持 `try_lock_for()` / `try_lock_until()` 超时等待。适用于当一个类的公有方法需要加锁，内部又调用了另一个也加锁的方法（递归特性），同时又不希望线程在锁竞争激烈时无限期等待（超时特性）。

```cpp
std::recursive_timed_mutex mtx;

// 内部方法：也需要加锁保护共享数据
void update_func()
{
    mtx.lock();
    // 更新缓存数据
    mtx.unlock();
}

// 公有方法：带超时地加锁，内部调用 update_func（同一线程再次加锁，递归不阻塞）
void thread_func()
{
    // 尝试在 500ms 内获取锁，避免长时间阻塞
    if (mtx.try_lock_for(std::chrono::milliseconds(500)))
    {
        std::cout << "Locked" << std::endl;
        update_func();  // 同一线程再次 lock，递归计数 +1，不阻塞
        // ... 执行其他工作
        mtx.unlock();    // 递归计数 -1
    }
    else
    {
        // 超时未获取锁，执行降级逻辑（如使用旧数据）
        std::cout << "Failed to lock" << std::endl;
    }
}
```

上面的示例中，`thread_func()` 用 `try_lock_for()` 带超时地获取锁，获取成功后调用 `update_func()`，后者会再次 `lock()`。由于是同一线程且使用的是递归互斥量，第二次 `lock()` 只增加计数不阻塞，最终需要两次 `unlock()` 才能完全释放。如果换用普通 `std::mutex`，第二次 `lock()` 就是未定义行为；如果换用 `std::recursive_mutex`，则没有超时能力，线程可能永久阻塞。

#### std::shared_mutex(C++17)

C++17 引入的读写锁（也叫共享互斥量），它允许多个线程同时读共享数据，但同一时间只允许一个线程写共享数据。也就是说，在存在多个线程对共享资源读、少许线程对共享资源写的情况下，`std::shared_mutex` 比 `std::mutex` 效率更高。

`std::shared_mutex` 提供了 `lock()` 和 `unlock()` 方法获取写锁和解除写锁，提供了 `lock_shared()` 和 `unlock_shared()` 方法获取读锁和解除读锁，写锁模式我们称为排他锁（Exclusive Locking），读锁模式我们称为共享锁（Shared Locking）。

排他性锁定方法有：

| 函数       | 功能描述             | 备注     |
| -------- | ---------------- | ------ |
| `lock`     | 锁定互斥，若互斥不可用则阻塞   | 公有成员函数 |
| `try_lock` | 尝试锁定互斥，若互斥不可用则返回 | 公有成员函数 |
| `unlock`   | 解锁互斥             | 公有成员函数 |

共享锁定方法有：

| 函数              | 功能描述                   | 备注     |
| --------------- | ---------------------- | ------ |
| `lock_shared`     | 为共享所有权锁定互斥，若互斥不可用则阻塞   | 公有成员函数 |
| `try_lock_shared` | 尝试为共享所有权锁定互斥，若互斥不可用则返回 | 公有成员函数 |
| `unlock_shared`   | 解锁互斥（共享所有权）            | 公有成员函数 |

另外，实际使用中通常配合两个 RAII 包装器（**`std::unique_lock`** 和 **`std::shared_lock`**）来管理 `std::shared_mutex`。其中 `std::unique_lock` 是 C++11 引入的通用独占锁管理器，可配合包括 `std::shared_mutex` 在内的任意互斥量使用，这里用它管理写锁；`std::shared_lock`（C++14）则是专为共享锁设计的管理器，用它管理读锁。两者都在构造时自动加锁、析构时自动解锁。

> **注意**：`std::shared_mutex` 标准并不保证读写公平性，在写操作频繁的场景中可能出现**写者饥饿**（写线程长时间获取不到写锁）。如果需要超时等待能力，可使用 `std::shared_timed_mutex`（C++14）；如果编译器支持 C++17，优先使用 `std::shared_mutex`，它去掉了不必要的超时机制，实现更轻量。

```cpp
std::shared_mutex mtx;
void reader() 
{
    std::shared_lock<std::shared_mutex> lock(mtx);
    std::cout << "Reading sharedData" << std::endl;
}

void writer() 
{
    std::unique_lock<std::shared_mutex> lock(mtx);
    std::cout << "Writing sharedData" << std::endl;
}
```

#### std::shared_timed_mutex(C++14)

C++14 引入的带超时功能的读写锁。它是 `std::shared_mutex`（C++17）的前身，两者核心机制相同，区别在于 `std::shared_timed_mutex` 额外提供了带超时的尝试加锁接口，类似于 `std::timed_mutex` 的行为。`std::shared_timed_mutex` 额外提供了以下超时方法：`try_lock_for()`、`try_lock_until()`、`try_lock_shared_for()`、`try_lock_shared_until()`。

排他性锁定方法有：

| 函数             | 功能描述                      | 备注     |
| -------------- | ------------------------- | ------ |
| `lock`           | 锁定互斥，若互斥不可用则阻塞            | 公有成员函数 |
| `try_lock`       | 尝试锁定互斥，若互斥不可用则返回          | 公有成员函数 |
| `try_lock_for`   | 尝试锁定互斥，若互斥在指定的时限时期中不可用则返回 | 公有成员函数 |
| `try_lock_until` | 尝试锁定互斥，若直至抵达指定时间点互斥不可用则返回 | 公有成员函数 |
| `unlock`         | 解锁互斥                      | 公有成员函数 |

共享锁定方法有：

| 函数                    | 功能描述                            | 备注     |
| --------------------- | ------------------------------- | ------ |
| `lock_shared`           | 为共享所有权锁定互斥，若互斥不可用则阻塞            | 公有成员函数 |
| `try_lock_shared`       | 尝试为共享所有权锁定互斥，若互斥不可用则返回          | 公有成员函数 |
| `try_lock_shared_for`   | 尝试为共享所有权锁定互斥，若互斥在指定的时限时期中不可用则返回 | 公有成员函数 |
| `try_lock_shared_until` | 尝试为共享所有权锁定互斥，若直至抵达指定时间点互斥不可用则返回 | 公有成员函数 |
| `unlock_shared`         | 解锁互斥（共享所有权）                     | 公有成员函数 |

### 互斥量管理

`lock()` 和 `unlock()` 必须成对使用，但是如果一个函数中有很多出口，而互斥体对象又是需要在整个函数作用域保护的资源，那么在编码时容易因为忘记在某个出口处调用 `unlock()` 而导致锁泄漏（其他线程永远阻塞）。为此，推荐利用 RAII 技术封装这两个接口，C++ 标准已经为我们提供了如下封装：

| 互斥量管理       | 版本    | 作用          |
| ----------- | ----- | ----------- |
| `lock_guard`  | C++11 | 基于作用域的互斥量管理 |
| `unique_lock` | C++11 | 更加灵活的互斥量管理  |
| `shared_lock` | C++14 | 共享互斥量的管理    |
| `scoped_lock` | C++17 | 多互斥量避免死锁的管理 |

#### std::lock_guard(C++11)

**特点**：
- **基本用法**：简单、轻量级的锁管理。
- **自动解锁**：在作用域结束时自动解锁。
- **接口简单**：只有构造函数和析构函数，不能显式解锁，也无法重新加锁。
- **不可拷贝不可移动**：`std::lock_guard` 既不可拷贝也不可移动，生命周期严格绑定作用域。
- **适用场景**：当需要一个简单的互斥量保护，且不需要更复杂的锁控制时。
- **性能开销小**：由于功能简单，性能开销较小。

**适用场景**：
- 当锁定范围非常明确且简单，如在函数的起始和结束处保护一个共享资源。
- 当不需要在同一作用域内进行手动解锁或重新加锁操作时。
- 当不需要与条件变量配合使用时（`std::lock_guard` 无法满足 `condition_variable::wait` 的需求）。

```cpp
std::mutex mtx;
void thread_func()
{
    std::lock_guard<std::mutex> lock(mtx);
    std::cout << "In critical section" << std::endl;
    // 离开作用域，自动解锁
}
```

#### std::unique_lock(C++11)

**特点**：
- **基本用法**：提供更灵活的锁管理功能。
- **自动解锁**：在析构函数中自动解锁。
- **灵活控制**：支持延迟锁定、显式解锁和重新锁定。
- **可移动不可拷贝**：可以通过移动语义转移锁的所有权（如从工厂函数返回 `std::unique_lock`），但不能拷贝。
- **辅助接口**：提供 `owns_lock()` 查询当前是否持有锁、`release()` 释放锁所有权并返回关联的互斥量指针、`mutex()` 获取关联的互斥量指针。
- **与条件变量配合**：`std::condition_variable::wait()` 内部会先调用 `unique_lock` 的 `unlock()` 释放锁（让其他线程能进入临界区修改条件），被唤醒后再重新 `lock()`，因此条件变量必须搭配 `std::unique_lock` 使用，`std::lock_guard` 无法满足。
- **性能开销**：由于提供了更多功能，相比 `std::lock_guard` 性能开销略大。

**适用场景**：
- 当需要在同一作用域内手动释放锁，或者需要在不同的作用域中重新加锁时。
- 当需要与 `std::condition_variable` 一起使用以实现线程的等待和通知机制时。
- 当锁定范围不够明确，需要更灵活的锁控制时。

```cpp
std::mutex mtx;
void thread_func()
{
    std::unique_lock<std::mutex> lock(mtx);
    std::cout << "In critical section" << std::endl;
    std::this_thread::sleep_for(std::chrono::seconds(1));
    // 可以显式解锁
    lock.unlock();
    // 之后可以重新锁定
    lock.lock();
}
```

#### std::shared_lock(C++14)

C++14 标准中引入的一个类，用于与 `std::shared_mutex` 配合使用，以实现共享（读）锁的功能。

**特点**：
- **共享锁**：允许多个线程同时持有共享锁来读取数据。
- **构造函数**：通过构造 `std::shared_lock` 对象来获取 `std::shared_mutex` 的共享锁，并自动管理其生命周期。
- **自动释放**：当 `std::shared_lock` 对象被销毁时，它会自动释放持有的共享锁。

**适用场景**：
- 需要读写锁的时候。

示例见上文 `std::shared_mutex` 的示例。

#### std::scoped_lock(C++17)

在 C++17 标准中引入的，它提供了一种简洁且安全的方式来管理多个互斥锁的锁定。`std::scoped_lock` 是一种模板类，可以用于锁定一个或多个 `std::mutex`、`std::recursive_mutex`、`std::shared_mutex` 等互斥量，并在对象销毁时自动释放这些锁。

**特点**：
- **锁定多个互斥量**：可以同时锁定多个互斥量，内部采用死锁避免算法，防止因加锁顺序不一致导致的死锁。
- **自动解锁**：当 `std::scoped_lock` 对象被销毁时，它会自动解锁所有已锁定的互斥量。
- **避免死锁**：由于所有互斥量都在构造时同时锁定，可以减少死锁的风险。
- **单锁场景推荐**：C++17 起，即使只锁定单个互斥量，也推荐使用 `std::scoped_lock` 替代 `std::lock_guard`，以统一锁管理的编码风格。`std::lock_guard` 并未被废弃，但在新代码中没有理由优先选择它。

```cpp
std::mutex mutex1;
std::mutex mutex2;
void task1()
{
    std::scoped_lock lock(mutex1, mutex2);
    std::cout << "Task 1 is executing" << std::endl;
    // todo: 访问共享资源
}

void task2()
{
    std::scoped_lock lock(mutex1, mutex2);
    std::cout << "Task 2 is executing" << std::endl;
    // todo: 访问共享资源
}
```

### 锁标签

锁标签是 C++11 引入的空类标签，用于在 RAII 锁管理器的构造函数中指定加锁策略，避免在已经手动加锁的情况下重复加锁，或者延迟到稍后再加锁。

| 标签 | 类型 | 含义 |
| --- | --- | --- |
| `std::defer_lock` | `defer_lock_t` | 构造时不加锁，稍后手动调用 `lock()` |
| `std::try_to_lock` | `try_to_lock_t` | 构造时尝试加锁（非阻塞），可通过 `owns_lock()` 查询是否成功 |
| `std::adopt_lock` | `adopt_lock_t` | 假设当前线程已经持有锁，构造时只接管所有权，不重复加锁 |

三个标签并非适用于所有锁管理器：

| 标签 | `lock_guard` | `unique_lock` | `shared_lock` | `scoped_lock` |
| --- | :---: | :---: | :---: | :---: |
| `std::defer_lock` | ❌ | ✅ | ✅ | ❌ |
| `std::try_to_lock` | ❌ | ✅ | ✅ | ❌ |
| `std::adopt_lock` | ✅ | ✅ | ✅ | ✅ |

> `std::defer_lock` 和 `std::try_to_lock` 要求锁管理器拥有 `lock()` 或 `try_lock()` 方法，`std::lock_guard` 和 `std::scoped_lock` 没有这些方法，因此不支持。

#### std::defer_lock

延迟加锁，构造时不锁，由调用方在稍后手动 `lock()`。常用于需要先做某些准备操作，再进入临界区的场景。

```cpp
std::mutex mtx;
void thread_func()
{
    std::unique_lock<std::mutex> lock(mtx, std::defer_lock);  // 构造时不加锁

    // 执行一些不需要加锁的准备工作
    prepare_data();

    lock.lock();  // 手动加锁
    // 临界区
    // 离开作用域，lock 析构时自动解锁
}
```

#### std::try_to_lock

构造时尝试加锁但不阻塞，无论成功与否都会立即返回。通过 `owns_lock()` 查询是否拿到了锁，适合不希望线程被阻塞的场景。

```cpp
std::mutex mtx;
void thread_func()
{
    std::unique_lock<std::mutex> lock(mtx, std::try_to_lock);
    if (lock.owns_lock())
    {
        // 成功获取锁，可以安全访问共享资源
    }
    else
    {
        // 未获取锁，执行其他逻辑（如降级处理或稍后重试）
    }
}
```

#### std::adopt_lock

假设当前线程已经手动锁定了互斥量，构造时只接管所有权（接管后析构时自动 `unlock()`），不再重复加锁。通常与 `lock()` 或 `try_lock()` 配合使用，先手动锁定多个互斥量（利用死锁避免算法），再用 `std::adopt_lock` 交由 RAII 管理。

```cpp
std::mutex mtx1;
std::mutex mtx2;
void thread_func()
{
    // 先手动同时锁定多个互斥量（内部使用死锁避免算法）
    std::lock(mtx1, mtx2);

    // 用 std::adopt_lock 接管，析构时自动解锁
    std::lock_guard<std::mutex> lock1(mtx1, std::adopt_lock);
    std::lock_guard<std::mutex> lock2(mtx2, std::adopt_lock);

    // 安全访问共享资源，离开作用域后自动解锁
}
```

## 条件变量

条件变量的核心意义在于：解决多线程之间等待某个条件成立的同步问题，避免忙等待，实现高效的线程间协作。C++11 引入了 `std::condition_variable` 和 `std::condition_variable_any` 类型，用于实现条件变量的功能。

### std::condition_variable

`std::condition_variable` 需要与 `std::unique_lock<std::mutex>` 配合使用。当线程需要等待某个条件变成真时，它会获取一个互斥锁，然后在条件变量上等待，等待期间会自动释放互斥锁。另一个线程在满足条件后会获取相同的互斥锁，并调用条件变量的 `notify_one()` 或 `notify_all()` 函数来唤醒等待的线程。

`std::condition_variable` 有三个等待函数：`wait()`、`wait_for()` 和 `wait_until()`，这三个函数需要与互斥锁一起使用，以互斥的方式访问共享资源，并阻塞线程，等待通知。

#### wait

```cpp
// 基本版本，用于等待条件变量满足
void wait(std::unique_lock<std::mutex>& lock);

// 带谓词的版本，防止虚假唤醒，推荐使用
template <class Predicate>
void wait(std::unique_lock<std::mutex>& lock, Predicate pred);
```

`wait()` 函数用于阻塞线程并等待唤醒。在调用 `wait()` 之前，必须获取一个独占锁（`std::unique_lock<std::mutex>`）并将它传递给 `wait()` 函数。
如果条件变量当前不满足，线程将被阻塞，同时释放锁，使得其他线程可以继续执行。当另一个线程调用 `notify_one()` 或 `notify_all()` 来通知条件变量时，被阻塞的线程将被唤醒，并再次尝试获取锁。`wait()` 函数返回时，锁会再次被持有。

`wait()` 函数有一个带谓词的版本，等价于 `while(!pred()) wait(lock);`。只有当 `pred` 条件为 `false` 时调用 `wait()` 才会阻塞当前线程，解决了**唤醒丢失**的问题。而在收到其它线程的通知后只有当 `pred` 为 `true` 时才会被解除阻塞，解决了**虚假唤醒**的问题。

> 唤醒丢失：如果使用不带谓词的`wait()`，当`notify` 发生在`wait()` 之前，通知就丢失了，线程会永远阻塞。带谓词的 `wait()` 在进入阻塞前先检查谓词，从而避免此问题。

> 虚假唤醒：是操作系统/线程库实现层的现象，并非 C++ 规定的行为，但在多核处理器上可能发生（如信号合并、中断等），因此标准要求程序员假设其可能发生并做防护。

```cpp
std::condition_variable cv;
std::mutex mtx;
bool condition = false;

void worker()
{
    std::unique_lock<std::mutex> lock(mtx);
    cv.wait(lock, []{ return condition; }); // 等待条件满足
    // ...
}
```

#### wait_for

```cpp
// 基本版本，用于等待条件变量满足，超时时间为指定的相对时间
template <class Rep, class Period>
std::cv_status wait_for(std::unique_lock<std::mutex>& lock, const std::chrono::duration<Rep, Period>& rel_time);

// 带谓词的版本，防止虚假唤醒，推荐使用
template <class Rep, class Period, class Predicate>
bool wait_for(std::unique_lock<std::mutex>& lock, const std::chrono::duration<Rep,Period>& rel_time, Predicate pred);
```

`wait_for()` 函数用于阻塞线程并等待唤醒，但与 `wait()` 不同，它可以设置一个超时时间。在调用 `wait_for()` 之前，必须获取一个独占锁（`std::unique_lock`）并将它传递给 `wait_for()` 函数。

如果条件变量在指定的超时时间内变为满足，线程将被唤醒，并且 `wait_for()` 返回 `std::cv_status::no_timeout`。如果超时时间到期且仍未收到唤醒通知，`wait_for()` 返回 `std::cv_status::timeout`，线程继续执行。

`wait_for()` 函数同样有一个谓词版本，用法同 `wait()` 函数，可直接用返回值判断是否超时。

```cpp
std::condition_variable cv;
std::mutex mtx;
bool condition = false;

void worker()
{
    std::unique_lock<std::mutex> lock(mtx);
    // 最多等 100ms
    if (cv.wait_for(lock, std::chrono::milliseconds(100), [] { return condition; }))
    {
        // 条件成立
    }
    else
    {
        // 超时
    }
}
```

#### wait_until

```cpp
// 基本版本，用于等待条件变量满足，超时时间为指定的绝对时间点
template <class Clock, class Duration>
std::cv_status wait_until(std::unique_lock<std::mutex>& lock, const std::chrono::time_point<Clock, Duration>& abs_time);

// 带谓词的版本，防止虚假唤醒，推荐使用
template <class Clock, class Duration, class Predicate>
bool wait_until(std::unique_lock<std::mutex>& lock, const std::chrono::time_point<Clock,Duration>& abs_time, Predicate pred);
```

`wait_until()` 接受一个绝对时间点作为参数。线程将等待直到指定的绝对时间点，如果在该时间点之前条件变量满足，`wait_until()` 返回 `std::cv_status::no_timeout`，线程继续执行。如果到达指定时间点仍未收到唤醒通知，`wait_until()` 返回 `std::cv_status::timeout`，线程继续执行。

`wait_until()` 函数同样有一个谓词版本，用法同 `wait()` 函数，可直接用返回值判断是否超时。

```cpp
std::condition_variable cv;
std::mutex mtx;
bool condition = false;

void worker()
{
    std::unique_lock<std::mutex> lock(mtx);
    auto deadline = std::chrono::steady_clock::now() + std::chrono::seconds(1);
    // 等待到当前时间点后1秒
    if (cv.wait_until(lock, deadline, [] { return condition; }))
    {
        // 条件成立
    }
    else
    {
        // 超时
    }
}
```

#### notify_one

```cpp
void notify_one() noexcept;
```

`notify_one()` 用于唤醒等待在条件变量上的单个线程（如果有），若没有线程在等待，则什么也不做。如果有多个线程在条件变量上等待，只有其中一个线程会被唤醒，具体是哪个线程 C++ 标准并未明确，所以是不确定的。被唤醒的线程将尝试获取与条件变量关联的互斥锁，一旦成功获取锁，它可以继续执行。

#### notify_all

```cpp
void notify_all() noexcept;
```

`notify_all()` 用于唤醒等待在条件变量上的所有线程。如果有多个线程在条件变量上等待，所有这些线程都会被唤醒。唤醒的线程将竞争获取与条件变量关联的互斥锁，然后可以继续执行。

```cpp
std::mutex mtx;
std::condition_variable cv;
bool ready = false;

void waiting_thread()
{
    std::unique_lock<std::mutex> lock(mtx);
    cv.wait(lock, [] { return ready; });
    std::cout << "Thread resumed\n";
}

void notifying_thread()
{
    std::this_thread::sleep_for(std::chrono::seconds(1));

    {
        std::lock_guard<std::mutex> lock(mtx);
        ready = true;
    }
    cv.notify_one();
}
```

### std::condition_variable_any

前面提到了 `std::condition_variable` 只与 `std::unique_lock<std::mutex>` 配合使用，因为其 `wait()` 函数需要灵活地解锁和重新加锁，而 `std::unique_lock` 支持手动 `lock/unlock`，其他锁类型则不支持。

如果需要配合其他锁类型（如 `std::shared_lock`），应使用 `std::condition_variable_any`。它拥有完全相同的一套函数签名，只是锁类型是模板参数，可以与任何满足 BasicLockable 的锁（即提供 `lock()` 和 `unlock()` 方法）配合使用，代价是效率略低。

配合 `std::shared_lock<std::shared_mutex>`（共享等待）是 `std::condition_variable_any` 最典型的用武之地：

```cpp
std::shared_mutex mtx;
std::condition_variable_any cv;
bool condition = false;

void worker()
{
    std::shared_lock<std::shared_mutex> lock(mtx);  // 共享锁
    cv.wait(lock, [] { return condition; });
    // ...
}
```

### 特性对比

| 特性                 | std::condition_variable  | std::condition_variable_any |
| --------------------| ------------------------- | --------------------------------- |
| 默认构造             | 有                        |  有                               |
| 拷贝构造 / 拷贝赋值   | 删除                      | 删除                               |
| 移动构造 / 移动赋值   | 删除                      | 删除                               |
| 析构时若有线程等待    | 未定义行为（UB）           | 未定义行为（UB）                     |
| 析构前置要求         | 所有等待线程已被唤醒        | 所有等待线程已被唤醒                 |

## 信号量（C++20）

信号量（Semaphore）是一种同步机制，通过维护一个计数来控制多个线程对共享资源的访问。信号量的计数值是一个非负整数，表示可用资源的数量。当线程或进程需要访问共享资源时，它会尝试获取信号量。如果信号量的计数值大于 0，则将其减 1 并允许线程或进程继续执行；如果信号量的计数值为 0，则线程或进程将被阻塞，直到信号量的计数值大于 0。这样的信号量也称为计数信号量。

除了计数信号量之外，还有二值信号量。二值信号量只有两个状态（0 和 1），类似于互斥锁，主要用于控制单个资源的访问。计数值为 1 表示资源可用，计数值为 0 表示资源被占用。

**信号量用于线程同步时，保证的是操作间的依赖顺序（A 完成后 B 才能做）和并发数量限制，从而避免竞态和资源过载。但它不保证多线程的全局执行顺序。**

C++20 标准引入了 `std::counting_semaphore` 和 `std::binary_semaphore` 类，分别用于实现计数信号量和二值信号量的功能。

信号量的特性如下：
1. 非线程绑定：信号量没有"所有者"概念，任何线程都能 `release()`，不必是执行 `acquire()` 的那个线程。这与 `std::mutex` 有本质区别。
2. 不可拷贝、不可移动：和条件变量一样，信号量对象地址必须稳定。
3. 无虚假唤醒：`acquire()` 只有在真正拿到计数时才返回，不像条件变量需要 `while` 循环防虚假唤醒。
4. 轻量高效：内部通常用原子操作 + 内核等待队列实现，比 `std::mutex` + `std::condition_variable` 模拟更直接。

信号量对象的主要成员函数包括：
1. `acquire()`：用于请求信号量。如果计数值大于 0（表示有资源空闲），计数值减 1 并立即返回，线程获得对资源的访问权；如果计数值为 0（表示资源都已被占用），则阻塞线程直到信号量变为可用状态（即计数值大于 0）。
2. `release(update = 1)`：用于释放信号量，增加计数值 `update`，默认为 1。
3. `try_acquire()`：尝试获取信号量而不阻塞，失败返回 `false`。
4. `try_acquire_for(duration)`: 设置一个超时时间，在时长内反复尝试，超时返回 `false`。
5. `try_acquire_until(time_point)`：接受一个绝对时间点作为参数，在时间点前反复尝试，超时返回 `false`。
6. `max()`：静态函数，返回计数器的最大可能值。

### 计数信号量(std::counting_semaphore)

计数信号量对象可以通过 `std::counting_semaphore<LeastMaxValue> sem(desired)` 创建，并指定其最大计数值的下界和初始计数值。

- `LeastMaxValue`：表示计数器上限的下界，计数器最大能到多少（至少为 `LeastMaxValue` 的具体值），由编译期决定，实际 `max() >= LeastMaxValue`。
- `desired`：初始计数值，计数器一开始是多少，由运行时构造决定。理论上 `desired <= max()`，`max()` 由实现决定，标准只保证 `max() >= LeastMaxValue`。换平台后 `max()` 的具体值可能变化（同一个 `LeastMaxValue`，不同实现给的 `max()` 可能不同）。因此为可移植性，建议 `desired <= LeastMaxValue`，这样在所有平台上都必然满足 `desired <= max()`。

> 注意：`LeastMaxValue` 的必要性在于：它是用户向实现提前许下的需求上限承诺，让实现在编译期就能选用最紧凑的整数类型、最快的平台原语，从而兼顾性能、可行性与溢出边界。`max()` 是编译器实现的保证，`LeastMaxValue` 是用户的需求，方向相反，缺一不可。没有它，实现只能按最坏情况用最宽的类型，所有信号量都会变慢。

你可以用一个初始计数来初始化计数信号量，该计数代表可以同时无阻塞访问资源的线程数量。线程可以获取和释放计数，信号量的计数相应地增加或减少。如果线程尝试获取的计数超过了可用的数量，它将阻塞，直到计数变得可用。

获取和释放计数的伪代码示例如下：

```cpp
std::counting_semaphore<10> sem(1);  // 上限的下界为 10，初始计数值为 1

sem.acquire();  // 计数 1 → 0，成功
sem.acquire();  // 计数为 0，阻塞（等别人 release）

sem.release();  // 计数 0 → 1，唤醒一个等待者
sem.release();  // 计数 1 → 2

// ...
sem.release();  // 若计数已达到 max()，再 release 是未定义行为
```

实现一个并发数量控制的代码示例如下：

```cpp
std::counting_semaphore<3> sem(3);  // 最多 3 个线程同时进入

void worker(int id)
{
    sem.acquire();
    std::cout << "线程 " << id << " 进入临界区" << std::endl;
    std::this_thread::sleep_for(std::chrono::seconds(1));
    std::cout << "线程 " << id << " 离开" << std::endl;
    sem.release();
}

int main()
{
    std::vector<std::thread> ts;
    for(int i = 0; i < 6; ++i)
    {
        ts.emplace_back(worker, i);
    }
    for(auto& t : ts)
    {
        t.join();
    }

    return 0;
}
```

运行可以看到，最多只能有 3 个线程同时进入临界区，后面的线程会阻塞，直到有线程离开临界区。但有意思的是我们发现进入临界区的线程是随机的，而不是按顺序执行的。这正是上面提到的不保证多线程的全局执行顺序。

### 二进制信号量(std::binary_semaphore)

二进制信号量是一种更简单的信号量版本，它只能有两个值：0 和 1。

通常用于两个线程之间的基本互斥或信号传递。虽然具有互斥功能，但它与 `std::mutex` 有本质区别，信号量没有所有者语义，任何线程都可以 `release()`，不一定是执行 `acquire()` 的线程。因此它不能完全替代 `std::mutex`，而是更适合做线程间的信号传递而非资源互斥。

`std::binary_semaphore` 是 `std::counting_semaphore` 最大值为 1 的特例，即：

```cpp
using binary_semaphore = std::counting_semaphore<1>;
```

实现一个操作间的依赖顺序（A 完成后 B 才能做）的代码示例如下：

```cpp
std::binary_semaphore sem(0);  // 初始 0

// 线程 A
void threadA()
{
    std::cout << "线程A进入临界区" << std::endl;
    std::this_thread::sleep_for(std::chrono::seconds(1));
    std::cout << "线程A离开临界区 " << std::endl;
    sem.release();      // 通知：我完成了
}

// 线程 B
void threadB()
{
    sem.acquire();      // 等待：直到 A 完成才继续
    std::cout << "线程B进入临界区 " << std::endl;
}

int main()
{
    std::thread a(threadA);
    std::thread b(threadB);
    a.join();
    b.join();

    return 0;
}
```

| ---------| ----------------------| ----------------------|

| 虚假唤醒 | 需用谓词防护            | 无此问题               |

## 原子操作

### 原子操作定义

`std::atomic<T>` 是 C++11 引入的原子操作模板，用于在多线程环境下进行原子访问，避免数据竞争（data race）。

它保证单个操作不可分割：其他线程只能看到操作完成前或完成后的状态，不会观察到执行到一半的中间态。但多个原子操作之间不具备整体原子性，跨线程的可见性与顺序需通过内存序（`acquire`/`release`/`seq_cst` 等）来控制。

### 原子操作优势

虽然 C++11 提供了其他高并发的 API，例如互斥锁（`std::mutex`）和条件变量（`std::condition_variable`），但这些 API 在某些情况下并不是最佳选择：
1. 性能开销：现代 `std::mutex` 在无竞争时仅执行用户态的原子操作（快速路径），发生竞争时才可能陷入内核系统调用；而 `std::atomic<T>` 对常见标量类型（`int`、指针、`bool` 等）在多数平台上是 lock-free 的，直接映射到硬件原子指令，省去了加锁/解锁的路径开销；较大类型则可能退化为内部锁实现（是否无锁可用 `is_lock_free()` 或 `is_always_lock_free` 来判断）。
2. 避免死锁：使用互斥锁需要小心处理锁的获取和释放，否则容易导致死锁。`std::atomic<T>` 不需要显式加锁和解锁，减少了编程复杂性。
3. 细粒度控制：`std::atomic<T>` 提供了对单个变量的细粒度控制，使得某些简单的并发场景可以更高效地实现。

### 原子操作使用

`std::atomic<T>` 是一个模板类，可以支持多种数据类型的实例化。按照标准，只要类型同时满足以下五个条件：

```cpp
std::is_trivially_copyable<T>::value
std::is_copy_constructible<T>::value
std::is_move_constructible<T>::value
std::is_copy_assignable<T>::value
std::is_move_assignable<T>::value
```

`std::atomic<T>` 就能合法实例化，从而支持原子操作（保证原子性、消除数据竞争）。其支持的数据类型大致有以下几类：
1. 整型：如 `std::atomic<int>`、`std::atomic<long>`、`std::atomic<unsigned>` 等。
2. 浮点型：如 `std::atomic<float>`、`std::atomic<double>` 等。`std::atomic<float>` 可实例化，但对浮点的 `fetch_add` 等是 C++20 才加入的，C++11 下只能 `load`/`store`/`exchange`/CAS。
3. 指针：`std::atomic<T*>`，但不支持引用类型。
4. bool：`std::atomic<bool>`。
5. 其他满足条件的 trivially copyable 自定义类型（但有可能不是lock-free）。
6. 智能指针特化：C++20 额外提供 `std::atomic<std::shared_ptr<T>>` 与 `std::atomic<std::weak_ptr<T>>` 两个特化，可直接对共享指针做原子操作。其他智能指针则无法通过编译（如：`std::unique_ptr` 非 trivially copyable）。

但以上条件只是决定是否支持原子操作，在实际运用过程中，是否 lock-free 取决于类型大小和平台，需要用 `is_lock_free()` 或 `is_always_lock_free` 判断。

> trivially copyable 自定义类型，简单来说就是：无虚函数、无虚基类；至少有一个未删除的拷贝/移动构造或赋值操作；所有未删除的拷贝/移动构造与赋值都是平凡的；析构函数平凡且未删除。

一个最简单的使用场景是计数器，其示例代码如下：

```cpp
std::atomic<int> counter{ 0 };

void increment()
{
    for (int i = 0; i < 100000; ++i)
    {
        counter++;          // 原子自增
    }
}

int main()
{
    std::thread t1(increment);
    std::thread t2(increment);
    t1.join();
    t2.join();
    std::cout << counter.load() << std::endl;  // 200000
}
```

如果用普通 `int`，结果不可预测（数据竞争导致未定义行为），通常小于 200000。

### 原子操作函数

`std::atomic<T>` 提供了一系列的通用、特化和运算符重载函数：

| 分类 | 函数 | 适用范围 |
| --- | --- | --- |
| 构造/析构 | `atomic()`、`atomic(T)`、`~atomic()` | 通用 |
| 读取 | `load()`、`operator T()` | 通用 |
| 写入 | `store()`、`operator=(T)` | 通用 |
| 交换 | `exchange()` | 通用 |
| 比较交换 | `compare_exchange_weak()`、`compare_exchange_strong()` | 通用 |
| 查询 | `is_lock_free()`、`is_always_lock_free` | 通用 |
| 等待/通知 (C++20) | `wait()`、`notify_one()`、`notify_all()` | 通用 |
| 算术 fetch | `fetch_add()`、`fetch_sub()` | 整数 / 指针 |
| 位运算 fetch | `fetch_and()`、`fetch_or()`、`fetch_xor()` | 仅整数 |
| 算术运算符 | `++`、`--`、`+=`、`-=` | 整数 / 指针 |
| 位运算符 | `&=`、`｜=`、`^=` | 仅整数 |

> 注：`std::atomic<T>` 默认构造自 C++20 起会对底层 `T` 做值初始化（等价于 `T()`，故 `std::atomic<int> a;` 得到 0）；C++11–17 则为未初始化的不确定值，读取前必须先写入。此外，原子变量的初始化本身不是原子操作，若在构造期间被其他线程访问属于未定义行为，通常应在线程启动前完成初始化。

#### 基础函数

```cpp
struct Point { int x, y; };

// ===== 通用 =====
std::atomic<Point> p{ Point{1, 2} };        // 构造
Point cur = p.load();                       // load
p.store(Point{ 3, 4 });                     // store
Point implicit = p;                         // operator T()
p = Point{ 5, 6 };                          // operator =


// ===== 算术运算符重载 =====
std::atomic<int> a{ 5 };
int x = a++;        // x=5, a=6
int y = ++a;        // y=7, a=7
a += 10;            // a=17
a -= 2;             // a=15
int v = a;          // load
a = 100;            // store

// ===== 位运算符重载 =====
std::atomic<unsigned> b{ 0b1100 };
b &= 0b1010;
b |= 0b0001;
b ^= 0b1111;

// ===== 位运算 =====
std::atomic<unsigned> bits{ 0b1100 };
bits.fetch_and(0b1010);
bits.fetch_or(0b0001);
bits.fetch_xor(0b1111);

// ===== 整数特化：fetch_* =====
std::atomic<int> counter{ 10 };
int o1 = counter.fetch_add(5);            // 10 → 15
int o2 = counter.fetch_sub(3);            // 15 → 12

// ===== 指针特化 =====
int arr[10] = {};
std::atomic<int*> ptr{ arr };
ptr += 2;                                 // 前进 2 个元素
int* po = ptr.fetch_sub(1);               // 返回旧指针

// ===== 交换 =====
Point old = p.exchange(Point{ 7, 8 });    // exchange
```

`std::atomic<T>` 的所有运算符重载都固定使用 `std::memory_order_seq_cst` 访问内存，无法指定内存序。而 `load()`、`store()`、`exchange()`、`compare_exchange_*()`、`fetch_*()` 等函数都提供了带 `memory_order` 参数的重载，可显式指定内存序（默认仍然为 `seq_cst`）。

#### 无锁查询函数

```cpp
bool lock_free1 = p.is_lock_free();
bool lock_free2 = std::atomic<Point>::is_always_lock_free; // C++ 17
```

`is_lock_free()` 是一个成员函数。`is_always_lock_free` 是一个静态常量，C++17 引入。

#### 比较交换函数（CAS操作）

比较交换有两个函数 `compare_exchange_strong()` 和 `compare_exchange_weak()`，其概念逻辑为：

```cpp
if (this->load() == expected)     // 比较
{
    this->store(desired);         // 交换
    return true;
}
else
{
    expected = this->load();      // 回写当前值
    return false;
}
```

1. 成功：`*this == expected` → 写入 `desired`，返回 `true`，`expected` 不变。
2. 失败：`*this != expected` → 不写，返回 `false`，把当前值写回 `expected`。

> 注意：上面用 `==` 只是为了表达概念。标准中 `compare_exchange_*` 实际比较的是值的**表示（value representation）**，即按位比较（memcmp 语义），并不调用 `T` 的 `operator==`。例如对 `std::atomic<double>`，`-0.0` 与 `+0.0` 按位不同（比较为不相等），而同 payload 的 `NaN` 按位相同（比较为相等），结论恰好与 `operator==` 相反。

`compare_exchange_strong()` 和 `compare_exchange_weak()` 的区别是伪失败。当值相等时 `strong` 一定成功（不会伪失败），`weak` 可能伪失败。

| 属性 | `compare_exchange_weak` | `compare_exchange_strong` |
| --- | --- | --- |
| 值相等时是否保证成功 | 可能伪失败 | 一定成功 |
| 返回 `false` 时值一定不等吗 | 不一定 | 一定不等 |
| 是否必须放循环 | 必须 | 可单独用 |
| 性能 | 通常更快 | 稍慢 |
| 典型场景 | CAS 循环 | 单次判断 |

> 伪失败根源：LL/SC 架构（ARM、PowerPC 等）上，CAS 由 ldrex/strex 这类「加载-条件存储」对实现。独占标记绑定在缓存行和执行上下文上，任何破坏标记的事件——同地址或同缓存行的写入、本核中断、上下文切换、缓存行驱逐——都会让条件存储失败，即使值没变。x86 用单条 lock cmpxchg，硬件层面无伪失败，故在当前主流实现上 weak ≈ strong。但这只是实现事实，非标准保证；可移植代码须按标准语义处理伪失败：循环内用 weak，循环外用 strong。

两个函数示例如下：

```cpp
// strong：可单次使用
std::atomic<int> a{10};
int expected = 10;
if (a.compare_exchange_strong(expected, 20))
{
    // 确实原本是 10，已改为 20
}
else
{
    // 原本不是 10，expected 现为 a 的当前值
}

// weak：必须放循环
void add(std::atomic<int>& v, int n)
{
    int expected = v.load();
    while (!v.compare_exchange_weak(expected, expected + n))
    {
        // 失败时 expected 已被自动更新为当前值，直接重试即可
    }
}
```

要循环，用 `weak` 函数，循环消化伪失败；只试一次，用 `strong` 函数，杜绝伪失败。`expected` 是引用，失败自动更新。

> ABA 问题：CAS 只比较值是否相等，若某值经历 A → B → A 的变化，CAS 会把「值仍是 A」误判为「从未被改动」，从而错误地认为状态未被修改（典型场景是无锁栈/链表的节点回收）。由于 CAS 是按 value representation 按位比较，A → B → A 之间的中间修改对 CAS 不可见，因此无法察觉。常用规避手段是给指针附加版本号（tagged pointer，或把指针与计数封装成一个整体用 `std::atomic` 保护），每次修改同时递增版本号，使 ABA 不再等价。

#### 等待通知函数

`std::atomic<T>` 类模板的等待/通知机制是 C++20 引入的功能，用于替代低效的自旋等待，实现零 CPU 占用的阻塞。

`wait(T expected)` 的行为是：如果当前值等于 `expected`，则阻塞线程，直到被 `notify_one()`/`notify_all()` 唤醒，或发生虚假唤醒。唤醒后会重新检查值，如果值仍然等于 `expected`，则继续阻塞（这就是它内部处理虚假唤醒的方式）。

关键保证：`wait()` 绝不会在值仍等于 `expected` 时返回（即使虚假唤醒也会重新检查）；只有收到通知且值已改变后才返回。代码示例如下：

```cpp
std::atomic<int> ready{ 0 };
std::thread t([&] {
    ready.wait(0);
    std::cout << "worker woke up, value=" << ready.load() << std::endl;
    });
std::this_thread::sleep_for(std::chrono::milliseconds(50));
ready.store(1);
ready.notify_one();
t.join();
```

与 `std::condition_variable` 的核心区别：

| 对比项 | `std::atomic::wait` | `std::condition_variable` |
| --- | --- | --- |
| 是否需要 `std::mutex` | 不需要 | 需要 |
| 谓词 | 只需值不相等 | 任意谓词（lambda） |
| 虚假唤醒 | 内部自动处理 | 需手动循环 |

不需要 `std::mutex` 意味着更简单的代码和更低的开销。

### std::atomic_flag

`std::atomic_flag` 是一个特例：它是 C++11 中唯一由标准保证 lock-free 的类型（`is_always_lock_free` 恒为 `true`），仅提供 `test_and_set()` 与 `clear()`；C++20 起新增 `test()` 与等待/通知机制 `wait()`、`notify_one()`、`notify_all()`，常作为自旋锁的底层标志位。

- `test_and_set()`：将标志原子地置为 `true`，并返回其先前的值。
- `clear()`：将标志原子地清零为 `false`。
- C++11–17 默认构造后的状态不确定，必须用 `ATOMIC_FLAG_INIT` 初始化为确定的 clear 状态。
- C++20 起默认构造即为 clear 状态，无需 `ATOMIC_FLAG_INIT`。

用它实现一个简单的自旋锁：

```cpp
std::atomic_flag lock_flag = ATOMIC_FLAG_INIT;   // C++11 需显式初始化

void critical_section()
{
    while (lock_flag.test_and_set(std::memory_order_acquire))   // 自旋等待
    {
        // 已被其他线程占用，继续自旋
    }

    // ===== 临界区 =====
    // ...

    lock_flag.clear(std::memory_order_release);                 // 释放锁
}
```

C++20 起可省略初始化，并可用 `test()` 只读取标志而不修改：

```cpp
std::atomic_flag lock_flag;                      // C++20：默认即为 clear
bool busy = lock_flag.test(std::memory_order_acquire);          // C++20：仅查询，不置位
```

### std::atomic_ref<T>

`std::atomic_ref<T>`（C++20）用于对**已存在的非原子对象**施加原子访问：只要 `T` 满足 trivially copyable 且该对象满足对齐要求，即可通过 `std::atomic_ref<T>{obj}` 对其做原子操作，无需为了原子性去改变对象本身的类型。它常用于把普通对象或第三方库中的数据结构临时纳入原子操作。

```cpp
int value = 0;                                   // 普通（非原子）对象

void increment(std::atomic_ref<int> ref)
{
    for (int i = 0; i < 100000; ++i)
    {
        ref.fetch_add(1);                        // 对该 int 做原子自增
    }
}

int main()
{
    std::atomic_ref<int> ref{ value };           // 为 value 创建原子引用
    std::thread t1(increment, ref);
    std::thread t2(increment, ref);
    t1.join();
    t2.join();
    std::cout << value << std::endl;             // 200000
}
```

对同一个对象，原子引用与非原子访问不能同时存在，否则仍是数据竞争（UB）；在 `std::atomic_ref<T>` 的生命周期内，被引用对象必须保持有效，且满足对齐要求。

### 注意事项

1. `std::atomic<T>` 不可拷贝/移动（C++11），因为拷贝不是原子的。
2. 多个变量之间没有原子性：两个 atomic 分别操作之间可以被其他线程插入。
3. `std::atomic<T>` 不保证 lock-free，`is_lock_free()` 和 `is_always_lock_free` 可检查是否无锁实现。
4. 不要滥用：复杂逻辑仍应用 `std::mutex`，无锁编程容易引入难以调试的 bug。
5. `volatile` 不是同步原语：它只阻止编译器对访问做优化（如缓存到寄存器、消除看似冗余的读写），既不提供原子性，也不提供任何内存序保证，不能替代 `std::atomic` 或 `std::mutex` 来解决数据竞争。

## 内存序与内存屏障

### 核心概念

**内存序（`std::memory_order`）**

从 C++11 开始，标准库引入了内存序支持，用一组描述顺序强度的枚举值为不同硬件内存模型（尤其是弱内存序架构）提供语言层面统一、可移植的顺序保证。它与**原子操作**（`std::atomic<T>`）及**原子围栏**（`std::atomic_thread_fence`）配合，当**带 `release` 语义的写操作**（`release`/`acq_rel`/`seq_cst`）与**带 `acquire` 语义的读操作**（`acquire`/`acq_rel`/`seq_cst`）正确配对时，建立 synchronizes-with 关系（进而构成跨线程的 happens-before 关系），从而实现同步。而 `relaxed` 不建立跨线程同步。注意 `acq_rel` 仅可用于读-改-写（RMW）操作：纯 store 不能指定 `acquire`/`acq_rel`，纯 load 不能指定 `release`/`acq_rel`。

**内存屏障（memory barrier / memory fence）与原子围栏（`std::atomic_thread_fence`）**

**内存屏障**是硬件层的概念，指 CPU 提供的一条屏障指令（如 x86 的 `mfence`/`lfence`/`sfence`、ARM 的 `dmb`/`dsb`/`isb`、PowerPC 的 `sync`/`lwsync`/`isync`），它直接作用在硬件上，阻止 CPU 的乱序执行跨越屏障。这是真正的物理屏障。

**原子围栏**是语言层的接口，C++11 标准库提供的一条独立语句，接受 `std::memory_order` 参数。它描述的是**顺序语义契约**，编译后可能生成硬件屏障指令，也可能只生成编译器屏障，这取决于平台的内存模型和指定的内存序。它是硬件屏障在语言层面的**可移植抽象**。

两者的关系类似 CPU 指令与 C++ 函数调用：内存屏障是目标平台上的真实机器指令，`std::atomic_thread_fence` 是在 C++ 里写的、编译后可能产出那条指令的接口。之所以叫原子围栏，是因为它提供的是与原子操作同等强度的同步语义，和 `std::atomic<T>` 附带的内存序参数本质上是一回事，区别只在作用范围（一条操作 vs 一道界线）。

### 内存序（memory order）

内存序决定的是操作之间的顺序，以及一个线程的写操作何时、以何种顺序被其他线程观察到；它约束的是原子操作或原子围栏与周围内存访问之间的相对顺序和可见性，并在正确配对（如 `release`/`acquire`）时建立线程间同步。

#### 内存序的顺序语义

`std::memory_order` 是一组枚举值，它规定一次内存访问的同步强度与可见性，也就是允许编译器和 CPU 把它前后的内存操作重排到什么程度。它描述的是**访问之间的顺序关系**，常见取值如下：
1. **`memory_order_relaxed`**：最宽松，不施加任何顺序约束，编译器和 CPU 可自由重排它前后的内存访问（该原子对象自身的修改顺序一致性仍由原子性保证）。
2. **`memory_order_acquire`**：用于读操作，禁止其**之后**的内存访问被重排到该操作**之前**。
3. **`memory_order_release`**：用于写操作，禁止其**之前**的内存访问被重排到该操作**之后**。
4. **`memory_order_acq_rel`**：兼具 `acquire` 与 `release` 语义，用于既要读又要写的场合（读-改-写操作）。
5. **`memory_order_seq_cst`**：最严格，在 `release`/`acquire` 的基础上，额外要求所有线程看到同一个全局的操作总顺序（顺序一致性）。
6. **`memory_order_consume`**：基于数据依赖提供更弱的顺序保证，C++17 起被标准不建议使用，按 C++26 现行草案其语义被调整为与 `acquire` 等价（功能上移除，最终以发布标准为准），实际项目应直接使用 `memory_order_acquire`。

选择合适的 `std::memory_order` 不仅关乎正确性，更直接影响性能，理解其语义是避坑的第一步。

#### 内存序的载体

枚举值描述的是访问之间的顺序，但它本身不能单独生效，必须依附在载体上，载体有且只有两种：
1. **附着在原子操作上（参数形式）**：如 `x.store(1, std::memory_order_release)`。只约束这一条操作，同步经由该原子对象的写-读配对建立。这同时也是内存序唯一带默认值的场合，**不传参数时默认为 `std::memory_order_seq_cst`**（`std::atomic<T>` 的运算符重载固定为 `seq_cst`，无法指定）。读-改-写操作（`fetch_*`、`exchange`、`compare_exchange`）既可指定 `acq_rel`，也可按需指定其他取值。
2. **附着在独立原子围栏上（语句形式）**：如 `std::atomic_thread_fence(std::memory_order_release)`。约束界线前后**所有**内存访问（含非原子访问），同步仍需配合某个原子对象的 `relaxed` 读写、由 fence 升级建立。

两种载体的语义完全同源（`acquire`/`release`/`seq_cst` 的含义一致），但需要注意：以 `relaxed` 为参数的围栏是空操作——`relaxed` 本身不含任何顺序约束，没有可供 fence 放大的语义。

| 维度 | 载体一：原子操作 + 内存序参数 | 载体二：原子围栏（`std::atomic_thread_fence`） |
| --- | --- | --- |
| 解决的问题 | 单条原子操作的顺序与跨线程可见性 | 一道界线前后所有内存访问的重排约束 |
| 约束范围 | 该操作前后不得越界重排 | 界线前后所有访问不得跨越重排 |
| 同步建立方式 | 直接经由该原子对象的写-读配对 | 配合某原子对象的 `relaxed` 写-读，由 fence 升级 |
| 典型场景 | 发布-获取标志位、引用计数、无锁 CAS 循环 | 扫描多个 `relaxed` 标志后集中补一道 fence；批量 `relaxed` 操作共享同一同步点 |
| 选择原则 | 默认写法：直观、不易放错位置 | 仅当一条约束需同时升级多条 `relaxed` 操作时更划算 |

一句话总结：内存序配合原子操作，约束的是该原子点前后普通访问能否越过它，`release`/`acquire` 配对可直接建立同步。内存序配合原子围栏，约束的是界线两侧所有相关访问能否越过它，但围栏需与至少一个原子操作配合才能建立同步。

#### `happens-before` 与 `synchronizes-with`

- **synchronizes-with（同步于）**：线程 `A` 对原子对象 `M` 的带 `release` 语义的原子写操作（`release`/`acq_rel`/`seq_cst`，作用于 store 或 RMW），被线程 `B` 对同一对象 `M` 的带 `acquire` 语义的原子读操作（`acquire`/`acq_rel`/`seq_cst`，作用于 load 或 RMW）读到，则二者建立 synchronizes-with 关系。此外，`release` fence 配合一个后续原子写、`acquire` fence 配合一个前序原子读，在满足顺序条件且读观察到写时，也能建立等价于 `release`/`acquire` 原子操作之间的同步效果。
- **happens-before（先于）**：由两部分复合而成——同一线程内按语句顺序确立的 sequenced-before，加上跨线程的 synchronizes-with，再取传递闭包。其实际效果是：若 `A` 的写 happens-before `B` 的读，则 `A` 中位于该写之前的所有写操作，`B` 都能观察到。

这也正是 `release` 语义的写操作必须与 `acquire` 语义的读操作配对使用的原因。多线程同步的可见性保证由 happens-before 关系给出；synchronizes-with 是跨线程建立 happens-before 的主要途径。`relaxed` 不携带 `release`/`acquire` 语义，无论怎么配都建立不了同步关系。

标准中 synchronizes-with 最常见的建立组合有四种（每种都要求写侧带 `release` 语义、读侧带 `acquire` 语义，`acq_rel`/`seq_cst` 也在其中）：

| 写方 | 读方 |
| --- | --- |
| `release` store | `acquire` load |
| `release` store | `acquire` fence（+ `relaxed` load） |
| `release` fence（+ `relaxed` store） | `acquire` load |
| `release` fence（+ `relaxed` store） | `acquire` fence（+ `relaxed` load） |

> 注意：表格中第一种组合的准确表述是——`acquire` 读读到 `release` 写**或以它为首的释放序列（release sequence）**中的任意值，同步即可成立。释放序列指 `release` 写之后、同一原子对象上由同一线程的后续写、或任何线程的读-改-写操作（无论何种内存序）延续的写入链。这正是共享指针引用计数递减用 `acq_rel` 即可、无需 `seq_cst` 的理论依据。

> 注意：happens-before 具有**传递性**：若 `A` happens-before `B`、`B` happens-before `C`，则 `A` happens-before `C`。多个线程可以借助 release-acquire 链（包括 `acq_rel`/`seq_cst` 等带相应语义的操作）逐段传递可见性。

#### relaxed 与 seq_cst 的对比

1. **`relaxed`**
   - **优点**：开销极低，只涉及该原子对象自身的读写，不做跨线程排序。适合彼此无依赖的独立操作，如日志计数器；又如引用计数的**递增**通常用 `relaxed`。
   - **缺点**：不建立线程间的同步，无法用来在多个线程间安全地传递其他（非原子）数据。注意它并非"不可见"——同一原子对象在所有线程间仍有一致的修改顺序（coherence），缺的是**跨线程、跨变量的顺序保证**。

2. **`seq_cst`**
    - **优点**：提供最强的顺序保证，所有线程感知到一致的操作序列，逻辑简单，易于推理。
    - **缺点**：需要维护全局的操作总序，在弱序平台上会插入额外屏障，多核系统中可能引发跨核同步开销。

3. **性能差异**
    - `relaxed` 不做任何跨线程排序，通常最轻量；`seq_cst` 的开销则取决于平台和操作类型：在 x86 等强序平台上差距可能很小，而在 ARM/PowerPC 等弱序平台上差距明显。

一个常见误解是 `relaxed` 不保证可见性。实际上，标准要求同一个原子对象在所有线程之间存在一个唯一的**修改顺序（modification order）**。任何线程读取它时，只能读到修改顺序中的某个值，且不会出现先读到较新的值，再读到较旧的值的回退（这是 coherence 的要求之一）。因此 `relaxed` 保证的是**单个原子对象自身的一致性**；它缺的只是**跨线程、跨变量的顺序与同步**，所以不能用来在线程间安全传递非原子数据。

#### 内存序与原子操作配合使用

1. 发布-获取（release-acquire）模式，误用 `relaxed` 导致数据不一致

原始代码如下：

```cpp
#include <atomic>
#include <thread>
#include <iostream>

std::atomic<int> flag{ 0 };
std::atomic<int> data{ 0 };

void producer()
{
    data.store(42, std::memory_order_relaxed);   // 数据更新
    flag.store(1, std::memory_order_relaxed);    // 顺序未保证
}
void consumer()
{
    while (flag.load(std::memory_order_relaxed) != 1);  // 忙等待
    int val = data.load(std::memory_order_relaxed);
    std::cout << "Data: " << val << std::endl;   // 可能输出 0
}

int main()
{
    std::thread t1(producer);
    std::thread t2(consumer);
    t1.join();
    t2.join();
    return 0;
}
```

`producer` 中 `data` 与 `flag` 的写入顺序没有受到任何约束。由于 `relaxed` 不建立同步，编译器与 CPU 都可能把 `flag.store(1)` 重排到 `data.store(42)` 之前，于是 `consumer` 可能先看到 `flag == 1`，却仍读到旧的 `data == 0`。这是误以为写入顺序就是观察顺序的典型陷阱。

> 注意：由于 `data` 也是原子变量，这里不构成数据竞争，程序行为是良定义的，只是结果可能不符合预期。若把 `data` 换成普通 `int`，并发读写就构成数据竞争，属于未定义行为，后果远不止读到旧值。

使用 `release`/`acquire` 配对建立线程间同步的优化代码如下：

```cpp
#include <atomic>
#include <thread>
#include <iostream>

std::atomic<int> flag{ 0 };
std::atomic<int> data{ 0 };

void producer()
{
    data.store(42, std::memory_order_relaxed);   // 数据更新无需强同步
    flag.store(1, std::memory_order_release);    // 确保 data 更新先于 flag
}
void consumer()
{
    while (flag.load(std::memory_order_acquire) != 1);  // 看到 flag 更新后再读 data
    int val = data.load(std::memory_order_relaxed);
    std::cout << "Data: " << val << std::endl;   // 保证输出 42
}

int main()
{
    std::thread t1(producer);
    std::thread t2(consumer);
    t1.join();
    t2.join();
    return 0;
}
```

`release` 保证 `data` 的写入不会被重排到 `flag` 的写入之后，`acquire` 保证 `consumer` 在看到 `flag == 1` 之后才会执行后续读取。这一对 `release`/`acquire` 建立了标准中的"同步于（synchronizes-with）"关系，从而使 `producer` 中 `flag.store` 之前的所有写入对 `consumer` 可见。这种发布-获取（release-acquire）模式轻量且正确，避免了 `seq_cst` 的过度同步。注意：必须是 `release` 语义的写与 `acquire` 语义的读配对，且作用于同一原子对象。

2. 过度使用 `seq_cst` 的代价（与平台相关）

原始代码如下：

```cpp
#include <atomic>
#include <thread>
#include <iostream>

std::atomic<int> counter{ 0 };
void increment()
{
    for (int i = 0; i < 1000000; ++i)
    {
        counter.fetch_add(1, std::memory_order_seq_cst);   // 过度同步
    }
}
int main()
{
    std::thread t1(increment);
    std::thread t2(increment);
    t1.join();
    t2.join();
    std::cout << "Counter:" << counter << std::endl;   // 预期 2000000
    return 0;
}
```

`fetch_add` 只需要保证原子性，不需要全局顺序一致性，默认使用 `seq_cst` 属于用最贵的工具干最轻的活。但需要强调的是：代价大小与平台强相关，不能一概而论。
- 在 x86/x64 这类强序（TSO）平台上，`fetch_add` 无论用 `seq_cst` 还是 `relaxed`，都会被编译成带 `lock` 前缀的读改写指令，二者耗时几乎相同，改成 `relaxed` 通常看不出收益。
- 在 ARM、PowerPC 等弱序平台上，`seq_cst` 会额外插入全屏障指令，此时放松内存序才有明显价值。

`seq_cst` 真正昂贵的地方，往往不是 RMW（读-改-写），而是对原子对象的纯 `store`（以及 `seq_cst` fence）。例如 x86 上一条 `seq_cst` store 需要额外的 `mfence`（或改用 `xchg`）来强制全局可见顺序，而 `relaxed` store 只是一条普通 `mov`；`seq_cst` load 在 x86 上同样是普通 `mov`，与 `relaxed` load 同价，其额外代价只体现在 ARM/PowerPC 等弱序平台上。

优化代码如下：

```cpp
#include <atomic>
#include <thread>
#include <iostream>

std::atomic<int> counter{ 0 };
void increment()
{
    for (int i = 0; i < 1000000; ++i)
    {
        counter.fetch_add(1, std::memory_order_relaxed);
    }
}
int main()
{
    std::thread t1(increment);
    std::thread t2(increment);
    t1.join();
    t2.join();
    std::cout << "Counter:" << counter << std::endl;   // 预期 2000000
    return 0;
}
```

把 `seq_cst` 换成 `relaxed`，去掉不必要的排序约束，逻辑上依然正确（计数器结果仍是 2000000），在弱序平台上收益明显；在 x86 上则收益有限。核心原则是：只在确实需要跨线程顺序保证时才使用更强的内存序。

#### 内存序与原子围栏配合使用

除了给单个原子操作指定内存序，C++ 还提供独立的**原子围栏**接口：
- `std::atomic_thread_fence(std::memory_order)`：**线程间屏障**。它自身不依附于任何原子对象，但建立同步仍需经由**某个原子对象 `M` 的一写一读**（用 `relaxed` 即可）——fence 的作用是把这一对 `relaxed` 操作"升级"出 `release`/`acquire` 语义，并把顺序约束扩展到屏障两侧的**所有**内存访问（含非原子访问）。例如 `x.store(1, std::memory_order_release)` 的效果，可以拆成"先执行 `std::atomic_thread_fence(std::memory_order_release)`，再执行 `x.store(1, std::memory_order_relaxed)`"。
- `std::atomic_signal_fence(std::memory_order)`：**编译器屏障**，只阻止编译器重排，不生成硬件屏障指令，用于线程与信号处理函数之间的场景。

1. 用 `release` fence/`acquire` fence 实现同步，下面的代码与发布-获取模式示例的优化版本完全等价，只是把附着在原子操作上的内存序换成了独立的 fence：

```cpp
#include <atomic>
#include <thread>
#include <iostream>

std::atomic<int> flag{ 0 };
std::atomic<int> data{ 0 };

void producer()
{
    data.store(42, std::memory_order_relaxed);
    std::atomic_thread_fence(std::memory_order_release);   // release fence：屏障前的写入不得重排到屏障后
    flag.store(1, std::memory_order_relaxed);              // 效果相当于 release store
}
void consumer()
{
    while (flag.load(std::memory_order_relaxed) != 1);     // 配合下方 fence，效果相当于 acquire load
    std::atomic_thread_fence(std::memory_order_acquire);   // acquire fence：屏障后的读取不得重排到屏障前
    int val = data.load(std::memory_order_relaxed);
    std::cout << "Data: " << val << std::endl;             // 保证输出 42
}

int main()
{
    std::thread t1(producer);
    std::thread t2(consumer);
    t1.join();
    t2.join();
    return 0;
}
```

`release fence` 后接 `relaxed store` ≈ `release store`；`relaxed load` 后接 `acquire fence` ≈ `acquire load`。

fence 的价值在于：一条屏障可以同时升级其前后的多条 `relaxed` 操作（例如循环中多次读写，只需一对 fence），把同步点集中，减少开销，代价是位置必须精确。把 `acquire` fence 放到 `load` 之前、或把 `release` fence 放到 `store` 之后，同步关系都不成立。


2. 如下示例使用 `release` 写操作/`acquire` fence 实现多写一读、命中才补 `acquire` fence，这也正是 fence 无法被单操作内存序替代的价值所在

```cpp
#include <atomic>
#include <thread>
#include <cassert>
#include <vector>

constexpr int N = 2;
std::atomic<int> flag[N];
int data[N];

void writer(int i)
{
    data[i] = i + 1;   // 先写数据
    flag[i].store(1, std::memory_order_release);    // release 写 flag
}

void reader()
{
    for (int i = 0; i < N; ++i)
    {
        if (flag[i].load(std::memory_order_relaxed) == 1)    // 扫描用廉价的 relaxed
        {
            std::atomic_thread_fence(std::memory_order_acquire);   // 命中才补 fence
            assert(data[i] == i + 1);   // 必然成立
        }
        // 读到 0 也无妨：只是本次跳过，不构成任何竞争
    }
}

int main()
{
    std::vector<std::thread> ws;

    for (int i = 0; i < N; ++i)
        ws.emplace_back(writer, i);

    std::thread r(reader);

    for (auto& t : ws)
        t.join();

    r.join();
}
```

同步链为：`writer()` 的 `release store` → `reader()` 的 `relaxed load` 读到 1 → `reader()` 的 `acquire fence`。`writer()` 在 store 之前写入的 `data[i]` 对 `reader()` 可见。在弱序平台上 `acquire load` 每次都有屏障代价，而 `relaxed load` 几乎没有。扫描次数越多、命中越少，这个模式省得越多。

### 总结

#### 原子操作与原子围栏的选择

**memory order 选择：**
- 无依赖操作用 `relaxed`，追求性能（但仍保证该原子对象自身的读写一致性）。
- 有跨线程依赖的数据传递：`release` 语义的写与 `acquire` 语义的读配对（基础写法是 `release` store 配 `acquire` load）。RMW 操作（`fetch_*`/`exchange`/`compare_exchange`）用 `acq_rel` 同时满足两侧，`seq_cst` 则多带全局序但开销最高。`relaxed`/`consume` 无法建立同步。
- 仅在需要全局一致的观察顺序时使用 `seq_cst`，避免滥用。

**fence 选择：**
- 默认把内存序直接写在原子操作上，直观且不易放错位置。
- 仅当一条约束需同时升级多条 `relaxed` 操作（如批量扫描后集中同步）时，才使用 `std::atomic_thread_fence`，并格外留意屏障的放置方向。

#### 内存屏障与原子围栏的关系

理解了内存序的语义和两种载体后，再把整个链条串起来，就能看清内存屏障和原子围栏的关系，它们分布在三层结构的不同层级上：

```
┌─────────────────────────────────────────────────────────┐
│  语义层：std::memory_order 枚举值                        │
│  （relaxed / acquire / release / acq_rel / seq_cst）     │
│  描述顺序强度，本身什么也不做                              │
└─────────────────────────────────────────────────────────┘
           ↓ 依附于
┌─────────────────────────────────────────────────────────┐
│  语言层：两种载体                                         │
│  ├── atomic<T> + memory_order 参数                       │
│  │   例：x.store(1, memory_order_release)                │
│  └── atomic_thread_fence(memory_order)                   │
│      例：atomic_thread_fence(memory_order_release)       │
│  两者语义完全同源，是可移植的 C++ 接口                     │
└─────────────────────────────────────────────────────────┘
           ↓ 编译生成
┌─────────────────────────────────────────────────────────┐
│  指令层：编译器屏障 + 硬件屏障指令                         │
│  ├── 编译器屏障：阻止编译器重排                            │
│  │   （如 GCC 的 __asm__ __volatile__("" ::: "memory")） │
│  └── 硬件屏障指令：阻止 CPU 乱序                          │
│      x86: mfence / lfence / sfence                      │
│      ARM: dmb / dsb / isb                               │
│      PowerPC: sync / lwsync / isync                     │
└─────────────────────────────────────────────────────────┘
```

> 关键点：**语言层接口编译后生成什么指令，取决于平台内存模型和指定的内存序**。同一个 `atomic_thread_fence(memory_order_release)`，在 x86 TSO 强序平台上通常只生成编译器屏障（因为硬件天然保证两点：写不与写重排、写不被重排到更早的读之前，release 语义的约束天然成立），而在 ARM/PowerPC 弱序平台上则真的生成硬件屏障指令（如 `dmb ish`）。这也解释了为什么性能差异高度依赖平台：弱序平台需要真正的硬件屏障，开销显著，而强序平台大多省了这一步。同理，`seq_cst` 在 x86 上最昂贵的时刻也正是需要硬件屏障的时刻，比如 `seq_cst store` 会额外生成一条 `mfence`，而 `relaxed store` 只是一条普通的 `mov` 指令。

### 注意事项

1. 平台差异：

    内存序与内存屏障的实际开销取决于 CPU 的内存模型
    - **x86/x64（TSO 强序模型）**：`load` 天然具有 `acquire` 语义、`store` 天然具有 `release` 语义，因此 `release`/`acquire` 通常只产生编译器屏障、几乎不增加硬件指令；只有 `seq_cst` 的 `store`/fence 才需要 `mfence`（或 `xchg`）。RMW 操作则无论如何都需要 `lock` 前缀。
    - **ARM / PowerPC（弱序模型）**：`load`/`store` 可能被硬件乱序执行，`release`/`acquire` 需要真正的屏障指令（如 ARM 的 `dmb`、PowerPC 的 `sync`），此时不同内存序的性能差异才明显。

2. 与 CAS 的配合：

    `compare_exchange_weak`/`compare_exchange_strong` 接受两个内存序参数（成功序、失败序）。**失败序不能强于成功序**，且失败序不允许为 `release` 或 `acq_rel`。常见写法是成功用 `acq_rel`（或 `release`），失败用 `acquire`（若失败路径无需同步，也可用 `relaxed` 以省开销）。

3. `volatile` 不能替代原子与内存序：

    `volatile` 只保证编译器不优化掉对该变量的访问，它**既不保证原子性，也不提供任何线程间同步或顺序语义**（多线程下访问 `volatile` 变量仍可能构成数据竞争）。它适用于内存映射寄存器等场景，不能用于线程同步。

## 同步相关机制与设施对比

围绕多线程同步，我们了解到了六种相关的机制与设施，很多初学者会把这几者当成同一类东西的不同写法，其实它们解决的是不同层面的问题，不是互替关系：
- **互斥量（`std::mutex`）**：保证**一段代码（临界区）**的互斥执行，保护的是多个变量之间的**不变式**（如"`a` 和 `b` 必须同时更新"）。
- **条件变量（`std::condition_variable`，以及 `std::condition_variable_any`）**：**不保护数据**，必须与互斥量配合使用；作用是让线程**挂起等待**某个谓词（条件）成立，由 `notify_one`/`notify_all` 唤醒，从而取代忙等待；同步经由 `wait()` 内部对互斥量的 unlock（`release` 语义）与重新 lock（`acquire` 语义）配对建立。
- **信号量（`std::counting_semaphore` / `std::binary_semaphore`，C++20）**：通过**许可计数**限制并发数量，或作简单的跨线程通知；`acquire()` 在无许可时阻塞（`acquire` 语义），`release()` 归还许可（`release` 语义）。其中 `binary_semaphore` 即计数上限为 1 的信号量。
- **原子操作（`std::atomic`）**：保证**单个变量**访问的不可分割性，但无法保护多变量间的一致性。
- **内存序（`memory order`）**：**不是独立的同步工具**，它是一组描述顺序强度的枚举值，需要依附在"载体"上才能生效——载体既可以是原子操作（参数形式），也可以是**原子围栏**（语句形式），详见上文「内存序的载体」。脱离载体谈内存序是没有意义的。
- **原子围栏（`std::atomic_thread_fence`）**：内存序语义的**独立形态**，语言层接口——不附着在某一条原子操作上，而是单独成行，对界线两侧**所有**内存访问（含非原子访问）施加**有方向**的重排约束。它编译后可能生成硬件层的内存屏障指令（如 x86 的 `mfence`、ARM 的 `dmb`），也可能只是编译器屏障，取决于平台和内存序。它同样不保护数据，需与原子操作配合才能建立跨线程同步。

六者对比如下：

| 维度 | 互斥量 `std::mutex` | 条件变量 `std::condition_variable` | 信号量 `std::counting_semaphore` | 原子操作 `std::atomic` | 内存序 `memory order` | 原子围栏 `atomic_thread_fence` |
| --- | --- | --- | --- | --- | --- | --- |
| 解决的问题 | 临界区的互斥执行 | 等待某个谓词成立，避免忙等待 | 限制并发数量、跨线程通知（许可计数） | 单个变量访问的不可分割性 | 操作之间的顺序与可见性（依附于原子操作或原子围栏） | 界线两侧内存访问的重排约束 |
| 保护粒度 | 任意大小的临界区、多变量不变式 | 不保护数据，须配合互斥量 | 不保护数据，管理"许可"配额 | 单个对象 | 不保护数据，仅约束顺序 | 不保护数据，作用于代码中的一条"界线" |
| 是否阻塞 | 竞争时可能阻塞（陷入内核等待） | 阻塞等待，直到被唤醒且谓词成立 | 许可耗尽时阻塞 | 主流平台上的整型/指针类型通常 `is_lock_free()` 为 true、不阻塞 | —（只是一个参数） | —（只是一条语句） |
| 顺序保证 | `lock()`/`unlock()` 自带 `release`/`acquire` 语义 | 经由 `wait()` 内部对互斥量的 unlock/lock 配对建立 happens-before | `acquire()`/`release()` 自带 `release`/`acquire` 语义 | 由内存序参数决定（默认 `seq_cst`） | 本身就是顺序语义的来源 | 与内存序同级的语义，独立施加 |
| 典型场景 | 复杂共享状态、多变量一致性 | 生产者-消费者、等待任务就绪 | 线程池限流、资源计数、简单通知 | 计数器、标志位、无锁数据结构 | 发布-获取、无锁算法的精细控制 | 无锁算法中集中同步点，配合 `relaxed` 操作 |
| 主要风险 | 死锁、优先级反转 | 丢失唤醒、虚假唤醒（必须在循环中检查谓词） | 许可计数泄漏/过度释放、被误当作互斥量 | 误用内存序导致数据不一致、ABA 问题 | 过弱则错、过强则慢 | 放置位置错误导致同步失效 |

几个容易忽略的联系与误区：
1. 互斥量内部就隐含了内存序语义：`lock()` 相当于 acquire 操作，`unlock()` 相当于 release 操作。因此互斥锁保护的临界区天然建立了 happens-before 关系。你用 `std::mutex` 时其实一直在享受 `release`/`acquire` 语义，只是由标准库替你完成了。
2. 原子操作不是更快的互斥量：它不能保护不变式（例如"转账时 `a` 账户扣款与 `b` 账户入账必须一起被看到"这种需求），两个独立的 `std::atomic<T>` 变量无法满足（其他线程可能看到只完成了一半的中间态），必须用互斥量，或把两个值打包成**一个**原子对象。
3. 选择经验法则：能用互斥量清晰表达的逻辑，优先用互斥量（正确性优先、代码易推理）；需要等待某条件成立时用条件变量（或 C++20 的 `std::atomic::wait`），而不是自旋或 `sleep` 轮询；需要限制并发数量或做通知时用信号量；只有当临界区退化到单个变量的读写/计数，或性能分析证明锁是瓶颈时，才下沉到 `std::atomic` + 内存序的精细控制。原子与内存序属于优化手段，不应作为默认写法。
4. 条件变量与信号量的核心职责是等待/准入：它们负责让线程合理地阻塞与唤醒（避免忙等、限制并发数）；而一个线程的写何时对另一个线程可见，仍由它们内部的 `release`/`acquire` 语义顺带保证（使用原子操作时，则由你显式指定的内存序决定）。
